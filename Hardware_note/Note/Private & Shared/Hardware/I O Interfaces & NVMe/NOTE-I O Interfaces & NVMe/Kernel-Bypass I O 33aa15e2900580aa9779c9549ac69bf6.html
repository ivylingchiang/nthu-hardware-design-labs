Kernel-Bypass I/O

在現代高速存儲系統中，NVMe SSD 的延遲已演進至微秒 (μs) 等級。這使得傳統 Linux Kernel 的 I/O 棧（Stack）從原本的「加速器」變成了效能「瓶頸」。身為系統架構師，我們必須重新審視底層 I/O 路徑，理解從 Kernel-space 轉向 User-space 的技術動機與架構演變。

Key Word Definition/ Discussion
Kernel bypass

當 NVMe SSD 硬體延遲降到微秒等級時，傳統針對 HDD 設計的作業系統軟體層（Block Layer、File System 等 Kernel I/O Stack）開銷變得極度顯著，成為拖垮整體系統效能的瓶頸。

Kernel I/O 的轉型背景與效能瓶頸

  • I/O Scheduling (I/O 排程) 的失效 原本為 HDD 設計的「電梯演算法」（Elevator Algorithm）旨在減少物理磁頭的移動路徑。然而，NVMe SSD 具備極高的並行處理能力與無機械運作特性，複雜的排程演算法反而增加 CPU 計算延遲，現在的重點已轉向如何極大化減少處理路徑。
  • I/O Merging (I/O 合併) 的效能折損 合併請求是為了補償 HDD 隨機讀寫效能差的弱點。但在 SSD 高隨機存取能力面前，判斷並執行請求合併的 CPU 運算成本，往往高於直接發送多個小 I/O 所產生的收益，導致其成為效能拖油瓶。
  • Interrupts (中斷機制) 導致的上下文切換 中斷會強迫 CPU 停止目前任務進行 Context Switch（上下文切換）。在每秒數百萬次 I/O (IOPS) 的場景下，頻繁的中斷會使 CPU 浪費大量週期在處理核心狀態切換，而非實際搬運數據。

極致效能並非沒有代價，繞過 Kernel 意味著必須自行處理原本由作業系統託管的複雜服務。

服務類別傳統 Kernel I/OSPDK Kernel-Bypass
Security/Isolation (安全性與隔離)由 Kernel 統一管理，程序間隔離嚴密。應用程式直接操作硬體，安全性防線後退至應用層。
Fairness/Sharing (公平性與共享)核心排程器確保多個程序公平分配資源。通常由單一程序獨佔資源，難以在多個程序間彈性共享。
POSIX Ecosystem (標準生態系)支援 open/read/write，開發成本低。須使用特定 API，與現有 POSIX 程式不相容，重寫成本高。

解釋為什麼傳統針對 HDD 設計的 I/O 機制（排程、合併、中斷）在高速 NVMe SSD 時代反而會成為效能「拖油瓶」。

中間路線：eBPF/XRP 與 xNVMe

  • 簡介：極致的 Kernel Bypass 需要付出極大代價（失去 OS 管理與 POSIX 相容性）。對於成熟的系統（如 PostgreSQL），全面推翻 Kernel 路徑並不切實際，因此出現了不需完全繞過 Kernel 的中間方案。
  • 重點：
    • eBPF / XRP：允許將自定義的處理邏輯「下放」到 Kernel 的驅動層執行。這能大幅縮短 I/O 路徑，跳過 Block Layer 或 File System 的開銷，同時確保程式仍留在 Kernel 環境的保護中。
    • xNVMe：提供一層統一的抽象介面。開發者只需寫一次程式，就能在不大幅修改架構的前提下，靈活切換底層要使用 io_uring、SPDK 還是標準 Syscall。
  • 考試：
    • 為什麼需要中間路線？（關鍵字：相容性、重寫成本、POSIX 生態系）。
    • 比較 eBPF/XRP 與徹底 Kernel Bypass 的適用場景差異。
  • 補充：
    • Pitfall: 評估存儲架構時，不可僅看極限效能。成熟資料庫若強行引入 SPDK，可能因失去 File System 支援或重寫核心模組而導致專案失敗。

Pitfall:
有些系統在升級 SSD 後效能不如預期，往往是因為沒有調整 OS 層級的 I/O Scheduler（例如應將其設為 none 或 kyber），導致軟體層吃掉硬體紅利。

SPDK

SPDK (Storage Performance Development Kit) 是一套建立在 DPDK (Data Plane Development Kit) 之上的框架，旨在透過 User-space 驅動程式徹底榨乾硬體效能。

  • User-space Driver & Hugepages：將驅動移至用戶空間。利用大頁記憶體 (Hugepages, 如 2MB/1GB) 減少 CPU 的 TLB Miss，並確保實體連續的 DMA buffer，讓硬體能繞過 Kernel 直接存取記憶體。同時透過 MMIO 直接操作硬體佇列。
  • Polling Mode (輪詢模式)：完全捨棄硬體中斷。改派專屬 Thread 持續輪詢 (Polling) 檢查 Completion Queue (CQ)。雖然 CPU 使用率較高，但完全消除了中斷造成的 Context Switch 開銷。
  • Lockless Design & Thread-to-queue affinity：採用 Share-nothing 架構，每個 Thread 綁定專屬的 I/O 佇列。處理過程中不需要爭搶全域鎖 (Global Lock)，徹底消除多核心間的鎖競爭 (Lock contention)。

SPDK I/O 流程追蹤 (全程無 Syscall、無 Interrupt、無 Context Switch)

  1. 請求初始化：應用程式在 User-space 準備好數據，存放在 Hugepage DMA buffer。
  1. 提交指令：SPDK 直接將指令寫入 NVMe 的 Submission Queue (SQ)。
  1. 觸發硬體：透過 MMIO 更新 Doorbell Register，通知 SSD 執行任務。
  1. 數據傳輸：SSD 透過 DMA 直接從 User-space 緩衝區進行數據搬運。
  1. 完成偵測：Polling Thread 持續監測 Completion Queue (CQ)，一旦發現 I/O 完成即刻回報。
  • SPDK I/O 的完整流程：User-space 準備 DMA buffer -> 指令寫入 SQ -> MMIO 敲擊 Doorbell 觸發硬體 -> SSD DMA 搬運數據 -> Polling 監測 CQ 完成狀態。
  • 解釋 SPDK 的「三個沒有」：無 Syscall、無 Interrupt、無 Context Switch。
  • 比較傳統 Kernel I/O 與 SPDK Bypass 在 Security、Fairness 與 POSIX 支援上的取捨（Trade-off）。

Pitfall:

極致效能的代價是「責任轉嫁」。使用 SPDK 意味著應用程式必須自行管理資源隔離與安全性，且無法與其他一般 Process 公平共享該 SSD 資源。

user-space driver

將硬體驅動程式從核心空間（Kernel-space）搬到用戶空間（User-space）。應用程式不再透過系統呼叫（Syscall）請求 Kernel 存取硬體，而是直接操作硬體寄存器。

  • DMA & Hugepages: 透過 UIO (Userspace I/O) 或 VFIO 框架，應用程式能直接存取硬體的 MMIO 空間。使用 Hugepages 確保記憶體在物理上是連續的，方便硬體透過 DMA 直接搬運數據，且減少 TLB Miss。
  • Zero-copy: 數據直接從硬體傳輸到應用程式的 Buffer，無需在 Kernel Buffer 與 User Buffer 之間進行二次拷貝。

Pitfall:

  • 安全性降低: Kernel 失去了對硬體的保護與監控，若應用程式崩潰，可能導致硬體狀態異常。
  • 開發難度: 必須自行實作原本 Kernel 處理的錯誤恢復（Error Recovery）與資源回收

Reference:

Polling mode

捨棄中斷機制（Interrupt-driven），讓 CPU 核心不斷地檢查（Poll）硬體的完成佇列（Completion Queue），確認任務是否完成。

  • 消除 Context Switch: 傳統中斷會強迫 CPU 暫停當前工作並切換到中斷處理程序；Polling 讓 CPU 始終處於工作狀態，省去切換開銷。
  • 確定性延遲: 減少了處理中斷的抖動（Jitter），讓 I/O 延遲極度穩定。

Pitfall:

  • CPU 佔用率 100%: 即使沒有 I/O，負責 Polling 的核心也會顯示滿載，造成電力浪費。
  • 飢餓問題: 如果 Polling Thread 權限過高，可能會導致同核心的其他 Task 無法執行。

Reference:

thread-to-queue affinity

每個 CPU 執行緒擁有自己專屬的硬體 I/O 佇列對（Queue Pair, SQ/CQ），並固定綁定處理。

  • 並行化: NVMe 硬體支援多佇列（Multi-queue），這項技術讓多核心能真正並行發送指令，而不會在硬體入口發生擠碰。
  • Cache Locality: 數據處理始終在同一個核心上完成，極大化 L1/L2 Cache 的命中率。

Pitfall:

負載不均: 若特定佇列負載過重而其他空閒，系統無法自動平衡（需在應用層手動設計 Load Balancing）。

Reference:

DPDK

一組由 Intel 發起的函式庫，最初用於高速網路封包處理，SPDK 借鑑了其記憶體管理與環境抽象層（EAL）。

  • 基礎組件: SPDK 使用 DPDK 的 Hugepage 管理、環形佇列（Ring Buffer）以及 CPU 核心綁定（Lcore）機制。
  • 環境抽象: 讓存儲應用能像網路應用一樣，以極高的吞吐量處理數據報文（Data Plane）。

Pitfall:

  • 環境配置複雜: 需要調整系統 Boot loader（如 Grub）來預留 Hugepages。
  • 硬體限制: 對網卡/存儲設備的型號與驅動支援有較嚴格的要求。

Reference:

Lockless design

一種軟體架構模式，各個執行緒之間互不共享數據，因此不需要使用互斥鎖（Mutex）或原子鎖。

  • 消除 Contention: 在多核心系統中，傳統鎖機制會造成 CPU 核心互相等待（Lock Contention），效能無法隨核心數線性增長。
  • Message Passing: 若執行緒間需通訊，改用非同步訊息傳遞（Async Messaging）而非修改共享變數。

Pitfall:

邏輯複雜化: 開發者必須改變「共用記憶體」的思維，改用 Event-driven 或 Reactor 模式，增加程式碼維護門檻。

Key Concepts
理解 kernel 為 HDD 時代設計的三項優化在 SSD 時代的取捨：I/O scheduling, I/O merging, interrupt vs. polling

Answer

在 HDD 時代，Kernel 為了彌補機械延遲，著重於重排與合併 I/O 以減少磁頭移動；
但在 SSD 時代，隨機存取極快且具備高度並行性，這些複雜的 Scheduling 反而成為 CPU 瓶頸，因此轉向簡單化並改用 Polling 以追求低延遲。

Key Concept

I/O Scheduler (Elevator), I/O Merging (Coalescing), CPU Overhead, Parallelism, Interrupt Latency vs. Polling.

Detail

  • I/O Scheduling/Merging： HDD 時代為了避免磁頭來回跳動（Seek time），Kernel 會像電梯一樣對請求進行排序與合併。但 SSD 沒有機械結構，其內部具備多通道並行處理能力，傳統的 Scheduling 演算法會消耗過多 CPU 資源，現代系統多半改用 none 或 mq-deadline。
  • Interrupt vs. Polling： 過去 I/O 很慢，CPU 發出請求後去切換做別的事，等「中斷」通知是高效的。但 NVMe SSD 完成一次 I/O 可能只需幾微秒，處理中斷與 Context switch 的時間（數微秒）已經跟 I/O 本身差不多，因此改由 CPU 不斷輪詢（Polling）結果，雖然耗電但延遲更低。

理解 SPDK 的完整 I/O 流程：透過 hugepage DMA buffer 與 MMIO doorbell register，在 user space 直接操作 NVMe 的 submission/completion queue，由 polling thread 偵測 completion，全程無 syscall、interrupt 或 context switch

Answer

SPDK 透過將 NVMe 驅動移至 User space，利用 Hugepage 進行零拷貝 DMA，並由專屬線程直接操作硬體暫存器（Doorbell）與輪詢 Queue，達成完全避開核心開銷的極速 I/O。

Key Concept

User-space Driver, Hugepages (Zero-copy), MMIO (Doorbell), Polling Mode Driver (PMD), No Syscall/No Context Switch.

Detail

SPDK (Storage Performance Development Kit) 的核心在於「完全掌控」。它透過 UIO/VFIO 框架將硬體控制權拉到 User space。

  • 提交： 應用程式在 Hugepage 分配緩存（減少 TLB miss），將請求填入 Submission Queue，直接對硬體 MMIO 地址寫入 Doorbell 告知 SSD。
  • 收割： 一個專屬的 Polling Thread 持續檢查 Completion Queue。
    整個過程不進出 Kernel（無 Syscall），不產生硬體中斷（無 Interrupt），更沒有進程切換（No Context Switch），效能幾乎等同硬體極限。

了解 kernel bypass 犧牲的三大類服務：security/isolation、fairness/sharing、POSIX ecosystem

Answer

Kernel Bypass 雖然快，但犧牲了核心提供的安全隔離（Security）、公平資源分配（Fairness）以及成熟的作業系統標準生態（POSIX）。

Key Concept

Isolation, Resource Sharing, POSIX standard, Management Overhead.

Detail

  • Security/Isolation： Kernel 是資源的守門員，Bypass 後硬體通常被單一進程獨佔，難以防止惡意程式或錯誤程式碼破壞硬體或其他進程的資料。
  • Fairness/Sharing： Kernel 內建複雜的調度機制確保各應用公平使用磁碟。在 Bypass 模式下，誰搶到硬體誰就是老大，多應用併發時的資源管理變得極其困難。
  • POSIX Ecosystem： 所有的標準工具（如 ls, cat, grep）與 API（open, read）都無法直接作用在 Bypass 的裝置上，開發者必須針對特定 SDK（如 SPDK）重寫整套應用。

理解 eBPF/XRP 的中間路線

Answer

eBPF/XRP 是在不離開 Kernel 的前提下，允許應用程式將自訂邏輯（如 B+Tree 查找）下推至 Kernel 的驅動層執行，兼顧了安全、標準與效能。

Key Concept

XRP (eXpress Resubmission Path), eBPF In-kernel Execution, Function Offloading, Safety Sandbox.

Detail

Kernel Bypass 太激進，傳統 Kernel 太慢。XRP 提出一種折衷方案：利用 eBPF 這個在 Kernel 內的安全沙箱，讓應用程式把「查找邏輯」寫成 eBPF 程式。
當資料從磁碟讀取完成時，直接在驅動層執行該 eBPF 程式，決定下一個要讀取的地址（如追蹤 B+Tree 指標），而不需要回到 User space。這省下了大量的 User/Kernel 切換，卻保留了檔案系統的安全邊界。

理解 kernel bypass 不只為效能，更為 controllability：application 可控制 data placement、降低 write amplification

Answer

Bypass 讓應用程式能精準控制資料存放位置與寫入時機，藉此優化固態硬碟的「寫入放大」問題並提升存取一致性。

Key Concept

Deterministic Latency, Data Placement, Write Amplification (WAF), Log-structured Storage.

Detail

效能只是其一，更重要的是「可預測性」。Kernel 的快取管理與調度往往是黑盒子。
對於高效能資料庫而言，能直接控制資料在 SSD Flash 上的分佈（Data Placement）可以避免 SSD 內部頻繁的垃圾回收（GC），進而降低寫入放大（Write Amplification）。應用程式可以根據自身的負載特性（如只做 Append-only 寫入）來優化存取，達到比核心通用演算法更高的效率與更穩定的延遲。

能描述 CSAL 雙層架構：高速 SSD 以 log-structured 方式吸收 random write，經 compaction 以 sequential I/O 寫入 QLC SSD

Answer

CSAL 將高效能 SSD（如 Optane/SLC）作為寫入快取，以 Log-structured 方式接收隨機寫入，再透過背景壓縮轉換為大塊順序 I/O 寫入低成本、壽命短的 QLC SSD。

Key Concept

Cloud Storage Acceleration Layer (CSAL), Tiered Storage, Log-structured, QLC SSD, Random-to-Sequential.

Detail

QLC SSD 儲存密度高、價格低，但隨機寫入極慢且容易損壞。CSAL 架構建立了兩層系統：

  • 上層（Performance Layer）： 用高速 SSD 吸收頻繁且破碎的隨機寫入（Random Writes），並以日誌形式（Log-structured）紀錄。
  • 下層（Capacity Layer）： 待數據累積到一定量後，CSAL 在 Host 端進行 Compaction，將其轉化為對 QLC 最友善的「大塊順序寫入」，從而保護 QLC 壽命並大幅提升系統整體的寫入吞吐量。

理解 CSAL 的兩階層 host-side FTL

Answer

CSAL 在主機端管理兩套映射關係：第一階層將邏輯地址映射到快取 SSD，第二階層則在冷數據搬移時將其映射到大容量 QLC。

Key Concept

Host-side Flash Translation Layer (FTL), Indirect Mapping, Cache Management, Background Data Migration.

Detail

傳統 SSD 的 FTL（Flash Translation Layer）位於硬體內部。CSAL 將 FTL 的管理邏輯拉到主機端（Host-side）：

  • 第一階 (L1)： 當數據寫入高速層時，主機維護一個 LBA 到高速 SSD 的 Mapping Table。
  • 第二階 (L2)： 當數據從高速層移到 QLC 層（Eviction/Migration）時，主機更新 Mapping Table 到 QLC 的實體位置。
    這樣做的好處是主機能「全局俯瞰」所有 SSD 的狀態，並根據應用需求（而不是硬體黑盒邏輯）來決定何時搬移數據與清理空間。

    1. 在 SPDK 架構下，IOMMU 無法有效隔離異質 SSD 設備，將導致安全性風險。
    1. 由於 SPDK 能支援多家廠商的 NVMe SSD，異質環境帶來的軟體複雜度不會顯著增加，因此使用 SPDK 不會提高維護成本。
    Answer

    SPDK 雖然能提供極致效能，但在此異質硬體環境下，企業必須自行承擔原本由 Linux Kernel 處理的硬體「抽象化」與「相容性」維護，開發成本將大幅增加。因此，此伺服器不建議使用 SPDK。

    解析:

    Linux Kernel 的 I/O Stack （如 VFS 和 Block Layer） 隱藏了不同廠牌 SSD 的實作差異。一旦 Bypass Kernel，應用程式就必須直接面對 10 種不同特性的 SSD，對於企業來說，維護成本往往會抵消 SPDK 帶來的效能收益。權衡之下，在這種多廠商混合的異質環境中，使用 SPDK 的綜合價值可能有限。

    (2) io_uring 雖然能改善 Linux 的 I/O 效能，但它的原理是透過非同步的 SQ/CQ 來減少 System call 開銷，而非自動解決異質硬體的相容性。事實上，io_uring 仍運行在 Kernel 之中，完全依賴原有的 VFS 和 Block Layer 來提供硬體抽象化。相較之下，SPDK 才是真正繞過 Kernel，需要在 User space 處理硬體差異的方案。因此，儘管 io_uring 無法在效能上與 SPDK 相提並論，但對於許多實際場景而言，它仍然是一種更平衡的選擇。

    (3) 只要處理器和主機板支援 IOMMU，SPDK 就能確保異質 SSD 之間的安全隔離，這與廠牌種類無關。IOMMU 是硬體層級的 DMA 隔離技術，與 SPDK 和諧共處。

    (4) 雖然 SPDK 可以技術上支援眾多廠商的 NVMe SSD，但異質環境仍然會大幅增加軟體複雜度和維護工作量。各種不同型號 SSD 在細節上的實作差異，使得相容性調校和持續維運的難度遠高於單一廠商環境。若輕忽這方面的開銷，很可能會抵銷 SPDK 的效能優勢。

    解析:

    完全正確。CSAL 中有兩層 GC 概念，分別為 1. write shaping 的循序大檔寫入能避免 QLC 裝置端硬體內部的 GC；2. 同 VM 短壽命資料分群在一起，則是為了當 Host 端軟體層的 FTL 需要做 GC 時，該區段多數資料已經 invalid，可以直接整塊回收，從而降低 host-side FTL 層的 WAF。

    (1) CSAL 的 Upstream 採用 log-structured storage，compaction 是在背景非同步進行，除非 buffer 達到 hard limit，否則不會直接封鎖前端寫入路徑。 此外，對 CPU 沒影響是錯誤的推論：雖然 polling 本來就佔用 100% core，但 compaction 相關的 I/O 處理會消耗 polling thread 實際的處理週期 (cycles)，會與同一 thread 下服務的其他 I/O 產生排擠效應。

    (3) 選項有兩個明顯錯誤。第一，新寫入或 compaction 中更新的 L2P 通常會駐留在 DRAM cache 中（被標記為 dirty），並非後續的讀取就必然發生 cache miss。 第二，SPDK 異步非阻塞的設計，正是要讓系統在等待某個 I/O 的 metadata 載入時，CPU 能夠繼續推進處理其他 I/O，這確保了整體的總吞吐量 (throughput) 能維持飽和，不會因為單一 IO 延遲而成為吞吐量瓶頸。

    (4) SPDK 的 shared-nothing 是以 CPU core 為單位，一個 polling thread 往往負責輪詢多個 SSD 的 queue pairs，因此它們極可能在同一個執行緒下被處理。 即便刻意隔開執行緒，compaction 的資料依然需要從 Upstream SSD 讀出，勢必佔用 Upstream 的 I/O 頻寬，不管在軟體還是硬體層面上，都不可能完全隔離且影響為零。

  1. 你正在設計一個基於 CSAL 的儲存系統， 目標是透過暫存層將上層應用產生的 random write 重新組織為對 QLC SSD 較友善的 sequential write。

    若要選擇作為 CSAL 暫存層的 SSD，其應優先具備哪一種特質？

    1. 高 read IOPS 與低 read latency
    1. 提供大容量 SSD（例如數 TB）以容納更多暫存資料
    1. 採用高 over-provisioning 與多通道 NAND 設計，支援低延遲、高 IOPS small random write 並具高耐久度
    1. 專為 large sequential write 最佳化，追求高吞吐量
    Answer

    採用高 over-provisioning 與多通道 NAND 設計，支援低延遲、高 IOPS small random write 並具高耐久度

    解析:

    暫存層的任務是即時吸收 small random write 並重組成 sequential write，因此 SSD 需要在 small I/O 下提供低延遲和高 IOPS， 並具備足夠耐久度支撐長時間高頻寫入。高 over-provisioning 可降低 GC 阻塞，多通道 NAND 增加並行度提高 IOPS，高耐久度則支撐長期負載。

    (1) 暫存層主要處理 write，讀取效能對這類負載幫助有限，無法解決 write path 的瓶頸。

    (2) 大容量可以存放更多資料，但對暫存層吸收 small random write 的效能幫助有限，無法改善延遲或 IOPS，不是首要考量。

    (4) 暫存層瓶頸在於吸收 random write，而不是 flush 時的 sequential write 吞吐量。若 random write 延遲高或 IOPS 低，仍會造成暫存層阻塞。

  1. 某資料庫團隊考慮將 storage layer 從 io_uring_cmd 改為 SPDK，以進一步降低 latency。 下列哪個敘述最能描述兩者本質差異？
    1. io_uring_cmd 比 SPDK 更接近硬體，因為使用 NVMe passthrough
    1. SPDK 與 io_uring_cmd 都完全繞過 kernel，差別為 API 不同
    1. SPDK 透過 polling 與 user-space driver 完全消除 syscall 與 interrupt
    1. SPDK 與 io_uring_cmd 均可避免資料複製（memcpy），因此 latency 差異主要來自 queue depth 與 batching 能力
    Answer

    SPDK 透過 polling 與 user-space driver 完全消除 syscall 與 interrupt

    解析:

    正確。SPDK 直接控制 NVMe queue， 透過 polling thread 避免 syscall、interrupt 與 context switch。

    (1) passthrough 實際仍經 kernel driver，SPDK 才是真正直接控制裝置。

    (2) io_uring_cmd 仍依賴 kernel driver， SPDK 則完全在 user space 操作裝置。

    (4) 錯誤，兩者皆可支援高 queue depth 與 batching，亦可能避免 memcpy，但主要差異在於 control path。 io_uring_cmd 仍經 kernel，而 SPDK 完全繞過 kernel，因此效能差異不在 batching。
