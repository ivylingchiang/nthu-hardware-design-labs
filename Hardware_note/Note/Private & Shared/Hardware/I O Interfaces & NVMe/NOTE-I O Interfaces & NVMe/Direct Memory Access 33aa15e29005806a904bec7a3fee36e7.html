Direct Memory Access

你正在看一部 4K 影片（串流大約 25 Mbps），同時在背景編譯大 code，瀏覽器還開了十幾個分頁。影片每秒鐘需要把大量的畫面資料從 SSD 搬到記憶體、再送到 GPU 去解碼 render，累死。如果這些資料都要 CPU 親自一個 byte 一個 byte 搬運，你的 CPU 大概就什麼事都別做了，光搬資料就忙不過來。但實際上你的電腦可以邊播影片邊 compile 邊跑瀏覽器，就是因為有 DMA 在背後幫忙。

沒有 DMA 的世界是什麼樣子？假設你要從 SSD 讀 4KB 的資料到記憶體。CPU 對裝置下一個 read 指令，裝置準備好資料之後，CPU 要親自跑一個迴圈，一次搬幾個 byte，把資料從裝置的 data register 搬到記憶體。這叫 programmed I/O（PIO）。

PIO 的問題很明顯：CPU 在搬資料的時候什麼其他事都不能做。搬 4KB 要幾千次 register read/write 操作。在慢速裝置的年代（例如軟碟），資料量小、速度慢，PIO 還可以接受。但現在一顆 NVMe SSD 的 bandwidth 可以到 7 GB/s，你不可能讓 CPU 用迴圈搬 7 GB 的資料，CPU 的運算能力會被完全浪費掉。

Key Word Definition/ Discussion
DMA

一種硬體機制，允許外圍設備（如磁碟控制器、網卡）直接存取系統記憶體（RAM），而無需 CPU 全程介入搬運資料。

  1. CPU 初始化：告訴 DMA Controller「資料來源/目的地」、「記憶體位址 X」、「長度 N」。
  1. 搬運階段：DMA Controller 接管匯流排，自主完成裝置與記憶體間的資料傳輸。
  1. 完成通知：傳輸結束後，DMA 發出一個 Interrupt 通知 CPU 處理後續邏輯。

Reference:

Physical address

記憶體硬體上的真實物理位址。與 CPU 使用的虛擬位址（Virtual Address）相對。

DMA 對記憶體的三大硬性要求：

  1. Physical Address:

    傳統 DMA Controller 不懂虛擬記憶體，必須給它真實的物理位址。
    CPU 在執行程式的時候用的是 virtual address，經過 page table 轉換才對應到 physical address。但 DMA controller 和裝置通常不認識 virtual address，它們直接看 physical address（或者透過 IOMMU 轉換，但先不管這個）。所以設定 DMA 的時候，driver 必須把 buffer 的 virtual address 轉換成 physical address 告訴裝置。

  1. Physically Contiguous:

    最簡單的 DMA 要求記憶體在物理上必須是連續的。因為它只會從起始點一直往後數 N 個 bytes。
    OS 的 virtual memory 系統會把連續的 virtual address 映射到不連續的 physical page。你 malloc 一塊 64KB 的 buffer，在 virtual space 是連續的，但底層可能散佈在 16 個不相鄰的 physical page。最簡單的 DMA controller 需要一塊 physically contiguous 的記憶體，因為它要從一個起始 physical address 開始，連續搬 N bytes。如果記憶體不連續，DMA controller 搬到一半就會搬到錯誤的位置。

  1. Pinned (Locked):

    DMA 傳輸時，該記憶體分頁絕對不能被 OS 換出（Swap out）或搬移（Migration），否則 DMA 會寫入錯誤的物理位置，造成 Memory Corruption。
    OS 的 virtual memory 系統會把不常用的 memory page swap 到 disk 上。但 DMA 傳輸可能在任何時候發生（裝置準備好就開始搬），如果 DMA 目標的那個 page 剛好被 swap out，裝置就會寫到錯誤的 physical address，直接破壞其他 process 的資料，甚至導致 kernel panic。所以 DMA buffer 必須被 pin 住（也叫 lock），確保在 DMA 進行期間不會被 OS 搬走。

在 Linux kernel 裡，分配 DMA buffer 通常不用 kmalloc（它不保證 physically contiguous 大區塊），而是用專門的 dma_alloc_coherent() 或 dma_pool API，這些 API 會同時處理 physical contiguity、alignment 和 pinning 的問題。

Pitfall: Cache Coherency（快取一致性）問題

當 DMA 直接改寫了記憶體，但 CPU 的 Cache 裡還留著舊資料時，CPU 讀到的會是錯誤的數據。現代系統通常靠硬體（Bus Snooping）或軟體（DMA Cache Flush/Invalidate）來解決。

Scatter-gather list

一種 DMA 技術，允許在單次 I/O 操作中，將資料傳輸到多段「物理上不連續」的記憶體空間。

Scatter-Gather List
前面說最簡單的 DMA 需要 physically contiguous buffer，但在實際系統中，分配大塊 physically contiguous 記憶體既困難又浪費（尤其系統跑久了之後，physical memory 已經碎片化了）。

Scatter-gather list（SGL）解決了這個問題。它讓你在一次 DMA 操作中指定多段不連續的記憶體區間。具體來說，SGL 是一個陣列，每個 entry 包含一個 (physical_address, length) pair。DMA controller 會依序處理每個 entry，把資料搬到（或從）對應的記憶體區段。

舉個例子：你要從 SSD 讀 16KB 的資料，但你的 buffer 散佈在 4 個不連續的 physical page 上。沒有 scatter-gather 的話，你要先分配一塊 16KB 的 contiguous buffer 讓 DMA 搬進去，搬完之後再 memcpy 到你真正要用的 buffer。有了 scatter-gather，你直接建一個 4 個 entry 的 SGL，每個 entry 指向一個 4KB page 的 physical address，DMA controller 自己搞定。省掉了分配 contiguous buffer 和額外 memcpy 的成本。

NVMe 支援 scatter-gather（NVMe 的術語叫 PRP，Physical Region Page，或更新的 SGL），所以 NVMe driver 在設定 I/O command 的時候可以直接把 scatter-gather list 放進 command 裡面。

解決物理記憶體碎片化問題。它透過一個描述符陣列（包含多組 [Address, Length]），讓 DMA Controller 像玩接力賽一樣，自動搬完一段再搬下一段。這避免了為了湊出「大塊連續記憶體」而進行昂貴的 memcpy。

Pitfall: SGL Entry 數量限制

每個硬體（如特定的 NVMe 控制器）能處理的 SGL entry 數量是有上限的。如果你的記憶體太過破碎，超出了硬體支援的 Max SGL segments，驅動程式仍須回退到複製模式或拆分請求。

Zero-copy

消除資料在「核心空間快取 (Kernel Space)」與「使用者空間緩衝 (User Space)」之間不必要複製的技術。

傳統路徑 (Traditional Path)

  • 流程： 裝置 DMA​ Kernel Buffer CPU memcpy​ User Buffer
  • 特性： 經歷 2 次 搬運。
  • 缺點： 需要 CPU 介入執行 memcpy，造成計算資源浪費與額外延遲。

零拷貝 (Zero-copy)

  • 流程： 裝置 DMA​ User Buffer
  • 特性： 僅需 1 次 搬運。
  • 優點： CPU 零參與搬運過程，顯著降低負載。

Zero-Copy I/O

理解了 DMA 和 scatter-gather 之後，你可能會問：既然 DMA 已經把資料搬到記憶體了，為什麼有時候 I/O 還是很慢？因為「搬到記憶體」不代表「搬到你程式的 buffer」。傳統的 I/O 路徑有很多次不必要的資料複製。以 read() system call 為例，典型的流程是：

  • 裝置透過 DMA 把資料搬到 kernel 的 buffer（kernel space）
  • Kernel 再用 memcpy 把資料從 kernel buffer 複製到你的 user space buffer

這個 kernel buffer 到 user buffer 的複製看起來好像沒什麼大不了，但 memcpy 的成本其實不低。複製 4KB 大約需要幾百個 nanoseconds，如果你每秒做幾十萬次 I/O，光是 memcpy 就會吃掉可觀的 CPU 時間和 memory bandwidth。而且同一份資料在記憶體裡佔了兩份空間（kernel buffer 和 user buffer），也浪費 DRAM。

Zero-copy I/O 的核心想法

讓裝置的 DMA 直接搬到應用程式的 buffer，完全跳過 kernel buffer 這一層。資料從裝置出發，經過 DMA 直接到達 user space，不需要任何 CPU 介入的 memcpy。

要做到 zero-copy，application 的 buffer 必須滿足 DMA 的所有要求：physical address 已知、pinned、alignment 正確

在 Linux 上，O_DIRECT flag 就是走這條路，它繞過 kernel 的 page cache，讓裝置直接 DMA 到 application buffer（但 application buffer 必須是 page-aligned 的）。

更極端的做法是 kernel-bypass I/O（像 SPDK），不只省掉 kernel buffer copy，連 kernel 本身都繞過去了。我們後面會專門討論。

這裡要注意一個 trade-off：zero-copy 省掉了複製的成本，但同時也放棄了 kernel 的 page cache。如果你的 workload 有大量重複讀取相同資料的 pattern，page cache 的命中率可能非常高，走 zero-copy 反而更慢，因為每次都要真的去讀裝置。Zero-copy 最適合的場景是大量 sequential I/O 或者資料只讀一次的 workload，在這種情況下 page cache 幫不上忙，省掉 copy 的好處才會真正體現出來。

Pitfall: 失去 Page Cache 的保護。

使用 O_DIRECT 達成 Zero-copy 後，OS 不再幫你快取這份資料。如果你的應用程式沒有自己實作 Buffer Pool，重複讀取同一份資料會導致頻繁的實體磁碟 I/O，效能反而下降。

Bounce buffer

當裝置無法直接存取目標記憶體（例如：舊硬體只能存取 32-bit 位址，但 Buffer 在 64-bit 區域）時，作為中轉站的一塊「保證可達」的記憶體。

當發生「位址不可達」或「對齊不合法」時，核心會分配一塊符合硬體要求的 Bounce Buffer。資料先 DMA 到這裡，再由 CPU 搬到真正的目標。這雖然不是 Zero-copy，但能保證硬體相容性。

Pitfall: 顯著的效能損耗

Bounce Buffer 隱含了額外的 CPU 複製與記憶體分配開銷。在高吞吐系統中，出現大量 Bounce Buffer 通常意味著驅動程式配置錯誤或記憶體對齊（Alignment）不當。

Reference:

IOMMU

位於設備與記憶體之間的硬體單元，功能類似於 CPU 的 MMU，負責將設備發出的「裝置虛擬位址」轉換為「物理位址」。

  • 解決連續性問題: 透過 IOMMU 映射，物理上散亂的分頁可以在裝置眼中看起來是「連續」的。
  • 安全性 (Isolation): 防止惡意或出錯的設備存取它不該存取的記憶體區域（如 Kernel Data）。

Pitfall: TLB Miss Latency

就像 CPU 有 TLB，IOMMU 也有。頻繁的位址轉換可能帶來輕微的延遲增加。

Reference:

Pinned memory

被標記為「不可移動且不可換出」的實體記憶體頁面。

在進行 DMA 或高效能運算（如 GPU 運算）前，必須調用 mlock() 或核心內部的 pin_user_pages()。這是為了防止 OS 在傳輸中途啟動 Page Reclaim 或 Swap，導致 DMA 寫入的物理位置變成別人的資料。

Pitfall: 可用記憶體減少

Pinned Memory 無法被 OS 靈活排程。如果應用程式 Pin 了太多記憶體而不釋放，會導致系統出現Memory Pressure，甚至引發 OOM Killer。

Key Concepts
理解為什麼需要 DMA：當 CPU 親自搬運資料時會佔用運算資源，DMA 讓裝置直接存取記憶體以釋放 CPU 去做其他工作

Answer

傳統 PIO 模式下，CPU 需親自執行讀寫指令搬運資料，耗費大量運算資源。DMA 允許硬體裝置直接與記憶體交換資料，完全釋放 CPU 去執行其他任務。

Key Concept

PIO (Programmed I/O)、CPU Overhead、Hardware Offloading。

Detail

在沒有 DMA 的系統中，資料的每個位元組都必須經過 CPU 的暫存器才能寫入記憶體，這在面對高速儲存裝置（如 NVMe SSD）時，會導致 CPU 100% 滿載於無意義的搬運。導入 DMA (Direct Memory Access) 控制器後，CPU 只需下達傳輸指令（起點、終點、大小），搬運過程全由 DMA 硬體代勞。完成後再透過 Interrupt 通知 CPU，從而實現 I/O 傳輸與 CPU 運算的完美並行。

理解 DMA 對記憶體的要求，知道裝置使用 physical address 定址，因此 DMA buffer 必須是 physically contiguous 且 pinned 在實體記憶體中不被 swap 出去

Answer

傳統 DMA 不具備虛擬位址轉換能力，因此必須提供實體位址（Physical Address）且空間需連續（Contiguous）。此外，該記憶體區塊必須被鎖定（Pinned），防止被 OS 換出。

Key Concept

Physical Address、Physically Contiguous、Pinned (Locked) Memory、Page Swap

Detail

DMA 控制器直接掛載在硬體匯流排上，看不懂作業系統層級的虛擬位址，只能根據真實的實體位址來讀寫。因為 DMA 傳輸是獨立於 CPU 運作的非同步過程，若作業系統的虛擬記憶體管理員（VM Subsystem）在傳輸期間將該實體分頁換出（Swap out）到磁碟，或重新分配給其他程序，DMA 就會無意間覆寫錯誤的實體位置，引發致命的 Memory Corruption。因此，進行 DMA 前必須強制將目標分頁 Pinned 釘在實體記憶體中。

理解 scatter-gather list 的用途，知道它允許一次 DMA 操作描述多段不連續的記憶體區段，避免必須先將資料複製到連續 buffer 的額外開銷

Answer

SGL 是一份記錄多個「實體位址與長度」的清單，允許 DMA 控制器一次性將資料自動分段寫入多個物理上不連續的記憶體區塊，免去 CPU 的複製介入。

Key Concept

Scatter-Gather List (SGL)、Memory Fragmentation、memcpy overhead

Detail

系統長時間運行後，實體記憶體往往會碎片化，極難配置出一大塊連續的空間給 DMA 專用。若硬體不支援 SGL，系統被迫先配置一塊連續的 Bounce Buffer 讓 DMA 寫入，再由 CPU 透過軟體 memcpy 將資料拆分複製到原本不連續的目標分頁。SGL 解決了這個痛點：驅動程式預先將分散的實體位址整理成陣列（List）交給硬體，硬體便能像接力賽一樣，自動將連續的磁碟資料分散填入這些不連續的記憶體碎片中，徹底消除軟體複製的效能折損。

理解 zero-copy I/O 的概念，知道它讓資料直接在裝置與應用程式 buffer 之間傳輸，省去經由 kernel buffer 中轉的複製成本

Answer

Zero-copy 讓硬體裝置透過 DMA 直接與應用程式的緩衝區（User Buffer）交換資料，完全跳過作業系統核心（Kernel Buffer）的中轉與 CPU 的記憶體複製。

Key Concept

Kernel Buffer Bypass、User Space、Context Switch、O_DIRECT。

Detail

傳統檔案讀取（如 read()）會先由 DMA 將資料寫入 OS 的 Page Cache，接著再由 CPU 耗費算力 memcpy 到應用程式層級的 User Buffer，這造成了雙倍的記憶體佔用與額外的 CPU 負擔。Zero-copy I/O（如 Linux 的 O_DIRECT）允許開發者將符合 DMA 嚴格規範的 User Buffer 位址直接交給底層硬體，達成「裝置 → 應用程式」的一步到位傳輸。不過，這種做法也同時放棄了 OS 內建的快取保護，通常只適用於大檔循序掃描或自行管理快取池的高效能資料庫引擎。

Test your understanding
在PIO 模式下，CPU 要親自搬運資料。如果一顆 NVMe SSD 的 bandwidth 是 7 GB/s，用 PIO 搬運所有資料會有什麼問題？DMA 如何解決這個問題？

Answer

CPU 會花費所有時間在執行記憶體的讀寫指令上，導致滿載且無力處理其他任務。DMA 透過專屬硬體直接將資料寫入記憶體，完全解放 CPU。

Key Concept

PIO (Programmed I/O)、CPU Utilization、DMA Controller

Detail

PIO 模式要求 CPU 親自逐字節或逐字組地讀取裝置的暫存器，再寫入主記憶體。對於 7 GB/s 這種海量頻寬，CPU 的時脈與匯流排頻寬會被龐大的資料搬移工作完全吃光（佔用率達 100%）。DMA 控制器改變了這個機制，允許 CPU 只下達「起點、終點、長度」的指令，隨後由 DMA 硬體獨立完成裝置與記憶體間的搬運。期間 CPU 可以去執行其他應用程式，大幅提升系統整體吞吐量。

為什麼 DMA buffer 必須用 physical address 而不是 virtual address？如果裝置使用 virtual address 去做 DMA，會發生什麼事？

Answer

因為傳統 DMA 設備不具備 CPU 內的 MMU（記憶體管理單元），看不懂作業系統建立的虛擬位址。若直接餵給它虛擬位址，它會將其當作實體位址寫入，導致覆寫錯誤的記憶體位置。

Key Concept

Physical Address、Virtual Address、MMU、Memory Corruption

Detail

CPU 存取虛擬位址時，會透過自身的 MMU 與 Page Table 即時轉換成實體位址。但傳統的 DMA 控制器直接掛在系統匯流排上，運作時繞過了 CPU 的 MMU。如果把程式裡的虛擬位址丟給 DMA，它會照著這個數字盲目寫入實體記憶體，極可能覆蓋到系統核心或其他程式的敏感資料，進而引發系統崩潰（Kernel Panic）。

為什麼 DMA buffer 必須被 pin 住不能被 swap out？

Answer

確保 DMA 傳輸期間，目標的實體記憶體分頁不會被作業系統搬移或置換到硬碟，避免硬體把資料寫錯位置。

Key Concept

Pinned Memory、Page Swap、Page Reclaim

Detail

作業系統的虛擬記憶體機制會在實體 RAM 不足時，主動把不常用的頁面換出（Swap out）到硬碟，並把該實體空間分配給其他進程。因為 DMA 傳輸是硬體非同步進行的，如果 DMA 準備寫入的實體分頁突然被 OS 換出並重新分配，DMA 就會把資料無情地寫進另一個無辜程式的記憶體中。因此，在發起 DMA 之前，必須透過核心將該頁面 Pinned（鎖定），確保它在物理上絕對靜止。

沒有 scatter-gather 的時候，如果你的資料分散在 4 個不連續的 physical page，你要怎麼做才能完成 DMA？有了 scatter-gather 之後省掉了什麼？

Answer

沒 SGL 時，作業系統必須先配置一塊連續的實體記憶體（Bounce Buffer），讓 DMA 寫入後，CPU 再用 memcpy 複製到那 4 個分散的 page 中。SGL 省去了額外的連續記憶體配置與 CPU 複製開銷。

Key Concept

Scatter-Gather List (SGL)、Physically Contiguous、memcpy overhead

Detail

傳統 DMA 要求寫入區塊必須「實體連續」。若目標空間分散，OS 必須分配一塊夠大的「連續實體緩衝區」，等 DMA 把資料全搬進來後，CPU 再用軟體迴圈把它們切分並複製到那 4 個不連續的實體分頁。使用 SGL 後，OS 只需給 DMA 控制器一張包含 4 個實體位址與長度的清單，硬體就會像跑接力賽一樣，自動依序把資料精準填入分散的頁面，完全免除 CPU 介入。

Zero-copy I/O 省掉了哪些 overhead？在什麼情況下，zero-copy 反而會比走 kernel page cache 的傳統路徑更慢？

Answer

Zero-copy 省去了資料在 Kernel Space Buffer 與 User Space Buffer 之間的 CPU memcpy 開銷。但如果面臨具有高度時間局部性（反覆讀取相同資料）的工作負載，Zero-copy 會因繞過快取而變慢。

Key Concept

Zero-copy、Page Cache Bypass、Temporal Locality

Detail

在傳統 I/O 中，裝置把資料 DMA 到 Kernel Buffer 後，CPU 還需花時間將其複製到 User Buffer。Zero-copy 讓裝置透過 DMA 直接寫入 User Buffer，省下了 CPU 時間與多餘的記憶體佔用。然而，實作 Zero-copy 通常意味著繞過作業系統的 Page Cache（如使用 O_DIRECT）。如果應用程式反覆讀取同一批「熱資料」，傳統路徑可以直接從記憶體（Page Cache）極速返回，而 Zero-copy 卻強迫每次都要向底層慢速磁碟發起實體 I/O，導致延遲暴增。

  1. 某資料庫工程師為了解決系統 CPU 負載過高的問題，決定將儲存引擎的讀取路徑全面改寫為 零拷貝 I/O（Zero-copy I/O，例如使用 Linux 的 O_DIRECT）。該資料庫的 workload 主要集中在「頻繁反覆讀取同一批熱點索引區塊（Hot index blocks）」。改寫上線後，工程師原本預期能省下大量的 CPU memcpy 開銷並提升效能，但實際測試卻發現資料庫的讀取延遲大幅增加，整體吞吐量嚴重衰退。根據 DMA 與 I/O 軟體堆疊的原理，造成此反直覺現象的最主要原因是什麼？
    1. O_DIRECT 會強制 DMA 控制器退化成 Programmed I/O（PIO）模式。在 PIO 模式下，CPU 必須親自參與每一個位元組的搬運，這不僅沒有省下 CPU 資源，反而導致 CPU 被 I/O 傳輸完全卡死。
    1. 應用程式透過標準 malloc() 分配的 User buffer 預設在實體記憶體中是不連續的（Physically fragmented）。由於 Zero-copy 必須使用實體連續的記憶體，DMA 控制器為了處理這些碎片，耗費了大量時間在硬體層級進行重組。
    1. 零拷貝 I/O 會導致目標記憶體區塊被永久 Pinned（釘住）在實體記憶體中無法被作業系統 Swap out。當熱點索引區塊不斷增加時，會迅速耗盡所有的實體記憶體，引發系統嚴重崩潰。
    1. 零拷貝 I/O 雖然省下了將資料從 Kernel buffer 複製到 User buffer 的 CPU 開銷，但也同時完全繞過了作業系統的 Page cache（分頁快取）。對於頻繁反覆讀取熱資料的負載，原本可以直接從記憶體快取中極速命中的請求，現在全部被迫轉換成對底層 NVMe SSD 的實體 I/O 讀取，導致延遲大幅增加。
    Answer

    零拷貝 I/O 雖然省下了將資料從 Kernel buffer 複製到 User buffer 的 CPU 開銷，但也同時完全繞過了作業系統的 Page cache（分頁快取）。對於頻繁反覆讀取熱資料的負載，原本可以直接從記憶體快取中極速命中的請求，現在全部被迫轉換成對底層 NVMe SSD 的實體 I/O 讀取，導致延遲大幅增加。

    解析:

    這是正確的。根據講義，Zero-copy 的核心代價就是放棄了 Kernel 的 Page cache。在資料庫頻繁讀取「熱點資料」的場景中，Page cache 的命中率通常極高，直接從 DRAM 讀取的延遲遠低於向 SSD 發送 DMA 請求。強行套用 Zero-copy 反而會讓每個讀取指令都必須走完完整的 PCIe 與 NVMe 實體傳輸路徑，導致效能嚴重衰退。Zero-copy 真正適合的是「只讀一次」或「循序大檔案」等 Cache 命中率低的場景。

    (1) 這是錯誤的觀念。使用 O_DIRECT 達成 Zero-copy 時，底層依然是完全依賴硬體 DMA 控制器來將資料從 SSD 直接搬運到應用程式的 User buffer 中，並不會退化成古老且低效的 PIO（由 CPU 親自跑迴圈搬資料）模式。

    (2) 這混淆了 DMA 的限制與現代解法。雖然簡單的 DMA 確實需要實體連續記憶體，但現代系統與 NVMe 協定廣泛支援 Scatter-Gather List（SGL） 或是 PRP 機制。這允許 DMA 控制器直接且高效地處理分散在多個實體分頁上的記憶體，並不會因此產生巨大的重組延遲。

    (3) 這個推論只對了一半。DMA 傳輸期間，記憶體確實必須被 Pinned 以防止 OS 將其 Swap 出去造成資料損壞。然而，Pinning 是動態的，通常只在 I/O 操作進行的期間鎖定，完成後就會釋放（或者由資料庫自行管理特定的固定緩衝池），並不會因為使用了 Zero-copy 就無條件「永久」鎖住所有記憶體導致系統立刻崩潰。效能立刻衰退的主因是失去了 Cache。

  1. 某資料分析系統將 I/O 路徑從 read()（使用 OS page cache）改為 direct I/O（例如使用 O_DIRECT，繞過 OS page cache）。 系統在以下兩種 workload 上進行測試：
    • Workload A： 連續掃描大型資料集，每筆資料只讀取一次
    • Workload B： 反覆讀取一個大小為 2× DRAM 的資料集，且存取具有 temporal locality，其 working set 明顯小於可用 DRAM，因此 page cache hit rate 很高

    實驗結果顯示，workload A 效能提升，但 workload B 效能顯著下降。 假設儲存裝置為 NVMe SSD，且 I/O queue depth 足夠高，請選出最合理的解釋：

    1. 在 workload B 中，direct I/O 無法利用 OS page cache 的 readahead 機制，導致 sequential throughput 下降
    1. 在 workload B 中，由於資料集大於 DRAM，page cache 無法有效運作，因此 direct I/O 與 read() 應具有相同效能
    1. 在 workload B 中，direct I/O 會限制 I/O queue depth，導致無法充分利用 NVMe 的內部平行性
    1. 在 workload B 中，read() 可利用 page cache 保留近期使用的 hot data，而 direct I/O 每次都需從 SSD 重新讀取，導致效能下降
    Answer

    在 workload B 中，read() 可利用 page cache 保留近期使用的 hot data，而 direct I/O 每次都需從 SSD 重新讀取，導致效能下降

    解析:

    read() 透過 page cache 保留最近使用的資料，使得具有 temporal locality 的存取可以直接命中 DRAM。 direct I/O（O_DIRECT）繞過 page cache，使每次讀取都需從 SSD 載入資料，無法利用 locality，導致效能下降。

    (1) 雖然 direct I/O 繞過 page cache，因此也不會使用 OS 的 readahead，但題目中的 workload B 重點是 temporal locality，而非 sequential throughput。 即使沒有 readahead，主要效能差異仍來自 cache reuse，而不是 prefetch。

    (2) 題目已明確指出 working set 明顯小於 DRAM，因此 page cache 可以保留大部分 hot data，並達到很高的 hit rate。 即使整體資料集大於 DRAM，只要存取具有 temporal locality，page cache 仍然能有效降低 I/O 次數。

    (3) I/O queue depth 通常由應用程式與 driver 控制，而不是 direct I/O 的直接限制因素。 在題目假設 queue depth 足夠高的情況下，NVMe 平行性並不是瓶頸。

    請問以下哪一個敘述是正確的？
    1. 只要使用 scatter-gather list，DMA controller 就可以在傳輸過程中根據 page table 重新解析 virtual address，因此不需要 pin pages。
    1. pin pages 的主要作用是確保 scatter-gather list 中記錄的 physical address 在 DMA 期間保持有效，即使 virtual address 不變，未 pin 仍可能導致 DMA 寫入錯誤位置。
    1. 如果改成先 DMA 到一塊 kernel 中的 contiguous buffer，再 memcpy 到 user buffer，則為了確保 memcpy 正確，user buffer 仍需要在整個 DMA 過程中被 pin。
    1. 因為使用 O_DIRECT 繞過 page cache，kernel 不會再對這些 pages 進行 migration 或 compaction，因此 pin 並非必要。
    Answer

    pin pages 的主要作用是確保 scatter-gather list 中記錄的 physical address 在 DMA 期間保持有效，即使 virtual address 不變，未 pin 仍可能導致 DMA 寫入錯誤位置。

    解析:

    DMA controller（在沒有 IOMMU 的情況下）完全依賴 driver 提供的 physical address， 並不會查詢 page table。scatter-gather list 中記錄的是一組固定的 physical address。 若沒有 pin，kernel 可能進行 page migration 或 swap，導致這些 physical pages 改變或被回收。 即使 user space 的 virtual address 完全沒有變，DMA 仍會寫入舊的 physical address， 造成資料毀損。

    (1) 這個選項混淆了 scatter-gather 與 virtual memory。SGL 中存的是 physical address， DMA controller 並不會在傳輸時查詢 page table 或重新做 virtual-to-physical 轉換。 scatter-gather 只是讓 DMA 可以處理多段不連續的 physical memory，並不提供任何動態位址轉換能力。 因此如果 physical page 被移動，SGL 仍會失效。

    (3) 在這種設計下，DMA 的目標是 kernel buffer，而不是 user buffer。需要穩定的是 kernel 的 DMA buffer（其 physical address）， 而不是 user buffer。memcpy 是 CPU 經由 virtual address 存取 user memory，會透過 MMU 做正確轉換， 不依賴固定的 physical address，因此 user buffer 不需要因為 DMA 而被 pin。

    (4) O_DIRECT 只代表 I/O 不經過 page cache，並不代表 kernel 不會對這些 pages 做 memory management。 user pages 仍然屬於一般的 virtual memory 管理範疇，可能被 migration、swap（若未 pin）或 compaction 影響。 因此 O_DIRECT 並不能取代 pinning 的需求。

    Answer

    DMA controller 會將該 virtual address 誤認為 physical address 並直接寫入，導致覆寫到系統其他不可預知的 physical memory 區域，造成資料毀損或系統崩潰。

    解析:

    應用程式拿到的指標是 virtual address，在 physical memory 中極可能是破碎且不連續的。 傳統 DMA controller 看不懂 virtual address，也沒有 CPU 的 MMU 可以幫忙翻譯。 它會把收到的數字當成 physical address 直接覆寫，這會摧毀作業系統或其他程式的資料。

    (1) controller 不會因為收到錯誤的位址格式就改變其中斷行為模式。它只會忠實地對指定的錯誤位置執行連續的記憶體寫入。

    (2) malloc() 分配的是 virtual memory，分配 1 MB 虛擬連續空間非常容易。問題不在於分配失敗，而在於開發者將 virtual address 錯誤地餵給了只懂 physical address 的硬體。

    (4) page fault 是由 CPU 的 MMU 觸發的。在這個情境中，是 DMA controller 繞過了 CPU 直接對 RAM 進行讀寫， CPU 根本不知道硬體正在寫入錯誤的實體位置，因此不會觸發 page fault 來保護應用程式。

  1. 某學生主張： 「 DMA 是 interrupt 的進階版本，兩者只是減少 CPU 負擔的程度不同。」 以下哪個回應最精準？
    1. 兩者皆用於減少 CPU 與裝置之間的資料傳輸時間，但沒有前後版本的關係
    1. DMA 仍需透過 CPU 執行 load/store 指令來完成資料搬移，不算一種進階
    1. 沒錯， interrupt 主要讓裝置與 CPU 間的資料同步， DMA 用於提升同步效率
    1. DMA 是資料傳輸方式，interrupt 是通知機制，兩者沒有前後版本的關係
    Answer

    DMA 是資料傳輸方式，interrupt 是通知機制，兩者沒有前後版本的關係

    解析:

    DMA 是允許資料在外部設備與記憶體之間直接傳輸、不需要通過 CPU 的方法； interrupt 則是通知 CPU 的方法。

    (1) DMA 是一種讓裝置不經過 CPU 直接對記憶體進行讀寫的傳輸機制， 不需 CPU 逐筆執行 load/store 指令，因此減少的是 CPU 的負擔與介入程度； interrupt 則是一種通知機制，它的目的在於避免 CPU 持續 polling， 而不是用來加速資料傳輸

    (2) DMA 的重點就在於可以不需要透過 CPU load/store 搬資料， 而 CPU 在這個機制當中只負責設定、不參與實際傳輸

    (3) interrupt 主要用於通知 CPU 裝置狀態，而非資料同步； 而 DMA 的目的是資料搬移

  1. 為何在缺乏 IOMMU 或 DMA access control 時，DMA 可能帶來安全風險，例如：DMA 遊戲外掛？
    1. 因為 DMA 一定需要 physically contiguous memory，只要 memory 碎片化就會直接造成資安漏洞。
    1. 因為 DMA 一定會繞過 CPU 的所有控制邏輯，所以 CPU 完全無法得知任何 DMA 行為。
    1. 因為 DMA 只能使用 virtual address，導致位址映射混亂，才會產生安全問題。
    1. 因為 DMA device 可直接對 memory 做讀寫；若缺乏 isolation 與 permission control，可能讀到或覆寫不該存取的 memory 區域。
    Answer

    因為 DMA device 可直接對 memory 做讀寫；若缺乏 isolation 與 permission control，可能讀到或覆寫不該存取的 memory 區域。

    解析:

    這是核心原因。DMA 直接對 memory 搬運資料，若沒有 IOMMU 或適當的 DMA access control，device 可能越權存取敏感 memory，造成資料外洩、資料毀損， 甚至 system stability 問題。

    (1) memory 是否連續屬於可用性與效能問題，且可透過 scatter-gather 緩解；這不是 DMA 安全風險的根本原因。根本仍是是否有正確的 access isolation 與 permission control。

    (2) DMA 不是完全脫離 CPU。CPU/driver 仍會參與 setup 與 completion handling。 風險重點在於 memory access isolation 不足，而不是 CPU 完全看不到 DMA。

    (3) DMA 常見使用的是 physical address（或經 IOMMU 轉換後的 address），不是只能用 virtual address。安全風險來源是存取範圍控制不足，不是位址型別本身。
