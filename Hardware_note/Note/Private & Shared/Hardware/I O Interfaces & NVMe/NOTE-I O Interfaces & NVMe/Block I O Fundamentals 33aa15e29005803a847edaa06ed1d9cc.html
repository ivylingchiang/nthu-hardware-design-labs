Block I/O Fundamentals

每次你按下 Ctrl+S 存檔、打開一個 app、或是載入遊戲的關卡，背後都有一連串的 I/O 操作在你看不到的地方發生。你的程式發出讀寫請求，作業系統把它轉成 block device 的操作，再交給底層硬體執行。同樣一個遊戲，在一台電腦上 2 秒就載入完成，在另一台卻要 30 秒，差異不只是「硬體比較快」這麼簡單，而是整條 I/O 路徑的效率問題。要理解這些差異，我們得先從最底層的抽象開始。

Key Word Definition/ Discussion
Block device

Block device 是一種儲存裝置介面，資料以「固定大小的 block」為單位進行讀寫（例如 512B / 4KB），並透過 block address（LBA）來存取。

Block Device Abstraction

作業系統把所有儲存裝置（不管是 HDD、SSD、還是 NVMe）都抽象成一個「由固定大小 block 排成的陣列」。每個 block 通常是 512 bytes 或 4KB。你不需要去想「我要把資料寫到 SSD 裡面第 3 顆 NAND chip 的第 17 個 block 的第 42 個 page」，你只需要指定 block 編號，告訴 OS 你要讀或寫，剩下的事情由 device driver 和裝置本身去處理。

這個 abstraction layer 是所有儲存系統的共同基礎。不管你後面學的是 file system、database、還是 key-value store，它們最底層都是在對 block device 發出 read 和 write 請求。搞清楚這層抽象的性質和限制，後面的東西會順很多。

IOPS vs Bandwidth

衡量儲存系統效能的兩大基礎指標，分別對應不同特性的 Workload。

IOPS（I/O Operations Per Second）衡量的是「每秒能完成幾次 I/O 操作」。主要反映儲存裝置處理高頻率、小檔案的併發能力。

Bandwidth（也叫 throughput）衡量的是「每秒能傳多少資料量」，單位通常是 MB/s 或 GB/s。主要反映連續讀寫大檔案的能力。

  • Random Small I/O (瓶頸在 IOPS)：

    例如遊戲載入關卡時，需要讀取大量幾 KB 的材質、模型與著色器檔案，或資料庫進行大量隨機 Point Lookup。
    假設一顆 NVMe SSD 的 Random 4KB Read 可達 500K IOPS，每次讀 4KB，實際頻寬只用到約 2 GB/s（500K × 4KB），遠未達到硬體頻寬上限，但 IOPS 已經飽和。

  • Sequential Large I/O (瓶頸在 Bandwidth)：

    例如將一部 10GB 的影片複製到另一個資料夾，或影片串流應用的連續讀取。
    假設每次讀取 256KB 的大 Block，在達到硬體 3.5 GB/s 的 Bandwidth 上限時，IOPS 需求僅約 14K（3.5 GB/s ÷ 256KB），此時瓶頸完全在資料吞吐量。

因此，評估儲存效能的第一個問題永遠是：「Workload 屬於 Random Small I/O 還是 Sequential Large I/O？」釐清這點才能決定正確的優化方向。

Throughput

系統在單位時間內「實際成功處理並傳遞的資料量」。

雖然 Throughput（吞吐量）常與 Bandwidth（頻寬）混用，但兩者在嚴謹的系統設計中有著微妙差異。Bandwidth 偏向描述「理論最大傳輸上限」（水管的物理粗細），而 Throughput 是描述「實際達到的有效傳輸率」（實際流出的水量）。

在儲存系統中，Throughput 的高低會受到 I/O 大小、佇列深度 (Queue Depth)、處理器負載以及檔案系統的軟體開銷等因素綜合影響。

Pitfall: 忽略 Protocol & Software Overhead

應用程式層級測量到的 Throughput 通常會低於硬體規格書上標示的 Bandwidth上限。這是因為資料從應用層穿越 File System、OS Kernel (VFS)、Device Driver 到最終的 PCIe/NVMe 匯流排，每一層都會加上 Header 或是產生額外的 Context Switch 與處理延遲。在計算效能瓶頸時，不能單看硬體規格，必須扣除這些 Overhead（即所謂的 Goodput）。

Latency

延遲。從應用程式發出一個 I/O 請求，到收到「處理完成」通知所需的時間。

單位通常為毫秒 (ms) 或微秒 (μs)。對現代儲存系統而言，Latency 是一段累積的時間，包含：

  1. Software Latency: OS System Call 轉換、File System 處理、Block Layer 排隊的時間。
  1. Hardware Interface Latency: 指令在 PCIe/NVMe 匯流排上傳輸的時間。
  1. Media Latency: 裝置內部 Controller 處理邏輯（如 FTL Address Translation）與實際對 NAND Flash 進行物理讀寫的時間。

從 HDD (約 10ms) 演進到 SATA SSD (約 100μs)，再到高階 NVMe SSD (可低於 20μs)，Latency 的數量級壓縮極大改變了軟體設計的假設。

Pitfall: 只看平均延遲 (Average Latency)，忽視長尾延遲 (Tail Latency)。

在大型分散式系統或資料庫中，看 P99 或 P99.9 Latency（最慢的 1% 或 0.1% 的請求耗時）比看平均值更具指標性。即使 SSD 的平均延遲極低，但若偶爾因為裝置內部的 Garbage Collection 或 Wear Leveling 觸發而導致個別 I/O 卡頓數十毫秒（Latency Spike），就會嚴重拖垮整體系統的回應時間。

Synchronous I/O vs Asynchronous I/O

應用程式發出 I/O 請求（如 read() System Call）時，執行緒 (Thread) 等待資料返回的行為模式。

Synchronous I/O：

呼叫 read() 之後，你的 thread 就被 block 住了，一直等到資料從裝置搬到記憶體、kernel 把結果複製到你的 user space buffer 之後才會返回。在等待的這段時間，這個 thread 什麼事都不能做。如果你要同時發 100 個 I/O 請求，你就需要 100 個 thread，每個 thread block 在自己的 read() 上。

Asynchronous I/O：

你提交一個 I/O 請求之後，呼叫立刻返回。你的 thread 可以繼續做其他事情，甚至繼續提交更多 I/O 請求。等 I/O 完成之後，你再透過某種機制（例如 polling、callback、或檢查 completion queue）拿到結果。

設計抉擇的演進：

想像一個高併發的 Web Server，同時處理上千個請求。
在 HDD 時代，一次 Random I/O 耗時約 10ms，Synchronous I/O 的阻塞尚可接受，CPU 大多在閒置等待。
但在 NVMe 時代，一次 Random Read 降至 100μs 左右，而一次 Thread Context Switch 的成本約為 1-5μs。
若繼續使用 Synchronous I/O 搭配大量 Thread，頻繁的 Context Switch 與 Thread Scheduling 開銷將會吃掉極大比例的 CPU 資源。

這正是為何現代高效能儲存框架（如 Linux 的 io_uring）皆全面轉向 Asynchronous I/O 架構的原因。

Interrupt vs Polling

I/O 完成後，硬體裝置通知 CPU「資料已就緒」的兩種底層機制。

Interrupt（中斷）：

裝置完成 I/O 之後，主動送一個 hardware interrupt 給 CPU。CPU 收到 interrupt 之後暫停手上的工作，跳去執行 interrupt handler 來處理完成的 I/O。這是裝置主動通知 CPU 的方式。

  • 優點： CPU 在等待期間不浪費資源，可執行其他任務。
  • 缺點： 每次 Interrupt 切換的耗時約需數微秒。當裝置極快（如 NVMe）、I/O 密度極高時，每秒可能產生數十萬次中斷，CPU 處理中斷的 Overhead 將成為嚴重負擔，引發所謂的 Interrupt Storm。

Polling（輪詢）：

CPU 不等裝置通知，而是自己不斷去檢查「I/O 好了沒？好了沒？賀啊沒啦？賀啊沒啦？」。具體來說就是反覆讀取裝置的某個 status register 或 completion queue，直到發現有新的完成結果。

  • 優點： 省去了中斷觸發與 Context Switch 的巨大開銷，I/O 一完成即可在下一次迴圈被立刻捕捉，具備極低的 Latency。
  • 缺點： CPU 在等待期間處於 Busy-Waiting（空轉），會持續消耗運算資源與電力。

當 I/O Latency 降至微秒等級且吞吐量極大時，Polling 反而比 Interrupt 更具效能優勢。現代的高效能驅動（如 Linux 核心的 Hybrid Polling 或 SPDK）會根據負載動態切換：在 I/O 密集時使用 Polling 極大化效能，在系統閒置時退回 Interrupt 以節省 CPU。

Key Concept

Abstraction (抽象化)、LBA (Logical Block Address)、硬體物理特性

Detail

儲存裝置的物理結構差異極大，HDD 透過磁柱與磁區運作，而 SSD 則由 NAND Flash 的 Page 與 Block 組成。如果直接暴露物理結構，每個軟體都必須為每種硬體撰寫特定的驅動邏輯。透過 Block Device Abstraction，作業系統提供 LBA，讓上層（如檔案系統）統一看待所有裝置。此外，多數儲存硬體在物理上無法做到 byte-level 的寫入（例如 SSD 寫入最小單位是 Page，通常為 4KB），以 Block 為單位進行 I/O 能最大化資料傳輸與匯流排的效率。

理解 IOPS 與 bandwidth 這兩個效能指標的差異，以及不同工作負載（random small I/O vs. sequential large I/O）分別會受限於哪一個指標

Answer

IOPS 衡量每秒操作次數（處理能力的密度），Bandwidth 衡量每秒傳輸資料量（資料流的寬度）。隨機小檔看 IOPS，順序大檔看 Bandwidth。

Key Concept

Random Small I/O、Sequential Large I/O、Throughput、Bottleneck

Detail

  • Random Small I/O (IOPS 密集型)：如資料庫 Point Lookup 或作業系統啟動。因為請求分散在不同位置，裝置處理請求的 Overhead（尋址、指令轉換）成為主導，通常會先撞到 IOPS 上限，此時 Bandwidth 往往還遠低於硬體標稱值。
  • Sequential Large I/O (Bandwidth 密集型)：如影片拷貝、大數據備份。資料連續排列，裝置可以一次搬運大量 Block，此時 IOPS 負擔極輕，瓶頸在於實體匯流排（PCIe/SATA）的傳輸極限。
    評估系統效能時，必須根據 Workload 的性質（IO Size 與存取分佈）來判斷該關注哪一個指標。

理解 synchronous I/O 與 asynchronous I/O 的差異，知道 synchronous I/O 會阻塞呼叫端直到完成，而 asynchronous I/O 允許提交後繼續執行其他工作

Answer

Synchronous I/O 是「發出請求後原地等待（Blocked）」，Asynchronous I/O 是「發出請求後立刻返回執行其他任務，稍後再收割結果」。

Key Concept

Blocking/Non-blocking、Thread Utilization、Context Switch、io_uring

Detail

  • Synchronous I/O：程式流程簡單，但效率低。Thread 被掛起後會進入 Blocked 狀態，不再佔用 CPU，但也無法處理其他邏輯。在高併發環境下，這會導致需要開啟大量 Thread，引發頻繁的 Context Switch。
  • Asynchronous I/O：程式邏輯較複雜（通常需要 Callback 或 Completion Queue），但效能上限極高。單一 Thread 可以同時「發出」成千上萬個 I/O 請求而不用等待。在微秒級延遲的現代 NVMe SSD 環境中，Asynchronous 模式能極大化系統吞吐量並維持極低的 CPU 指令開銷。

理解 interrupt 與 polling 這兩種 I/O completion notification 機制的運作方式與適用場景，知道 interrupt 由裝置主動通知 CPU，而 polling 由 CPU 主動檢查完成狀態

Answer

Interrupt 是裝置「主動」插斷 CPU 告知完成，節省 CPU 但有切換開銷；Polling 是 CPU「主動」循環檢查狀態，消耗 CPU 但 Latency 極低且無切換成本。

Key Concept

Interrupt Storm、Busy-waiting、Latency vs Efficiency、Hybrid Polling

Detail

  • Interrupt：適合「慢速裝置」或「低密度 I/O」。CPU 不用浪費時間等硬體，可以去做別的事。但高頻中斷會引發 Interrupt Storm，讓 CPU 陷入無窮的中斷處理，導致效能雪崩。
  • Polling：適合「超快速裝置（如 NVMe）」或「高密度 I/O」。雖然 CPU 會空轉（Busy-waiting），但在高負載下，省去的「儲存/恢復暫存器（Context Switch）」時間反而更划算。現代 Linux 核心常採用 Adaptive Polling (Hybrid)，即負載低時用中斷，負載高時自動切換為輪詢。

一顆 SSD 標示 random 4KB read IOPS 是 500K，sequential read bandwidth 是 3.5 GB/s。如果你的 workload 是 random 4KB read，你的實際 bandwidth 上限是多少？

Answer

實際 Bandwidth 上限為 2 GB/s

Key Concept

IOPS Bottleneck、Random Small I/O

Detail

儲存效能會受限於 IOPS 與 Bandwidth 兩者中「先到達」的瓶頸。在此 Workload 下，每次讀取大小為 4KB，當控制器的指令處理能力達到 500K IOPS 極限時，總資料傳輸量為：500,000 * 4KB = 2,000,000 KB/s，換算約為 2 GB/s。這表示系統已經因為「隨機小檔讀取」撞到了 IOPS 瓶頸，永遠無法跑滿硬體宣稱的 3.5 GB/s 物理頻寬極限。

在NVMe SSD 環境下，為什麼大量 thread 搭配 synchronous I/O 的做法會變得很沒效率？

Answer

因為 NVMe 的 I/O 延遲極低（微秒級），大量 Thread 的阻塞與喚醒會造成頻繁的 Context Switch，這部分的 CPU 開銷甚至會蓋過實際的 I/O 等待時間。

Key Concept

Context Switch Overhead、Thread Starvation、NVMe Latency

Detail

Synchronous I/O 的特性是發出系統呼叫後，Thread 會被 OS 掛起（Blocked）。在 HDD 時代（延遲約 10ms），將 Thread 掛起並切換給其他人工作是很划算的；但在 NVMe 時代，一次 Random Read 僅需數十微秒，而 OS 進行 Thread Context Switch 的成本約需 1~5 微秒。若使用大量 Thread，CPU 資源將被嚴重浪費在排程與切換狀態上，而非執行真正的應用邏輯，導致效率低落。

描述一個 interrupt 比 polling 好的場景，和一個 polling 比 interrupt 好的場景。

Answer

Interrupt 較佳： I/O 請求稀疏且延遲較高的場景（如傳統 HDD）。
Polling 較佳： I/O 極度密集且延遲極低的場景（如 NVMe 高併發環境）。

Key Concept

Interrupt Storm、Busy-waiting、I/O Density

Detail

  • Interrupt 適用： 當系統 I/O 請求不多，或硬體處理速度較慢時，使用 Interrupt 可以讓 CPU 在漫長的等待期間去執行其他任務，不會空轉浪費資源。
  • Polling 適用： 當使用 NVMe SSD 且面臨極高 IOPS 吞吐時，Interrupt 機制會導致 CPU 每秒必須中斷數十萬次（Interrupt Storm），光是處理中斷就耗盡效能。此時改用 Polling 讓 CPU 專心在迴圈中檢查完成狀態，省去 Context Switch 的開銷，反而能大幅降低延遲。
