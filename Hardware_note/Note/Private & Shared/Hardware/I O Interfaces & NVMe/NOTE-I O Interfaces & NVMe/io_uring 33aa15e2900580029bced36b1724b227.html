在前面我們學過 synchronous 與 asynchronous I/O 的差異，而 Linux 早期的 async I/O 機制（如 libaio）有諸多限制，例如只支援 direct I/O 且 syscall 開銷仍然顯著。io_uring 是 Linux 從 5.1 開始引入的高效能 async I/O 框架，我們將深入探討它如何透過 kernel 與 user space 之間共享的 submission queue 和 completion queue ring buffer，讓應用程式不需要頻繁呼叫 syscall 就能提交與收割 I/O 請求。課程中我們也會介紹 batched submission 如何攤平 syscall 成本、SQPOLL 模式如何讓 kernel thread 持續 polling submission queue 以完全省去 submit 端的 syscall，以及 IOPOLL 模式如何用 polling 取代 interrupt 來降低 completion 延遲。此外，io_uring_cmd 機制允許我們直接下達 NVMe passthrough command，繞過傳統 block layer 的抽象。這些技術結合了我們先前學到的 block I/O 與 NVMe 知識，是目前 Linux 上最重要的高效能 I/O 介面。

Key Word Definition/ Discussion
io_uring

io_uring 是由 Jens Axboe 於 2019 年（Linux Kernel 5.1）引入的非同步 I/O 框架。它旨在解決傳統 system call 在高 IOPS 場景下的 Context Switch Overhead（模式切換開銷），透過 User Space 與 Kernel Space 共享記憶體（Ring Buffer） 的方式，實現極致的 I/O 吞吐量。

一個繁忙的資料庫 server 每秒要處理數十萬筆查詢，每筆查詢可能都需要從 SSD 讀取資料。傳統的做法是每次 I/O 都呼叫一次 system call，但 system call 本身不是免費的：

CPU 要從 user mode 切換到 kernel mode、儲存 register、做安全檢查，然後再切回來。

當你每秒要做幾十萬次這種切換，CPU 花在「進出 kernel 的門」上的時間比花在「實際搬資料」上的時間還多。io_uring 就是為了解決這個問題而被創造出來的。

Linux 很早就有 asynchronous I/O 的機制（POSIX AIO 和 libaio），但它們都有明顯的限制。

POSIX AIO 在 glibc 裡是用 thread pool 模擬的，本質上還是 synchronous。

libaio 只支援 O_DIRECT（不能用 page cache），而且每次提交都要呼叫 io_submit() system call，每次收割完成結果都要呼叫 io_getevents() system call。

在高 IOPS 場景下，system call 本身的成本就很可觀。一次 system call 涉及 user-to-kernel mode switch，大約需要幾百個 nanoseconds（包括 register save/restore、security checks 等等）。如果你每秒要做 100 萬次 I/O，那就是每秒 100 萬次 submit syscall 加上數十萬次 reap syscall，光是 syscall overhead 就會吃掉大量 CPU 時間。

  • 對比 libaio：libaio 僅支援 O_DIRECT（繞過 Page Cache），且每次提交與收割仍需 io_submit 和 io_getevents 兩個 syscall。
  • 對比 POSIX AIO：在 glibc 中是用 User-level thread pool 模擬，效率低下，並非真正的核心非同步。
  • 零拷貝 (Zero Copy)：因為使用了 mmap 共享記憶體，核心不需要在提交請求時從 User space 複製資料結構。

Pitfall:

  • 核心版本依賴：雖然 5.1 引入，但 5.10 (LTS) 之後的功能才趨於穩定與完整。開發時須檢查 IORING_FEAT_ 系列標誌。
  • 安全限制：由於繞過了許多傳統 syscall 路徑，早期版本在安全審查（如 seccomp）上存在挑戰。

SQE vs CQE

io_uring 的核心是兩個環形緩衝區（Ring Buffer）：

  1. SQ (Submission Queue)：應用程式寫入 SQE (Entry)，描述「要做的任務」。
  1. CQ (Completion Queue)：核心寫入 CQE (Entry)，回報「任務結果」。
  • SQE 關鍵欄位：opcode (讀/寫/fsync)、addr (Buffer 位址)、user_data (識別標籤)。
  • CQE 關鍵欄位：res (回傳值，如讀取的 bytes 或錯誤代碼)、user_data (與 SQE 對應)。
  • Head/Tail 機制：
    • Application 更新 SQ Tail，Kernel 消耗 SQ Head。
    • Kernel 更新 CQ Tail，Application 消耗 CQ Head。

Pitfall:

  • Memory Ordering：在直接操作記憶體而非使用 liburing 時，必須手動處理 Memory Barrier，確保寫入 SQE 的動作在更新 tail pointer 之前完成。
  • CQ Overflow：預設 CQ 是 SQ 的兩倍大。如果 CQ 滿了，新的 completion 可能會被暫時擋住甚至丟失。

Ring buffer

io_uring 的通訊基礎是建立在 User Space 與 Kernel Space 共享的兩組 Ring Buffer（環形緩衝區）：Submission Queue (SQ) 與 Completion Queue (CQ)。這是一種典型的生產者-消費者模型（Producer-Consumer），透過 mmap 技術，雙方都能直接存取這塊記憶體，徹底告別傳統 I/O 繁瑣的資料拷貝。

io_uring 的核心機制是 kernel 和 user space 共享兩個 ring buffer：

Submission Queue（SQ） 和 Completion Queue（CQ）。

初始化的時候，application 呼叫 io_uring_setup() 建立一個 io_uring instance。Kernel 會分配 SQ 和 CQ 的記憶體，然後把它們 mmap 到 user space。從此之後，kernel 和 application 直接透過 shared memory 溝通，不需要經過 syscall 來傳遞 I/O request 的內容。

提交 I/O：

Application 把一個 SQE（Submission Queue Entry）寫入 SQ ring buffer 的下一個空位。SQE 包含操作類型（read、write、fsync 等）、file descriptor、buffer address、offset、length 等所有必要資訊。寫完之後，application 更新 SQ 的 tail pointer。

收割結果：

Kernel 完成 I/O 之後，把結果寫成一個 CQE（Completion Queue Entry）放入 CQ ring buffer。CQE 包含結果狀態碼和一個 user_data field（application 在 SQE 裡面設的，用來辨別是哪個 request 完成了）。Application 讀取 CQ 的 head 到 tail 之間的所有 CQE 來收割結果，然後更新 CQ 的 head pointer。

SQ 和 CQ 都是 ring buffer，所以 head/tail pointer 到尾端之後會自動 wrap around。整個機制跟 NVMe 的 SQ/CQ 非常像，這不是巧合。io_uring 的設計明確受到 NVMe 的 command queue 模型啟發。

  • 同步機制：整個過程中，同步是透過更新兩個索引（Head 和 Tail）來完成的。
    • SQ (Submission)：Application 是生產者（更新 Tail），Kernel 是消費者（更新 Head）。
    • CQ (Completion)：Kernel 是生產者（更新 Tail），Application 是消費者（更新 Head）。
  • Indirection Table：為了靈活性，SQ 其實還有一層「索引表」。Application 寫入 SQE 後，在 sq_array 裡填入該 SQE 的位置。這樣的好處是允許 Application 以任意順序重複使用 SQE 陣列空間。
  • 致敬 NVMe：這套設計幾乎 1:1 模擬了 NVMe 的硬體通訊協議，這讓核心在轉發指令到 SSD 時的邏輯極簡化，路徑極短。

Pitfall:

  • Memory Ordering（記憶體屏障）：這是考試最愛考的細節。因為是共享記憶體且無鎖，你必須確保「SQE 的內容寫入」發生在「Tail 指標更新」之前。在 C 語言中需要手動呼叫 smp_store_release() 或 io_uring_smp_store_release()，否則核心可能讀到一個還沒寫完的殘缺指令。
  • CQ 溢出：如果你的 I/O 完成太快而你收割太慢，CQ 可能會溢出。雖然 io_uring 有內部的 backpressure 機制，但開發者仍需根據工作負載謹慎配置 entries 大小。

Batched submission

允許應用程式在一次 io_uring_enter() 系統呼叫中提交多個 SQE。

即使有了 shared ring buffer，application 還是需要呼叫 io_uring_enter() system call 來通知 kernel「我放了新的 SQE 進去，請處理」。

但 io_uring 的巧妙之處在於：你可以一次寫入多個 SQE，然後只呼叫一次 io_uring_enter()。假設你有 32 個 I/O request 要發，你先把 32 個 SQE 依序寫入 SQ，然後呼叫一次 io_uring_enter(submit=32)，kernel 就會一口氣處理這 32 個 request。

跟 libaio 的 io_submit() 比較：libaio 每次呼叫也可以提交多個 request，但 io_uring 的 batching 更高效，因為 SQE 已經在 shared memory 裡了，kernel 不需要從 user space 複製 request 的內容。

Batched submission 在高 IOPS 場景下效果非常明顯。假設你每秒要做 50 萬次 I/O，如果每次只 submit 1 個就 enter 一次，那就是每秒 50 萬次 syscall。如果你每次攢 32 個再 enter，syscall 降到每秒約 1.5 萬次，減少了 97%。

效率公式：假設每秒 N 個 I/O。傳統方式需要 N 次 syscall；Batch 方式（每次 batch M 個）只需 N/M 次 syscall。
Amortized Cost：在高負載下，單次 I/O 分攤到的 syscall 成本趨近於零。

Pitfall:

Latency vs. Throughput：過大的 Batch 會導致第一個請求被「壓」在 SQ 中等待後面的請求湊齊，進而增加 Tail Latency (長尾延遲)。

SQPOLL vs IOPOLL
  • SQPOLL：解決 Submit 端 成本。核心啟動 Kernel Thread 輪詢 SQ，實現「零 syscall 提交」。
  • IOPOLL：解決 Completion 端 成本。核心主動輪詢硬體完成狀態，實現「零 interrupt 完工」。

SQPOLL 模式：零 Syscall 提交

Batched submission 把 syscall 次數降了很多，但還是有 syscall。對於那些需要榨乾每一分效能的場景，例如高頻交易系統的 storage layer、或是每秒處理百萬筆請求的 key-value store，即使是少量的 syscall overhead 也嫌太多。io_uring 提供了更激進的 SQPOLL 模式，可以完全消除 submit 端的 syscall。

開啟 SQPOLL 之後，kernel 會啟動一個專屬的 kernel polling thread。這個 thread 不斷地去看 SQ ring buffer 有沒有新的 SQE（透過檢查 SQ 的 tail pointer 是否被 application 更新了）。只要發現新的 SQE，kernel thread 就自動取出來處理。

Application 的角度完全變了：你只需要把 SQE 寫進 SQ ring buffer、更新 tail pointer，然後什麼都不用做。不需要呼叫任何 syscall。Kernel thread 會自己來取。

代價是什麼？那個 kernel polling thread 會持續佔用一個 CPU core（或至少佔用它的很大比例），即使沒有任何 I/O 要處理，它也在空轉 poll。所以 SQPOLL 適合的場景是 I/O 非常密集、需要最低延遲的 workload。如果你的 I/O 是偶爾才來一個，SQPOLL 就是在浪費 CPU。

為了緩解這個問題，SQPOLL 有一個 idle timeout 機制：如果 polling thread 發現超過一段時間都沒有新的 SQE，它會自動進入 sleep 狀態。下次 application 寫了新的 SQE 之後如果發現 polling thread 已經 sleep，就需要呼叫一次 io_uring_enter() 把它叫醒。所以 SQPOLL 不是「永遠零 syscall」，而是「在 I/O 持續密集的時候零 syscall」。

IOPOLL 模式：Polling 取代 Interrupt

前面的 SQPOLL 解決的是 submit 端 的 syscall 問題。IOPOLL 解決的則是 completion 端 的 interrupt 問題。

在正常模式下，I/O 完成的時候裝置送 interrupt 通知 kernel，kernel 把結果填入 CQ，然後透過某種機制（eventfd、signal、或 application 下次呼叫 io_uring_enter 順便 reap）通知 application。每次 interrupt 都有幾個 microseconds 的 overhead。

IOPOLL 模式開啟之後，kernel 不等 interrupt。Application 呼叫 io_uring_enter(flags=IORING_ENTER_GETEVENTS) 的時候，kernel 直接去 poll 裝置的 completion queue（對 NVMe 來說就是去檢查 NVMe CQ 有沒有新的 completion entry）。如果有，立刻處理並填入 io_uring 的 CQ。如果沒有，繼續 poll，直到有結果或超時。

IOPOLL 的好處是延遲更低：I/O 完成之後不需要等 interrupt delivery 和 handler 的開銷，下一次 poll 就能拿到結果。在 NVMe SSD 的 read latency 只有幾十個 microseconds 的情況下，省掉 interrupt 的幾個 microseconds 是有意義的改善。

IOPOLL 必須搭配 O_DIRECT 使用（因為 buffered I/O 的 completion path 不支援 polling）。而且 IOPOLL 會讓呼叫 io_uring_enter 的 thread 在 kernel space busy-wait，所以它會佔用 CPU。跟 SQPOLL 類似，適合 I/O 密集且對延遲極度敏感的場景。

把 SQPOLL 和 IOPOLL 同時開啟，就能得到一個「submit 不需要 syscall、completion 不需要 interrupt」的極致 I/O 路徑。在這個模式下，application 只需要操作 shared memory 的 SQ 和 CQ，kernel polling thread 處理 submit，completion 也走 polling。整條路徑上幾乎沒有任何 mode switch。

  • SQPOLL Idle Timeout：核心執行緒若一段時間沒事做會睡覺，需呼叫 io_uring_enter 喚醒。
  • 最強組合：同時開啟 SQPOLL + IOPOLL，資料搬運過程完全沒有 User/Kernel Mode 的切換與中斷開銷。

Pitfall:

  • CPU 飢餓 (Starvation)：SQPOLL 會無條件占用一個 CPU 核心進行輪詢，即便沒資料也會空轉（Busy-wait），適合 I/O 密度極高的服務。
  • IOPOLL 限制：必須搭配 O_DIRECT 使用。

io_uring_cmd

繞過 Linux Block Layer（I/O 調度器、檔案系統層），讓 io_uring 直接發送原生 NVMe 指令給驅動程式。

io_uring_cmd：NVMe Passthrough

io_uring 預設的 I/O 路徑還是要經過 Linux 的 block layer。Block layer 提供了很多有用的功能（I/O scheduler、I/O accounting、encryption 等等），但在極端效能場景下，它也是一層 overhead。

io_uring_cmd 機制允許 application 透過 io_uring 直接向 NVMe driver 發送 passthrough command，完全繞過 block layer。Application 可以自己組裝 NVMe command（包括 opcode、LBA、PRP 等），然後用 io_uring_cmd 直接把這個 raw NVMe command 丟給 driver。

這有什麼用？一般的 read() / write() 經過 block layer 之後，中間有 I/O scheduler 的 reordering、merging、plugging 等處理，這些東西在 HDD 時代很有價值（可以減少 disk seek），但在 NVMe SSD 上反而是多餘的 overhead。透過 io_uring_cmd passthrough，application 可以跳過這些中間層，直接操作 NVMe 的 command queue。

io_uring_cmd 也支援 NVMe 的特殊 command，比如 zone management command（for Zoned Namespace SSD）或 vendor-specific command，這些是一般 block layer 不支援的。

不過 io_uring_cmd 的使用門檻比較高：application 必須自己理解 NVMe command format，自己管理 DMA buffer，而且失去了 block layer 提供的所有便利功能（file system、encryption、I/O priority）。它的定位是給高效能 storage application（例如 database engine、storage target）使用的進階功能，不是給一般 application 用的。

  • 繞過 Overhead：Block Layer 的隊列管理在 HDD 時代有用，但在萬分之一秒等級的 NVMe SSD 上卻是多餘的 CPU 負擔。
  • 特殊指令：支援 Zoned Namespace (ZNS) 或廠商自定義指令。

Pitfall:

  • 資料損壞風險：失去檔案系統保護，應用程式若寫錯地址會直接破壞硬體數據。
  • 複雜性：應用程式需自己處理 DMA Buffer 對齊與 NVMe 指令封裝。

NVMe passthrough

這是 io_uring 在核心 5.19 引入的重磅功能（透過 IORING_OP_URING_CMD 指令）。它允許應用程式直接對 NVMe 驅動程式發送原生指令，完全跳過 Linux 傳統的 Block Layer（塊設備層）。

  • 消滅中間商：傳統 Block Layer 會做 I/O 合併、排序與排隊計費。但在現代超高速 NVMe SSD 上，這些軟體邏輯往往比硬體還慢。Passthrough 就像是給 I/O 辦了「快速通關」，直接從應用程式通往硬體。
  • 解鎖隱藏功能：許多 NVMe 的進階功能（如 ZNS 區塊管理、KV 指令集、或是特定廠商的 Health Debugging）無法透過標準 read/write 實現。Passthrough 讓開發者能直接撰寫 nvme_passthru_cmd 結構並丟給核心。
  • 效能數據：在極限測試中，使用 Passthrough 往往能比標準 io_uring 再降低 5%~10% 的延遲，並減少 CPU 在 Block Layer 的耗能。

Pitfall:

  • 失去安全墊：Block Layer 提供了一層保護，防止你誤寫核心區域或檔案系統元數據。用 Passthrough 時，如果你 LBA (Logical Block Address) 算錯，核心不會擋你，資料會直接毀損。
  • 不可移植性：你的代碼會與「NVMe」這個硬體規範綁死。如果客戶換成 SATA SSD 或雲端虛擬硬碟，代碼會直接失效。
  • 權限問題：這種操作通常需要 CAP_SYS_ADMIN 權限，這在容器化環境（如 Kubernetes）中需要特別配置 Security Context。

Key Concept

Shared Memory (mmap), Submission Queue Entry (SQE), Completion Queue Entry (CQE), Zero-copy, Context Switch 降低

Detail

在傳統的 I/O 模型中，每次提交或收割請求，都需要透過系統呼叫（Syscall）跨越 User/Kernel 邊界，並將資料結構進行複製。io_uring 運用了 Ring Buffer 加上 mmap 技術，讓作業系統與應用程式看見同一塊記憶體。
當應用程式要提交 I/O 時，只需在 User Space 將 SQE 填入並推進 SQ 的 Tail 指標；收割時則是檢查 CQ 的 Head 指標並讀取 CQE。這種設計使得 Kernel 能直接存取請求，完全消除了 memcpy 的額外開銷，同時也為後續的 Batched 與 Polling 最佳化打下基礎。

理解 batched submission 如何將多筆 I/O 請求一次提交，攤平 syscall 的成本，提升高 IOPS 場景下的效率

Answer

允許應用程式在 shared ring buffer 中一次填寫多個 I/O 請求後，僅呼叫一次系統呼叫來通知 Kernel 處理，藉此將單次 syscall 的成本平均分攤。

Key Concept

Batching, io_uring_enter, Syscall Amortization (成本攤平), High IOPS

Detail

在高 IOPS（每秒輸入/輸出次數）的場景下，如果每一個 4KB 的請求都觸發一次 Syscall，CPU 大量的時間會被浪費在 Context Switch（上下文切換）上。透過 Batched Submission，應用程式可以連續在 SQ 中寫入幾十或幾百個 SQE，然後只呼叫一次 io_uring_enter 系統呼叫來喚醒 Kernel。這樣一來，單次 Context Switch 的 CPU 週期成本被多個 I/O 請求共同承擔，大幅提升了整體的吞吐量 (Throughput)。

理解 SQPOLL 模式的運作方式，知道它讓一個專屬的 kernel thread 持續 polling submission queue，使應用程式完全不需要呼叫 syscall 就能提交 I/O

Answer

啟動一個專屬的 Kernel Thread 於背景持續輪詢 (Polling) Submission Queue。應用程式只需放入請求，完全不需要呼叫 syscall 就能觸發 I/O。

Key Concept

SQPOLL (IORING_SETUP_SQPOLL), Kernel Thread, Zero-syscall, 主動輪詢

Detail

這是 io_uring 追求極致效能的進階模式。當開啟 IORING_SETUP_SQPOLL 標記後，Kernel 會建立一個專屬的執行緒 (通常名為 io_uring-sq)。這個 Thread 會持續監控共用的 Submission Queue；一旦應用程式在 User Space 更新了 SQ 的 Tail 指標，Kernel Thread 會立刻偵測到並抓取 SQE 進行處理。
這意味著應用程式提交 I/O 的過程變成了純粹的 User Space 記憶體操作，達成了真正的「Zero-syscall (零系統呼叫)」，極大地壓榨出硬體極限。

理解 IOPOLL 模式如何用 polling 取代 interrupt 來通知 I/O 完成，降低 completion 端的延遲

Answer

放棄傳統的硬體中斷 (Interrupt) 通知機制，改由 CPU 主動向底層 NVMe 裝置輪詢 I/O 是否完成，用 CPU 資源換取極低的 I/O 延遲。

Key Concept

IOPOLL (IORING_SETUP_IOPOLL), Interrupt vs. Polling, Low/Tail Latency, NVMe completion queue。

Detail

傳統硬體在 I/O 完成時，會向 CPU 發送硬體中斷，OS 接著觸發中斷處理程序來收割結果。對於現代超高速的 NVMe SSD 而言，這種「中斷延遲」已經成為效能瓶頸。啟用 IOPOLL 後，Kernel 不再被動等待中斷，而是在提交 I/O 後主動去查閱裝置硬體層的 Completion Queue。雖然這會造成 CPU 占用率升高 (100% busy-wait)，但在需要極端低延遲 (Low Tail Latency) 的資料庫或儲存引擎場景中，這是非常划算的交易。

了解 io_uring_cmd 機制如何讓應用程式直接下達 NVMe passthrough command，繞過傳統 block layer 的抽象來操作 NVMe 裝置

Answer

允許應用程式繞過 Linux 核心龐大的 Block Layer 與 VFS，將原生的 NVMe 指令透過 io_uring 直接傳送給底層裝置驅動。

Key Concept

io_uring_cmd, NVMe Passthrough, Block Layer Bypass, Character Device (/dev/ngXnY)。

Detail

傳統 Linux I/O 會經過虛擬檔案系統 (VFS)、Block Layer 抽象層，最後才轉譯為硬體指令，這段軟體堆疊開銷不小。io_uring_cmd 是後來引入的強大機制，它允許應用程式對 NVMe 的 Character Device (/dev/ng*) 開啟檔案，並將特製的 NVMe command (例如特定的 Admin command 或自訂的 I/O command) 包裝進 SQE 中直接發送給驅動層。這為需要深度控制硬體的應用 (如 SPDK 等級的應用程式) 提供了一個原生的、極高效的 Kernel 替代方案。

Test your understanding
io_uring 的 shared ring buffer 設計和傳統 libaio 比起來，在 submit 和 reap 的流程上各省掉了什麼開銷？為什麼光是「不需要 copy request 內容」就能帶來明顯的效能差異？

Answer

比起 libaio，io_uring 省下了 submit 時複製請求 (iocb) 和 reap 時複製結果 (io_event) 的開銷。免除記憶體拷貝不僅省下 CPU 週期，更避免了 CPU Cache 污染與指標驗證的負擔，從而帶來效能提升。

Key Concept

io_submit / io_getevents, Memory Copy Overhead (User-to-Kernel), CPU Cache Eviction (快取污染)

Detail

  • 流程上的省卻：

    傳統的 libaio 在呼叫 io_submit 時，Kernel 必須將 User space 的 iocb 結構陣列 複製 (copy_from_user) 到 Kernel space；在呼叫 io_getevents 收割時，又必須將結果的 io_event 結構 複製 (copy_to_user) 回 User space。io_uring 憑藉 Shared ring buffer 的設計，徹底移除了這兩段資料複製流程。

  • 效能差異原因：

    光是「不需要 copy」就能帶來顯著效能差異的原因在於：這不僅省去了 memcpy 指令本身的 CPU 時間，更重要的是它避免了高並發下的 CPU 快取失效 (Cache Misses)。當大量無謂的資料在 user/kernel 間複製時，會把有用的資料擠出 L1/L2 Cache。Zero-copy 讓 CPU 能專注於業務邏輯與 I/O 處理，且免去了 Kernel 每次都要檢查 user space 記憶體指標合法性的安全驗證開銷。

假設你的 application 每秒需要做 50 萬次 4KB random read。在不使用 batching 的情況下需要多少次 syscall？使用 batch size 64 的 batched submission 之後需要多少次？SQPOLL 模式下需要多少次？

Answer

  • 不使用 batching：50 萬次 syscall。
  • Batch size 64：7,813 次 syscall。
  • SQPOLL 模式：0 次 syscall（理想狀態下）。

Key Concept

Syscall Math, Batching efficiency, SQPOLL zero-syscall, 效能攤平

Detail

  • 不使用 Batching： 每個請求獨立發送，1 次 I/O 請求對應 1 次 io_uring_enter，因此 500,000 次 random read 就會產生 500,000 次 System Call。
  • 使用 Batch size 64： 應用程式每累積 64 個 SQE 才呼叫一次 io_uring_enter 來通知 Kernel。計算方式為 500,000 / 64 = 7812.5。因此只需要約 7,813 次 System Call。Syscall 次數直接下降了超過 98%。
  • SQPOLL 模式： 由於背景有一個專屬的 Kernel Thread 在不停輪詢 (Polling) 共用的 Submission Queue，應用程式只需在 User Space 填寫 SQE 並更新 tail pointer，Kernel Thread 就會自動將其取走。在沒有因閒置導致 Kernel Thread 休眠的理想狀況下，應用程式提交這 50 萬次 I/O 完全不需要呼叫任何 syscall，即 0 次。

    Answer

    poll 在處理檔案 I/O 時存在侷限，因為它無法有效區分資料是存在硬碟還是已快取在 Page Cache；而 io_uring 統一了網路與儲存介面，並透過 Shared Ring Buffer 減少了 mode switch 的開銷。

    解析:

    Linux 的一般檔案幾乎永遠對 epoll 回報「就緒」，導致 epoll 無法感知實際磁碟延遲，資料庫系統因此不得不另行依賴 libaio 處理 Direct I/O。io_uring 透過 SQ/CQ 共享記憶體環形緩衝區，讓使用者空間與核心免於反覆切換，且同時覆蓋網 路、Buffered 與 Direct I/O。

    (1) io_uring 的效益來自 queue depth 的提高。若系統邏輯仍為同步 (送出請求後即原地等待)，queue depth 始終為 1，因此 必須配合 Fiber 或 Coroutine 等非同步設計，才能真正釋放 io_uring 的潛能。

    (2) io_uring 的核心優勢之一是透過 單一介面同時支援 Buffered I/O、Direct I/O 與網路 Socket ，打破了過去必須 混用 epoll + libaio 的局面。在網路場景中，io_uring 同樣可減少 syscall 次數，效能不遜於 epoll。

    (3) epoll 在網路連線上確實是成功的 Event-Driven 解法，但它對檔案 I/O 幾乎完全無效。Linux 的檔案永遠被視為「就緒」狀 態，epoll 無法分辨資料是已快取在 Page Cache 還是仍在硬碟上。因此資料庫系統不得不同時維護兩套機制：epoll 處理網 路、libaio 處理硬碟，這正是 io_uring 出現並統一兩者的動機。

    io_uring 透過 mmap 建立 User 與 Kernel 共享的 Ring Buffers，應用程式可實現 SQE 的 Batch submission，顯著減少 syscall 次數。

    這是 io_uring 的核心設計。透過 memory-mapped 將 Submission Queue (SQ) 與 Completion Queue (CQ) 映射至用戶空間，應用程式可以直接寫入多個 SQE，再透過一次 io_uring_enter 系統呼叫批量提交，大幅降低 Overhead。

    (1) Fibers 屬於 User-space 的協作式排程，在單一執行緒內僅能達成 Concurrency（並行）而非 parallelism。Parallelism 必須依賴多個實體 CPU 核心同時執行任務。

    (2) Direct I/O 的核心在於繞過 Kernel Page Cache（文件快取），使數據直接在儲存裝置與 User Buffer 之間傳輸。這消除了從 Kernel Buffer 到 User Buffer 的軟體拷貝開銷，而非增加雙重緩衝。

    (4) SQE 通常為 64 bytes（含指令、位址、偏移量等），而 CQE 通常僅為 16 bytes。CQE 並不攜帶大量的數據 Payload，僅回傳 res（結果狀態）與使用者定義的標記（user_data），實際數據是透過 DMA 直接傳輸至 User Buffer。

    解析:

    SQPOLL（Submission Queue Polling）功能會產生一個核心執行緒來輪詢提交隊列。這使得應用程式只需將資料寫入 SQ 並更新 userspace 中的 tail pointer，核心執行緒就會自動接手工作，未睡眠時可避免 system call。

  1. 某間公司的 HTTP 檔案伺服器運行於配備 NVMe SSD 的機器上， 尖峰時段需同時處理約 10,000 筆並行隨機讀取請求（每筆 4KB）。 工程師評估導入 io_uring 來降低 I/O 開銷，但伺服器的 CPU 核心數有限， 且 HTTP 流量具備明顯的 bursty。 在這個情境下，哪一種 io_uring 配置組合最能在吞吐量與 CPU 效率之間取得平衡？
    1. 啟用 SQPOLL 搭配 Registered Buffers，讓核心執行緒主動輪詢 SQ，以徹底消除 Syscall 與中斷的所有開銷。
    1. 使用 Registered Buffers 搭配 Registered Files，並以 Batching 方式批次提交 SQE；不啟用 SQPOLL 或 IOPOLL。
    1. 啟用 SQPOLL + IOPOLL 雙輪詢模式，並對每筆請求獨立提交一個 SQE（不使用 Batching）。
    1. 使用 IOPOLL 模式並對每次請求各自動態分配一個 4KB Buffer，以精確消除 interrupt storm 並最小化記憶體佔用。
    Answer

    使用 Registered Buffers 搭配 Registered Files，並以 Batching 方式批次提交 SQE；不啟用 SQPOLL 或 IOPOLL。

    解析:

    這是最符合此情境的組合： Registered Buffers 讓核心在 io_uring_register() 時一次性完成 DMA Mapping 與記憶體頁面固定（Pin）， 省去每筆 I/O 重複的 Setup 開銷； Registered Files 同理，省去每次操作的 File Descriptor 查找成本； Batching 則將多筆 SQE 於一次 io_uring_enter() 中一起提交， 大幅攤提 Syscall 開銷。 不啟用 SQPOLL/IOPOLL 的原因是：HTTP 流量具有突發性， 輪詢模式在低峰期會持續消耗 CPU，與 CPU 核心數有限的前提相衝突。

    (1) 此配置有兩個問題： 第一，SQPOLL 消除的是「提交端」的 Syscall 開銷，而非中斷開銷（那是 IOPOLL 的功能）， 描述混淆了兩者的職責； 第二，SQPOLL 的核心執行緒會 Burn 一顆 CPU 核心進行輪詢， 在 HTTP 這類具有突發性的場景中，流量低峰時這顆核心依然空轉， 對 CPU 核心數有限的伺服器是嚴重的資源浪費。

    (3) 此配置有兩個致命缺陷： SQPOLL 與 IOPOLL 各自佔用一個 CPU 核心進行 busy-poll， 在 HTTP 流量具有突發性的情境下，低峰期會大量浪費 CPU； 加上缺乏 Batching，每筆請求各自觸發一次 io_uring_enter()， Syscall 開銷完全無法攤提，整體 CPU 使用率反而更高。

    (4) 此配置有兩個矛盾： IOPOLL 確實能消除硬體中斷，但代價是 CPU 必須持續 busy-waitNVMe 控制器， 在高並行場景下反而會顯著拉高 CPU 使用率，與「CPU 效率」目標背道而馳； 同時，每次請求動態分配獨立 Buffer 意味著放棄了 Registered Buffers 的核心優勢—— 每筆 I/O 仍需重新進行 DMA Mapping 與頁面固定， 讓 io_uring 對記憶體管理的最佳化形同虛設。

  1. 某量化交易公司的一名工程師正在設計高頻交易系統（HFT storage layer），系統每秒需要處理數十萬次 4KB 隨機讀取。 他觀察到 CPU 使用率很高，但 SSD 使用率卻不高。進一步分析後發現，CPU 大量時間消耗在 system call 上。 因此他將系統從傳統 read() 改為 io_uring，並使用 batched submission，每次提交 32 個 I/O requests。

    1. 攤平 user 與 kernel mode 切換成本，使每個 I/O 平均 syscall 成本下降
    1. 將多個 I/O request 合併為單一實體 I/O，減少裝置操作次數
    1. 降低 DMA 傳輸成本，使資料搬運更快
    1. 降低 SSD 的 device latency
    Answer

    攤平 user 與 kernel mode 切換成本，使每個 I/O 平均 syscall 成本下降

    解析:

    正確。io_uring 的 batching 讓多個 request 共用一次 syscall， 原本每個 I/O 都需要 mode switch，現在變成 amortized cost。 CPU 時間從「進出 kernel」轉回「實際工作」。

    (3) DMA 行為完全不變，仍由裝置負責資料搬運。實際 DMA 由硬體處理，io_uring 不改變傳輸機制。

    解析:

    每 64 個 I/O 合併為一次提交，因此 syscall 次數從 640,000 次降為 10,000 次。 關鍵節省來自兩點： 第一， batched submission 減少 user mode 與 kernel mode 的 mode switch 次數； 第二， io_uring 將 SQE 直接放在 shared memory 中，kernel 不需要逐筆 copy request。

    (2) 雖然單次 syscall 處理的 SQE 變多，但 syscall 的固定成本（mode switch、register save/restore 等）只發生一次， 而不是隨 SQE 數量線性增加。因此總體 syscall overhead 會顯著下降，而不是只是把原本分散的延遲集中到少數幾次 syscall 中。

    (3) interrupt 次數主要與 completion path（例如 IOPOLL）相關，而非 submission batching。 batched submission 的核心目標是減少 syscall 次數與資料傳遞成本，並不直接影響裝置 interrupt 行為。

    (4) shared ring buffer 確實減少資料傳遞成本，但在未啟用 SQPOLL 的情況下， application 仍需要透過 io_uring_enter() 通知 kernel 有新的 SQE 進來請處理。 因此若不做 batching，每個 I/O 仍可能對應一次 syscall，無法消除 syscall overhead。

  1. 某系統工程師將系統從 io_uring（經 block layer）改為 io_uring_cmd（NVMe passthrough）， 發現 latency 降低約 10%，但系統變得更難維護。 下列哪個原因最能解釋這個 trade-off？
    1. 因為 application 必須自己處理 NVMe command 與 memory 管理，失去 kernel abstraction
    1. 因為 NVMe SSD 在 passthrough 模式下關閉了 queue 機制
    1. 因為 filesystem 被完全移除，資料直接寫入 DRAM
    1. 因為 DMA 不再使用 physical address，因此需要額外轉換成本
    Answer

    因為 application 必須自己處理 NVMe command 與 memory 管理，失去 kernel abstraction

    解析:

    正確。繞過 block layer 後需自行處理 NVMe command 與 DMA buffer， 失去 kernel abstraction，複雜度提升換取較低 latency。

    (2) NVMe queue 仍存在，passthrough 僅繞過 block layer，不影響裝置機制。

    (3) 混淆 filesystem 與資料來源。filesystem 只負責 mapping， 資料仍需從 SSD 經 DMA 搬到記憶體，並非直接產生於 DRAM。

    (4) 實際 DMA 仍使用 physical address，passthrough 不改變此機制，此說法不成立。

  1. 某超低延遲的交易系統正在將其儲存引擎從傳統的 libaio 遷移至 io_uring。工程師在 profiling 時發現，在每秒提交百萬次 I/O 請求的高負載情境下，io_uring 不僅消除了大量的 context switch，還大幅減少了 CPU 在 memory copy 上的開銷。

    請問 io_uring 是透過何種軟體架構設計，來徹底消除傳統 I/O 介面在「提交與接收指令」階段的資料搬運開銷？

    1. io_uring 會強制關閉 NVMe SSD 的 DMA 控制器，改為由 kernel 啟動一個專屬的 SQPOLL 執行緒，使用 CPU 親自將資料從 user space 搬運至 SSD 的快取中，藉此換取極低的延遲。
    1. io_uring 透過 mmap 機制，讓 user space 與 kernel space 直接共享 submission queue（SQ）與 completion queue（CQ）的記憶體區塊。應用程式只需將 I/O 指令寫入共享的 ring buffer，kernel 即可直接讀取，完全免除了傳統 system call 必須在兩個空間之間拷貝指令陣列的 CPU 開銷。
    1. io_uring 會在 user space 動態分配一塊記憶體，並要求應用程式每次提交 I/O 時，都必須主動呼叫 mmap() 來與 kernel 重新建立映射，藉此確保每個 I/O 請求的安全性與獨立性。
    1. io_uring 直接將 NVMe SSD 硬體上的 SQ 與 CQ 實體位址暴露給 user space，讓應用程式能完全繞過 Linux kernel 與檔案系統，直接對底層的 SSD 控制器發送指令。
    Answer

    io_uring 透過 mmap 機制，讓 user space 與 kernel space 直接共享 submission queue（SQ）與 completion queue（CQ）的記憶體區塊。應用程式只需將 I/O 指令寫入共享的 ring buffer，kernel 即可直接讀取，完全免除了傳統 system call 必須在兩個空間之間拷貝指令陣列的 CPU 開銷。

    解析:

    這是正確的。傳統的 libaio 在呼叫 io_submit() 時，kernel 必須將 user space 的 iocb 結構陣列逐一拷貝到 kernel space 才能處理。而 io_uring 巧妙地借鑑了 NVMe 的硬體設計，在軟體層面上實作了基於 mmap 共享的 SQ 與 CQ。應用程式在 user space 寫入指令、讀取結果，kernel 直接在同一個實體記憶體位址處理，達成了真正的 Zero-copy for commands。

  1. 工程師在一個對延遲極度敏感的 key-value store 中同時啟用了 SQPOLL 和 IOPOLL 模式，並搭配 O_DIRECT。系統上線後觀察到以下現象：

    在 I/O 持續密集的時間段（每秒超過 80 萬次 I/O），延遲表現非常好。 但在每天凌晨 3~4 點的低峰期（請求稀疏，常出現數秒的空窗期），偶爾會出現單筆請求延遲突然飆升到數十 ms 的情況，而且這種高延遲的發生是週期性的、而不是持續性的。請問最可能造成凌晨低峰期 週期性延遲飆升 的原因是什麼？

    1. IOPOLL 模式要求呼叫 io_uring_enter() 時 kernel 在 kernel space busy-wait。在低峰期，因為同時執行的 I/O 請求少，busy-wait 的競爭降低，反而讓 kernel 把更多 CPU 時間花在其他系統任務上，造成 I/O completion 的處理被延後。
    1. 同時啟用 SQPOLL 和 IOPOLL 在低負載下會造成兩個 polling thread 之間的 CPU 資源競爭。在高負載時兩者都有足夠的工作要做，分工明確；在低負載時兩者都在 idle spinning，競爭同一個 CPU core 的使用權，造成 context switch overhead 上升，間接拖慢 I/O 延遲。
    1. IOPOLL 在低 I/O 負載下會造成 kernel busy-wait 的時間拉長。因為 NVMe 裝置在 I/O 少的時候進入省電模式，response time 變慢，kernel polling thread 需要 busy-wait 更長時間才能等到 completion，導致單筆 I/O 的延遲上升。
    1. SQPOLL 的 kernel polling thread 在低 I/O 負載下會因為長時間沒有新的 SQE 而進入睡眠狀態。下一個 I/O 請求到來時，則必須把它叫醒，但這個 wake-up 本身有一定的延遲。因此在低峰期 I/O 稀疏的情況下，每次 idle sleep 過後的第一批請求需要等待喚醒，造成週期性的延遲飆升。
    Answer

    SQPOLL 的 kernel polling thread 在低 I/O 負載下會因為長時間沒有新的 SQE 而進入睡眠狀態。下一個 I/O 請求到來時，則必須把它叫醒，但這個 wake-up 本身有一定的延遲。因此在低峰期 I/O 稀疏的情況下，每次 idle sleep 過後的第一批請求需要等待喚醒，造成週期性的延遲飆升。

    解析:

    週期性這個關鍵詞是核心線索：不是每個請求都慢，而是 polling thread 睡著之後的第一個請求才慢，之後 polling thread 醒著的這段時間請求都正常，直到下一次 idle timeout 觸發。這個模式完全符合 SQPOLL idle timeout 機制的行為。 且 SQPOLL 適合的場景是 I/O 非常密集、需要最低延遲的 workload。如果你的 I/O 是偶爾才來一個，SQPOLL 就是在浪費 CPU。

    (1) 這個邏輯是自相矛盾的。IOPOLL 的 busy-wait 是主動輪詢 NVMe CQ，它不會因為競爭降低就把 CPU 讓給其他任務。低峰期 I/O 少反而讓每次 busy-wait 更快結束（因為等待的 I/O 少），不會造成延遲飆升，更不會是週期性的現象。

    (2) SQPOLL 是 kernel polling thread 監控 SQ，IOPOLL 是呼叫 io_uring_enter() 的 thread 在 kernel space busy-wait，這兩者的運作機制不同，不會形成兩個 polling thread 競爭同一 core 的情況。 且這個解釋無法說明為何延遲飆升是 週期性 的，而不是持續性的。競爭導致的延遲應該在低負載時持續存在，而不是像脈衝一樣週期性出現。

    (3) 這個解釋混淆了因果關係。IOPOLL 的 busy-wait 確實佔用 CPU，但它讓延遲 更低 而非更高，因為省掉了 interrupt 的 delivery overhead。 NVMe 省電模式確實存在，但這會讓所有 I/O 都變慢，不會造成週期性飆升，更不符合低峰期才出現的模式。

  1. 某高效能資料庫團隊在使用 io_uring 時發現，雖然已經將 SQ 與 CQ 的機制發揮到極致，但 Linux block layer 內部的 I/O scheduler（如 merging 或 reordering）在高速 NVMe SSD 環境下反而成為了多餘的 overhead。若團隊希望應用程式能直接掌控硬體，甚至發送裝置專屬的 vendor-specific command，最合適的架構選擇及其伴隨的代價為何？
    1. 透過調整 io_uring_setup() 的參數來增加 entries 數量並配合 batched submission。這能顯著提升單次 io_uring_enter 處理的指令總數。代價是記憶體開銷增加，且無法改變指令在 kernel 內部的傳遞路徑。
    1. 在開啟檔案時強制使用 O_DIRECT 旗標。這能確保資料不經過 page cache 而直接寫入硬體。代價是必須滿足特定的記憶體對齊要求，但底層路徑仍受 block layer 的規範限制。
    1. 同時啟用 SQPOLL 與 IOPOLL 模式。這能實現無 system call 提交與無 interrupt 完成的極致路徑。代價是會持續佔用 CPU 核心進行輪詢，且依然無法發送 block layer 不支援的硬體指令。
    1. 使用 io_uring_cmd 進行 NVMe passthrough。這允許應用程式直接繞過 block layer 並發送 raw command 給驅動程式。代價是開發者必須自行管理 DMA buffer，且會失去 file system 與 encryption 等核心功能。
    Answer

    使用 io_uring_cmd 進行 NVMe passthrough。這允許應用程式直接繞過 block layer 並發送 raw command 給驅動程式。代價是開發者必須自行管理 DMA buffer，且會失去 file system 與 encryption 等核心功能。

    解析:

    io_uring 的預設路徑仍需經過 block layer 的處理邏輯，而 io_uring_cmd 提供了 passthrough 機制直接對接 driver。這能跳過針對傳統磁碟設計的優化開銷，但也意味著應用程式必須承擔原本由 kernel 處理的資源管理責任，且無法享用基於 block device 構建的檔案系統功能。

    (1) batching 技術的核心在於減少頻繁進出 kernel 門檻（system call）的時間成本。它優化的是指令的提交密度而非處理路徑，指令內容本身仍受限於 io_uring 預設的結構定義，無法夾帶不符合規範的硬體指令。

    (2) O_DIRECT 的設計目標是消除 page cache 的複製與同步開銷。雖然減少了記憶體層級的負擔，但請求進入 kernel 後仍會被封裝成標準的 I/O 請求並遵循 block layer 的排程與處理機制，無法達成對硬體的直接指令控制。

    (3) 這兩項技術分別針對 submission 端的 system call 與 completion 端的 interrupt 進行優化。即便兩者並行，請求在 kernel 內部依然是透過標準的 block layer 路徑傳遞，因此無法解決 I/O scheduler 帶來的延遲，也無法發送非標準的硬體指令。

  1. 假設你正在開發一個類似 RocksDB 的儲存引擎，並打算將原本基於多執行緒的 synchronous I/O 遷移至 io_uring 搭配 asynchronous I/O。 下列關於這項技術轉換的敘述，下列哪項正確？

    Answer

    io_uring 透過 SQ 與 CQ 實現 user 與 kernel 空間的記憶體共享，能有效減少頻繁 syscall 帶來的 context switch 開銷。

    解析:

    這是 io_uring 的核心設計。透過與 kernel 共享 ring buffer，應用程式可以批次提交請求，在開啟 SQPOLL 模式下，不需要執行 syscall 就能讓 kernel 處理 I/O

    (1) 這是舊版 Linux AIO 的主要限制。io_uring 的一大突破就是它能處理包括 buffered I/O 在內的大部分 syscall，且能真正實現非同步執行。

    (2) Async I/O 的優勢在於提高 throughput 與 CPU 利用率，而非縮短單次硬體存取的時間，由於增加了隊列管理和任務調度的開銷，單次的 latency 通常與同步 I/O 持平。

    (4) io_uring 支持 I/O polling 模式（如 IORING_SETUP_IOPOLL），對於 NVMe SSD，使用 polling 繞過 interrupt 的開銷可以獲得更低的 latency 與更高的效能。
