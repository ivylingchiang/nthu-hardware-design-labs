Write Amplification

SSD 的規格表上寫著「600 TBW」（Total Bytes Written）。如果你每天寫入 50 GB，算一下大約可以用 33 年，聽起來完全不用擔心。但這個計算有個致命的盲點：你以為你寫了 50 GB，NAND flash 實際承受的寫入量可能是 150 GB 甚至 500 GB。差距的來源就是 write amplification。

Write amplification factor（WAF）直接告訴你 SSD 的韌體和上層軟體一共浪費了多少額外的寫入。WAF 越高，SSD 的壽命越短、效能越差。問題在於，write amplification 不只來自 SSD 內部的 garbage collection，整個 storage stack 從應用層到韌體層都在製造額外的寫入。理解 WAF 的全貌，才能做出正確的系統設計決策。

Key Word Definition/ Discussion
WAF(Write Amplification Factor)

Write Amplification Factor (寫入放大率) 是衡量固態硬碟（SSD）或儲存系統寫入效率的關鍵指標。

WAF = 實際寫入 NAND flash 的資料量 / 應用程式要求寫入的資料量

理想：WAF = 1（Host 寫入 1 MB，NAND 實際只寫入 1 MB）。

實際：WAF 幾乎總是大於 1（典型值為 2 到 10，極端未最佳化情況可 > 20）。

理想情況下 WAF = 1，代表應用程式寫 1 MB，NAND flash 上恰好只寫了 1 MB。但實際上 WAF 幾乎總是大於 1，典型值在 2 到 10 之間，極端情況下可以超過 20。

需要注意的是，WAF 可以在不同層級來定義。有時我們只看 SSD 內部的 WAF（NAND writes / host writes to SSD），有時我們看整個 stack 的 WAF（NAND writes / application logical writes）。後者通常更大，因為中間的軟體層也會製造額外寫入。

整個系統 WAF 的計算

當我們要估算整個系統的 WAF 時，各層的放大效果是相乘的，不是相加的。例如：

系統層級寫入放大來源 (Sources)WAF 貢獻 (Typical)
Application LayerLSM-Tree compaction (e.g., RocksDB, Cassandra)10 ~30+
File System LayerFile system journaling (e.g., ext4, XFS metadata)1.5 ~ 2.0
Hardware LayerSSD Garbage Collection (GC) & Wear Leveling2.0 ~ 5.0

這代表應用程式每寫入 1 MB 的邏輯資料，NAND flash 上實際寫了 30 MB。這個數字聽起來很誇張，但在未經最佳化的 LSM-Tree workload 上並不罕見。這也是為什麼資料庫管理員會對寫入模式斤斤計較：選錯 compaction 策略、用錯 journaling 模式，一顆原本能撐三年的 SSD 可能一年就接近壽命上限。在大規模部署中，WAF 差 2 倍代表每年要多換數百顆 SSD，成本差異以百萬計。

GC overhead

GC 是 SSD 內部 WAF 最主要的來源。NAND flash 具有「Out-of-place write」（無法直接覆寫）的特性，必須先 Erase (抹除) 整個 Block 才能寫入新的 Page。當 SSD 空間不足時，GC 會介入：

  1. 讀出舊 Block 中仍然有效的資料 (Valid Pages)。
  1. 將這些資料搬移（寫入）到新的空白 Block。
  1. 抹除舊的 Block 以釋放空間。

這些搬移產生的寫入量完全是「額外」的，應用程式並沒有要求這些寫入。

GC 造成的 WAF 與 block 的 valid page ratio 直接相關。假設一個 block 有 256 個 page：

  • 如果只有 10 個 valid page（96% invalid）：搬移 10 個 page，回收 256 個 page 的空間。GC 的效率很高。
  • 如果有 200 個 valid page（22% invalid）：搬移 200 個 page，回收 256 個 page 的空間。GC 的效率極差，幾乎是 1:1 的搬移。

一個簡化的 GC WAF 估算公式是：WAF_gc = 1 / (1 - valid_ratio)

如果平均每個被回收的 block 有 50% 的 valid page（valid_ratio = 0.5），WAF_gc = 2。也就是說應用程式每寫 1 MB，GC 額外搬移的資料量也約為 1 MB，NAND flash 實際寫了 2 MB。

影響 Valid Ratio 的兩大因素：

  1. Over-provisioning 比例：OP 越大，SSD 有更多 free block 可以用，GC 不需要回收那些 valid page 比例高的 block，平均 valid ratio 較低，WAF 較小。
  1. Workload pattern：
    • Random Write (隨機寫入)：Invalid pages 均勻散佈，導致每個 Block 的 Valid ratio 都偏高，GC 效率極差。
    • Sequential Write (循序寫入) / Locality：集中更新特定 LBA，使特定 Block 快速累積 Invalid pages，大幅提升 GC 效率。

Journaling overhead

軟體層的 write amplification，在 SSD 之上，各種軟體層也會產生額外寫入。
為了保證斷電或崩潰時資料不損毀，軟體層通常會採用「寫兩次」的策略。

File System Journaling：

如 ext4 為了確保 crash consistency，會把每筆 metadata 修改（有時包括 data）先寫到 journal area，確認成功後再寫到正式位置。

  • data=journal 模式：Metadata 與 Data 都寫入 Journal，WAF ≥ 2。
  • data=ordered 模式（通常是預設）：只將 Metadata 寫入 Journal，WAF 較小，但仍大於 1。

Database WAL（Write-Ahead Log）：

與 journaling 類似，資料庫的 WAL 先把每筆 transaction 的修改寫入 log file，之後再寫入實際的 data page。這也是一種 write amplification。
Ex. 關聯式資料庫 (RDBMS) 必須先將 Transaction 的修改 Append 到 Log file，隨後才 Flush 到實際的 Data page。

Compaction

現代 Key-Value Store (如 RocksDB, LevelDB, Cassandra) 廣泛採用 LSM-Tree 以優化寫入速度（將 Random write 轉為 Sequential write），但代價是極高的背景 WAF。

LSM-Tree compaction：

RocksDB、LevelDB 等 key-value store 使用 LSM-Tree 結構。資料先寫入 memory 的 memtable，flush 到 disk 成為 Level-0 SSTable，然後經過多次 compaction 從 Level-0 合併到 Level-1、Level-2、...。每次 compaction 都需要讀出舊的 SSTable、合併、寫入新的 SSTable。一筆資料從被寫入到穩定存放在最底層，可能被 compaction 搬移 10-30 次。LSM-Tree 本身的 WAF 就可能高達 10-30 倍。

Reference:

Partial-stripe write

來自陣列層的 WAF：RAID Partial-Stripe Write

RAID partial-stripe write：

在 RAID-5 或 RAID-6 中，資料與 Parity (同位元檢查碼) 是以 Stripe 為單位橫跨多顆硬碟分布的。

Read-Modify-Write (RMW)：如果你的小檔寫入（如 4KB）不足以填滿一個完整的 Stripe，陣列控制器必須：

  1. Read 出舊的 Data。
  1. Read 出舊的 Parity。
  1. 計算新的 Parity。
  1. Write 入新的 Data。
  1. Write 入新的 Parity。

這被稱為 RAID 5 Write Penalty，一個小寫入動作會放大成底層硬碟的 4 次 I/O（2 讀 2 寫），大幅增加整體系統的 WAF 與 Latency。

SSD lifetime

NAND Flash 顆粒的壽命由 P/E Cycle (Program/Erase Cycle) 決定。隨著製程從 SLC、MLC 演進到 TLC 與 QLC，P/E Cycle 上限正在急遽下降（例如 TLC 通常在 1,000 到 3,000 次之間）。
廠商標示的 TBW (Total Bytes Written) 或 DWPD (Drive Writes Per Day) 是基於 Host 端寫入量，前提是廠商內部預設了一個平均 WAF 假設值。如果你的 Workload WAF 遠高於廠商的假設，SSD 會提早陣亡。

WAF 對 SSD 壽命的影響

SSD 壽命通常用 TBW（Total Bytes Written）或 DWPD（Drive Writes Per Day）來衡量。這些規格是基於寫入到 SSD interface 的資料量，但 NAND flash cell 真正承受的寫入量是這個數字乘以 WAF。

壽命計算範例：1 TB TLC SSD (假設極限為 3,000 P/E Cycles)

  • NAND flash P/E cycle 上限：3,000 次
  • 理論上 NAND flash 能承受的總寫入量：1 TB x 3,000 = 3,000 TB
情境 A (一般負載，WAF = 3)：
  • 使用者實際可寫入量 = 3,000 TB / 3 = 1,000 TB (1 PB)
情境 B (LSM-Tree 資料庫負載，WAF = 6)：
  • 使用者實際可寫入量 = 3,000 TB / 6 = 500 TB

這就是為什麼在選擇 SSD 和設計 storage stack 時，必須把 WAF 當成一個系統層級的指標來考量。你不能只看 SSD 的 TBW 規格就假設它能撐多久，還必須估算你的 workload 在整個 stack 中會產生多少 write amplification。

一個常見的最佳化思路是：在 host 端減少不必要的寫入。例如：

  • 使用 log-structured file system 減少 random write 造成的 GC 壓力
  • 調整 LSM-Tree 的 compaction 策略（例如 tiered compaction vs leveled compaction）
  • 對冷熱資料做分離，讓熱資料集中在少數 block 中，提高 GC 回收效率
  • 使用 TRIM/UNMAP 命令告知 SSD 哪些 LBA 已不再使用，讓 SSD 提前回收空間

要延長 SSD 壽命，必須從整個 Storage Stack 著手「減少不必要的寫入」與「提高 GC 效率」：

基礎建設層

  • 善用 TRIM / UNMAP 指令：

    作業系統刪除檔案時，發送 TRIM 指令通知 SSD 該 LBA 已失效，讓 SSD 提前回收空間，增加 Free Blocks，降低 GC WAF。

  • 增加 Over-Provisioning (OP)：

    在硬碟分割時故意留下一部分不格式化的空間（例如 10%-20%），讓 SSD 控制器有更多餘裕執行高效的 GC。

軟體與檔案系統層

  • Bypass File System Journaling

    對於已經有 WAL 機制的資料庫（如 MySQL 的 InnoDB），可以考慮關閉檔案系統的 Journaling，或使用 Direct I/O (O_DIRECT) 繞過 Page Cache，避免 Double Write。

  • Log-Structured File System (LFS)

    例如 F2FS (Flash-Friendly File System)，設計理念是將所有隨機寫入在記憶體中整合成循序寫入再落盤，完美契合 NAND flash 特性，大幅降低 GC 壓力。

應用與資料庫層

  • 調整 LSM-Tree Compaction 策略：
    • Leveled Compaction：讀取快、空間放大低，但 WAF 極高。
    • Tiered/Universal Compaction：WAF 較低（適合高寫入負載），但代價是較高的 Read Amplification (讀取放大) 與 Space Amplification (空間放大)。這是一個標準的架構 Trade-off。
  • 冷熱資料分離 (Cold/Hot Data Separation)：

    將頻繁更新的「熱資料」與幾乎不變的「冷資料」分開儲存，確保熱資料的 Block 可以快速累積 Invalid pages，最大化 GC 回收效率。

為什麼 random write workload 比 sequential write workload 造成更高的 GC WAF？請從 block 內 valid page 分佈的角度解釋。

Answer

隨機寫入會讓各個區塊內的無效資料分布零散，回收時須搬移大量有效資料；循序寫入通常能讓整塊區塊同時失效，不需搬移。

Key Concept

區塊內的有效頁面比例 (valid_ratio) 決定搬移成本。

Detail

循序寫入會按順序寫滿整個 Block，當這批資料被覆蓋時，往往一整塊 Block 會同時變成無效，GC 幾乎不需搬移資料就能回收。反觀隨機寫入，會在 SSD 的各個 Block 留下零星的有效資料碎片。當 GC 要回收空間時，被迫要把這些散落的有效頁面讀出並重寫到新區塊，產生大量額外寫入，推高 WAF。

一個系統同時使用 RocksDB（LSM-Tree WAF 約 15）和 ext4 data=journal 模式（WAF 約 2），跑在一顆 GC WAF 約 2 的 SSD 上。整體 WAF 大約是多少？如果把 ext4 改為 data=ordered 模式（WAF 約 1.2），整體 WAF 能降低多少？

Answer

初始總 WAF 為 60，改為 ordered 模式後總 WAF 為 36。
整體 WAF 降低了 24。

Key Concept

跨層級寫入放大的乘法效應。

Detail

系統的總體寫入放大是各層級 WAF 的乘積。
初始狀態總 WAF = 15 (RocksDB) x 2 (ext4 journal) x 2 (GC) = 60。
若將檔案系統改為 ordered 模式，總 WAF = 15 x 1.2 x 2 = 36。
因此，總體寫入放大數值降低了 60 - 36 = 24。

為什麼 TRIM/UNMAP 命令能降低 SSD 的 write amplification？它如何影響 GC 在選擇 victim block 時的效率？

Answer

TRIM 讓作業系統主動告知 SSD 哪些空間已刪除，SSD 可提前將這些頁面標記為無效，GC 就不必再浪費力氣搬移它們。

Key Concept

減少無謂的有效頁面搬移 (Valid Page Copy)

Detail

作業系統刪除檔案通常只是刪除索引，若沒有 TRIM，SSD 控制器仍會將這些實際上已作廢的資料視為「有效」。啟動 GC 時，SSD 會浪費寫入壽命去搬移這些垃圾。有了 TRIM，SSD 能精準識別無效頁面，讓 GC 選擇的 victim block 裡面的有效比例 (valid_ratio) 更低，大幅減少搬移成本並降低 WAF。

有人說「買大容量的 SSD 不只是多了空間，也延長了壽命」。從 over-provisioning 和 WAF 的角度解釋這句話為什麼成立。

Answer

大容量不僅提供了更多的實體抹寫總量，閒置的剩餘空間也變相增加了超額配置 (OP)，降低了 GC 的搬移負擔。

Key Concept

隱形超額配置 (Over-provisioning) 帶來的低 WAF 優勢。

Detail

首先，大容量代表總 NAND 顆粒多，(容量 * P/E cycle) 的物理總預算更大。其次，假設同樣存放 500 GB 的資料，在 2 TB SSD 上的有效資料佔比會遠低於 1 TB SSD。根據公式 WAF = 1 / (1 - valid_ratio)，較低的有效比例會讓 GC 非常容易找到接近空白的區塊來回收，WAF 會大幅下降。寫入放大降低加上總預算變大，壽命自然顯著延長。

    Answer

    導入積極的 Static Wear Leveling 機制，主動將佔據年輕 Block 的冷資料搬移至老舊 Block。

    解析:

    Static Wear Leveling 會主動把存放在低 P/E cycle block 上的冷資料搬到高 P/E cycle 的 block 上。這些額外的搬移操作雖然能讓所有 block 的磨損更加均勻，進而延長整體壽命，但代價就是必然會產生額外的內部寫入，直接推升 WAF。

    (1) 這個機制不會增加 WAF。Dynamic Wear Leveling 僅是在 GC 選擇 victim block 並搬移資料時，優先選擇 P/E cycle 較低的 block 作為目的地。這只是在「原本就必須執行 GC 寫入」的當下改變寫入位置，它不像 static Wear Leveling 會去搬移本來不需要動的資料 ，因此不會在物理層面上產生額外的內部寫入開銷。

    (3) 這個機制會大幅降低 WAF。若冷熱資料混雜，GC 為了回收極少數失效的熱資料，會被迫搬移大量同 Block 內的冷資料。若實作冷熱分離，裝滿熱資料的 Block 很快就會整塊自然失效（Invalid page 比例高），GC 在回收這些 Block 時幾乎不需要搬移任何 Valid pages，能有效降低 WAF。

    (4) 這個改變會降低 WAF。DFTL 雖然節省了 SRAM，在存取範圍遠大於 SRAM 緩存容量的隨機寫入負載下，會導致 Cached Mapping Table (CMT) 頻繁發生 Miss。這迫使控制器必須不斷將 Dirty Mapping Entry 寫回 NAND Flash (Eviction)，產生大量的 metadata 內部寫入。改用完整的 Page-level mapping 能徹底消除這部分的額外 WA。

    1. 確認作業系統的 TRIM 功能已啟用，使 SSD 能即時得知哪些 LBA 已被檔案系統釋放。
    1. 將檔案系統從 ext4 data=journal 模式切換為 data=ordered 模式，僅對 metadata 做 journaling。
    1. 將 GC 的 victim block selection 從 greedy 改為 cost-benefit 策略，選擇回收對象時同時考慮資料冷熱程度。
    1. 透過廠商工具將 over-provisioning 從 7% 提高至 28%，犧牲可用容量以增加 GC 緩衝空間。
    Answer

    將檔案系統從 ext4 data=journal 模式切換為 data=ordered 模式，僅對 metadata 做 journaling。

    解析:

    此措施對 device-level WAF 幫助最小。data=journal 會讓 host 將資料先寫入 journal、再寫入最終位置，造成 host-level 寫入放大（約 2×）。切換至 data=ordered 確實減少了 host 送給 SSD 的寫入量，但 device-level WAF 的定義是 NAND 實際寫入量 ÷ host 寫入量，其分母雖然縮小，GC 的內部搬移效率 （由 OP 空間、invalid page 分佈、victim 選擇策略等決定）並未改變。 這是 host-level 的優化，不直接影響 SSD 內部的 GC 行為與 device-level WAF。

    (1) 此措施有效降低 device-level WAF。未啟用 TRIM 時，SSD 無從分辨哪些 page 在檔案系統層已失效，GC 會將這些「邏輯上已死」的 page 當作 valid data 搬移， 白白增加內部寫入。TRIM 讓 SSD 能即時標記 invalid page，GC 直接跳過，WAF 下降。

    (3) 此措施有效降低 device-level WAF。Greedy 策略只選 invalid page 最多的 block， 但若該 block 內仍有大量頻繁更新的熱資料，搬移成本依然高昂。Cost-benefit 策略 同時評估「可回收空間（benefit）」與「需搬移的 valid page 數（cost）」， 傾向選擇冷資料多、不太可能自然失效的 block，減少不必要的內部搬移，直接降低 WAF。

    (4) 此措施有效降低 device-level WAF。更大的 OP 區域代表 GC 可用的空閒 Block 更多， Victim block 中平均 valid page 比例因此降低，每次 GC 需搬移的有效資料更少， 內部寫入量隨之下降，WAF 明顯改善。

  1. 某企業儲存系統同時處理頻繁更新的交易紀錄 (Hot data) 與幾乎不修改的歷史封存檔案 (Cold data)。最初，這兩種資料被混合寫入 SSD 的同一個 Erase Block 中，導致系統的 GC 寫入放大 (WAF) 居高不下。

    1. 集中存放的 Hot block 內的資料會迅速被多次覆寫而失效，導致該 Block 的 valid_ratio（有效頁面比例）極低。當 GC 挑選這些 Block 作為回收對象時，幾乎不需要搬移 (Copy-forward) 任何有效資料即可回收一整塊空間。由於被回收的 Block 其 valid_ratio 趨近於 0，根據公式計算，WAF_{gc} 就會自然逼近於理想值 1。
    1. 冷熱交替的混合寫入會迫使 SSD 控制器放棄高效率的 Page-level mapping，動態降級使用 Block-level mapping。冷熱分離能讓 SSD 恢復 Page-level mapping，從而將 WAF 從 O(N) 降回 O(1)。
    1. 將冷資料獨立出來後，Cold block 會長期保持極高的 valid_ratio（接近 100%）。根據公式 
      WAFgc​=1/(1−valid ratio)，當 valid_ratio 數值越高時，分母越小，計算出來的 WAF 值就會越低，從而成功拉低了系統整體的平均寫入放大。
    Answer

    集中存放的 Hot block 內的資料會迅速被多次覆寫而失效，導致該 Block 的 valid_ratio（有效頁面比例）極低。當 GC 挑選這些 Block 作為回收對象時，幾乎不需要搬移 (Copy-forward) 任何有效資料即可回收一整塊空間。由於被回收的 Block 其 valid_ratio 趨近於 0，根據公式計算，WAF_{gc} 就會自然逼近於理想值 1。

    解析:

    這是正確的。根據講義，GC 造成的 WAF 與 Victim block 的 valid page ratio 直接相關。如果冷熱資料混寫，Block 內總是會殘留那些「不會被更新的 Cold data」，導致 valid_ratio 卡在中間（例如 0.5），計算出的 WAF_{gc} = 2。實施冷熱分離後，Hot block 會迅速充滿 invalid pages（valid_ratio 降至接近 0）；而 Cold block 則充滿 Valid pages 且不會被 GC 挑中。GC 專挑 Hot block 下手，搬運成本極低，大幅降低了整體的寫入放大。

    (1) 這混淆了多個名詞的定義。首先，TRIM 是作業系統用來通知 SSD「刪除無效資料」的指令；Cold data 是「有效但少更新」的歷史檔案，作業系統絕不會對其發送 TRIM 刪除。再者，冷熱分離本身並不會無中生有地增加硬體的實體 OP 空間總量。

    (3) 這是對 FTL 架構的錯誤認知。現代 SSD 的 FTL 映射層級（如混合式的 DFTL）是硬體/韌體出廠時就決定好的，不會因為資料冷熱混寫就「動態降級」成純 Block-level mapping。WAF 的改善純粹來自 GC 挑選 Victim block 時的有效頁面比例 (valid ratio) 改變，與映射架構切換無關。

    (4) 這是一個嚴重的數學與邏輯迷思。根據公式 WAF_{gc} = 1 / (1 - valid\_ratio)，當 valid_ratio 越高（例如接近 0.99 時），分母會變成 0.01，計算出的 WAF 會飆升至 100（極度惡化）。實際上，GC 演算法會刻意避開去回收高 valid_ratio 的 Cold block，而是專攻低 valid_ratio 的 Hot block 來降低搬運成本。

    這個 600 TBW 是廠商在特定測試條件（含特定 Write Amplification Factor）下得出的標示值。實際使用中，不同 workload 會產生不同的 Write Amplification Factor，因此實際可寫入量可能與標示值有顯著差異。

    解析:

    正確。從公式可知 Write Amplification Factor 位於分母，直接影響 TBW 的大小。廠商依據標準測試工作負載測出特定的 Write Amplification Factor 再算出 TBW。但使用者的實際 workload 可能產生不同的 Write Amplification Factor，導致實際可寫入量與標示值有差異。

    (1) Write Amplification Factor 並非固定常數，它受到寫入模式、OP 比例、GC 策略、是否啟用 TRIM 等多種因素影響，不同 workload 可以產生截然不同的數值。

    (3) TBW 是廠商在特定測試條件下的保固耐久規格，不是精確的死亡線。許多 SSD 在超過標示 TBW 後仍可繼續運作，也可能因其他因素在未達 TBW 前就發生問題。

    (4) 恰好相反。公式的分子是 NAND 能承受的總實體寫入量，但除以 Write Amplification Factor 後，得到的 TBW 是 host 端能寫入的邏輯資料量。因此 600 TBW 指的是 host 端的寫入上限估計值。

  1. 在一顆廠商預設 7% over-provisioning 的消費級 SSD 上，使用者將可用空間近乎寫滿並進入 steady state 後，陸續刪除了約 30% 的檔案。然而 host 端並未對這顆 SSD 發送任何 TRIM 指令。在這種情況下，若使用者繼續對該 SSD 進行寫入，最可能觀察到什麼現象？
    1. 沒有 TRIM 只會影響讀取效能，因為 SSD 需要額外查詢 mapping table 確認哪些 page 已被刪除，但對寫入效能和 WAF 沒有影響。
    1. 沒有 TRIM 的影響僅限於安全性層面（已刪除的資料仍可被還原），對 SSD 的效能和壽命沒有任何影響。
    1. SSD 的 GC 在回收 block 時，仍然會搬移那些已被 host 刪除但 SSD 仍視為 valid 的 page，導致 WAF 相較有發送 TRIM 的情況顯著上升。
    1. 沒有 TRIM 不影響 GC 的效率，因為 GC 的 victim block selection 只取決於 block 內的 invalid page 比例，而刪除檔案後這些 page 會自動變成 invalid。
    Answer

    SSD 的 GC 在回收 block 時，仍然會搬移那些已被 host 刪除但 SSD 仍視為 valid 的 page，導致 WAF 相較有發送 TRIM 的情況顯著上升。

    解析:

    正確。當檔案被刪除時，host 端只在自身層面處理了刪除操作，但不一定會通知 SSD。在本題的情境中 host 未發送 TRIM，因此 SSD 的 controller 無從得知哪些 page 上的資料已不再被需要，仍將其視為 valid data。GC 在回收 block 時會將這些「在 host 端已不存在但 SSD 仍認為有效」的 page 搬移到新的 block，產生無意義的額外寫入，推高 WAF。在低 over-provisioning 且高空間利用率的條件下，這個效應尤其嚴重，因為 GC 被迫更頻繁啟動，且每個 block 的 valid page ratio 被這些不必要的資料墊高。

    (1) SSD 的 mapping table 記錄的是 LBA 到 physical page 的對應關係，不具備判斷資料是否仍被 host 需要的能力。沒有 TRIM 時，SSD 根本不知道哪些資料已被刪除，不存在「額外查詢」的問題。TRIM 的主要影響在於寫入端：它讓 GC 能跳過已刪除的 page，減少不必要的搬移，從而降低 WAF。

    (2) TRIM 確實與資料安全性有關：未經 TRIM 處理的已刪除資料在 NAND 中仍然完整存在，可能被還原。但這不是 TRIM 唯一的作用。TRIM 對效能和壽命有直接影響：它讓 SSD 提前知道哪些 page 不再需要，使 GC 在回收 block 時能跳過這些 page，降低搬移量與 WAF，進而減少 NAND 的實體磨損並提升寫入效能。

    (4) 刪除檔案後，對應的 physical page 不會自動變成 invalid。在 SSD 的視角中，一個 page 變成 invalid 只有兩種途徑：該 LBA 被新資料覆寫（out-of-place write 使舊 page 失效），或收到 TRIM 指令。單純的檔案刪除只發生在 host 端，SSD 完全不知情，因此這些 page 仍被視為 valid。
