Slotted Page Layout

在 Indexing 單元中，我們要理解 B+Tree 與 LSM-Tree 等 indexing 結構如何在磁碟上高效地組織資料。但在討論這些巨觀結構之前，我們需要先瞭解單一 disk page 內部的資料是怎麼擺放的。

Given 一個固定大小（例如 8 KB）的空白 page。我們要往裡面塞入多筆長度不一的 record，同時滿足三個需求：

  1. 能快速找到任一筆 record
  1. 刪除或更新 record 後能回收空間
  1. 外部持有的 record 參照不會因為 page 內部的搬移而失效。

Slotted page 用一個三層結構同時解決了這三個問題：page header 記錄 page-level metadata（如 free-space offset、slot count），slot array 從 page 前端往後成長，每個 slot 是一組 (offset, length) 指向對應 record 的位置，而 record 資料（heap area）則從 page 尾端往前堆疊。一個向後長，一個向前長，中間的空隙就是可用空間。

這種資料結構，讓外部只需要記住「page ID + slot number」就能找到一筆 record，而 page 內部可以自由搬移 record（例如做 compaction 來消除 fragmentation），只要更新 slot array 中的 offset 即可。瞭解這個機制後，你會發現它在後續的 B+Tree leaf node、heap file、甚至 WAL record 中反覆出現。

Key Word Definition/ Discussion
Slotted page

在磁盤數據庫（Disk-based DB）中，數據是以 Page（頁） 為最小單位進行管理的（通常為 8 KB）。當資料列（Record/Tuple）長度不固定時，如何高效地在 Page 內定位、插入、刪除並保持外部引用的穩定，是 Slotted Page 設計的核心目標。
Slotted Page 是為了妥協 Variable-length（變長資料） 與 Performance（性能） 的最優解。

假設你在 PostgreSQL 裡面有一張學生資料表：

CREATE TABLE students (
    student_id  CHAR(7),        -- 固定 7 字元，如 '1131456'
    name        VARCHAR(50),    -- 最長 50 字元，實際長度不定
    department  VARCHAR(30)     -- 最長 30 字元，實際長度不定
);

student_id 是 CHAR(7)，固定長度。如果整張 table 的每個欄位都是固定長度，事情就很簡單：每筆 record 大小一樣，你只要把一個 page 切成等大的格子，像 array 一樣用 index 乘以 record size 就能算出任何一筆 record 的位置。

但 name 和 department 是 VARCHAR，長度不固定。'Nini' 佔 4 bytes，'Capoo' 佔 5 bytes，'CS' 佔 2 bytes，'PHYS' 佔 4 bytes。每筆 record 大小不同，你沒辦法用簡單的 array indexing 來定位了。更麻煩的是，這些 record 要塞進一個固定大小（例如 8 KB）的 disk page 裡面，而且你還需要能刪除、更新、回收空間，外部持有的 pointer 不能因為 page 內部搬移而失效。

這就是 slotted page layout 要解決的問題。它是幾乎所有 disk-based database 在 page 層級的標準做法，從教科書到 PostgreSQL、MySQL InnoDB、SQLite，都是同一個核心思路。連檔案系統 (btrfs) 也是這樣設計!!

Insert、Delete、Update 怎麼運作

Insert：在 slot array 末端新增一個 slot（pd_lower 往後推 4 bytes），在 heap area 前端放入 record 資料（pd_upper 往前推 record 長度）。如果 pd_lower 和 pd_upper 之間剩餘空間不夠，這個 page 就放不下了，需要去找別的 page 或申請新 page。

Delete：把對應 slot 標記為 "unused"（PostgreSQL 的做法是把 ItemIdData 的 length 設為 0），但 record 的資料不會立刻被清除，heap area 裡會留下一個 hole。這是因為立刻回收的成本太高，你得把後面的 record 往前搬，還要更新所有受影響的 slot。

Update：對 variable-length record 來說，update 可能改變 record 的大小。如果新的 record 比原來的大，原位放不下。所以很多系統的做法是把 update 當成 delete + insert：舊 record 標記刪除，新 record 插入到 heap area 的新位置，更新 slot 裡的 offset。PostgreSQL 更進一步，舊 record 不會立刻被刪掉。為什麼？因為可能有其他使用者正在讀取這筆資料的舊版本，如果馬上清掉，別人讀到一半就斷了。所以 PostgreSQL 會先留著舊 record，等到確定沒有人再需要它的時候，再由背景的清理程序（叫 VACUUM）統一回收空間。

MVCC 關聯： 在 PostgreSQL 中，Update 產生的舊版本 Record 不會被立即覆蓋，是為了支援多版本並行控制（MVCC），讓讀取者能讀到舊快照。

Fixed-length (固定長度): 像 Array。定位第 $i$ 筆 Record 只需要 $Base + i \times Size$。不需要 Slot Array，速度極快。Variable-length (變長長度): 包含 VARCHAR、TEXT、NULL 值（不佔空間）。由於每筆大小不同，必須有「地圖」（Slot Array）引導。

PostgreSQL 的實作細節

  1. PageHeaderData（24 bytes）：pd_lsn、pd_checksum、pd_lower、pd_upper、pd_special 等
  1. ItemIdData array：每個 4 bytes，從 byte 24 開始往後長
  1. Free space：pd_lower 到 pd_upper 之間
  1. Heap records：從 page 尾端往前長，每筆 record 包含 23 bytes header + null bitmap + user data
  1. Special space：B-Tree index page 會用到（存 sibling page link），普通 heap page 不使用

一個具體的數字感受：假設平均 record 大小是 100 bytes（含 header），一個 8 KB page 扣掉 24 bytes page header，剩 8168 bytes。每筆 record 需要 100 bytes data + 4 bytes slot = 104 bytes。大約能放 8168 / 104 = 78 筆 record。如果 record 更大（例如 500 bytes），一個 page 只能放 8168 / 504 = 16 筆。

PostgreSQL 的 ItemIdData 一旦分配了 slot number，即使 record 被刪除，這個 slot 位置也不會被其他 record 搶走（除非做完整的 page 重建）。這是因為外部可能還有 index entry 或其他 record 的 CTID 指向這個 slot number，貿然重用會導致 dangling pointer。

Pitfall:

空間碎片化： 即使 pd_lower 到 pd_upper 之間有 500B，但若中間夾雜了已刪除的「洞」，物理上可能不連續，導致無法直接插入 400B 的 Record。這需要靠 Compaction 解決。

Update 失敗： 即使 Table 還有空間，但若該 Page 的 Free Space 不足以容納 Update 後變大的 Record，該 Record 可能會觸發「跨頁搬移」，這會產生複雜的鏈接問題。

Overhead: 對於純整數（Integer）構成的表，Slotted Page 的 Slot Array 和 Record Header 其實佔用了近 30% 的空間開銷。這也是為什麼一些專門處理數字的 OLAP（分析型）數據庫會採用不同的 Columnar Storage（列式存儲）。

Page header & Slot array & Heap area

Slotted Page 是一種將固定大小的 Page 劃分為三個主要區域的佈局方式：Page Header、Slot Array（Line Pointers）、以及 Heap Area。其特徵是 Slot Array 與 Heap Area 從兩端向中間「對沖」成長。

三層結構：Header、Slot Array、Heap Area

  • Page Header (頁標頭): 存放 Metadata。包含 LSN（日誌序列號）、Checksum（校驗和）、以及最重要的兩個指針：
    • pd_lower: 指向 Slot Array 的末端（下一個 Slot 要放的位置）。
    • pd_upper: 指向 Heap Area 的前端（下一筆 Record 要放的位置）。
  • Slot Array (槽位數組): 由固定大小的單元組成（如 Postgres 為 4 bytes）。記錄每筆 Record 在頁內的 Offset（偏移量） 和 Length（長度）。
  • Heap Area (堆積區): 實際存放 Data Record 的地方。從頁尾（Page Bottom）開始往前堆疊。
  • Free Space: pd_lower 與 pd_upper 之間的間隙。當兩者相撞時，代表 Page 已滿。

Header 裡面最重要的兩個欄位是 free-space pointer：一個指向 slot array 的末端（下一個 slot 要放的位置），另一個指向 heap area 的前端（下一筆 record 要放的位置）。當這兩個 pointer 撞在一起，page 就滿了。

以 PostgreSQL 為例 (就一個栗子而已，不用背喔！)，它的 page header（叫 PageHeaderData）佔 24 bytes，裡面裝：

  • pd_lsn（8 bytes）：最後一筆修改這個 page 的 WAL record 的 LSN，用於 crash recovery
  • pd_checksum（2 bytes）：page 層級的 checksum，防止 bit rot
  • pd_lower（2 bytes）：指向 free space 的起始位置（slot array 末端）
  • pd_upper（2 bytes）：指向 free space 的結束位置（heap area 前端）
  • pd_special（2 bytes）：指向 special space 的起始位置，給 index page 用的（普通 heap page 沒有 special space）
  • 其餘欄位記錄 page size、版本、flags 等

每個 slot（PostgreSQL 叫 ItemIdData）佔 4 bytes，記錄對應 record 的 byte offset 和長度。所以一個 8192 bytes 的 page，扣掉 24 bytes header，理論上最多能放 (8192 - 24) / 4 = 2042 個 slot，當然實際上 record 本身也要佔空間，所以不可能到這個上限。

free-space pointer

Free-space Pointer 是 Page Header 中的兩個關鍵偏移量（Offset），在 PostgreSQL 中分別稱為 pd_lower 和 pd_upper。它們劃定了 Page 中間那塊連續的、尚未分配過的空間邊界。

這是一對「對沖」的指針：
• pd_lower (下界指針)： 指向 Slot Array (Line Pointers) 的末端。當有新的 Record 插入時，會在這裡新增一個 Slot，pd_lower 隨之向後（增大）移動。
• pd_upper (上界指針)： 指向 Heap Area (Data) 的前端。當有新的 Record 插入時，數據會寫入此處，pd_upper 隨之向前（減小）移動。
• Free Space 計算： 該 Page 物理上剩餘的連續空間大小 = pd_upper−pd_lower。

數據庫透過這兩個指針的距離，來判斷該頁是否還有能力承載新的數據。

插入時 (Insert)： 系統檢查 pd_upper−pd_lower 是否大於 (新 Record 大小 + 新 Slot 大小)。空間分配： 若空間足夠，Slot 從 pd_lower 往後長，Data 從 pd_upper 往前長。

碰撞 (Collision)： 當兩者相遇，代表「物理連續空間」已耗盡。即使 Page 內部有因為 Delete 產生的「洞（Holes）」，只要這兩個指針撞在一起，就無法直接進行簡單插入。

Free-space 指針只負責標示「中間那塊大空地」，它們不記錄因為 Delete 或 Update 產生的內部碎片（Holes）。

當一筆 Record 被刪除時：

  • 對應的 Slot 會被標記為 Dead。
  • pd_upper 不會往回退（因為往回退會弄亂其他 Record 的位置）。
  • 此時，Page 會出現「有效空間」大於「指針定義的 Free Space」的情況。

Pitfall:

虛假全滿 (False Full)： 有時候 pd_upper−pd_lower 很小，看似 Page 滿了，但其實 Page 內部可能有一半的空間都是刪除後的「洞」。

解決方案： 這時需要觸發 Page Compaction。系統會把所有活著的 Record 重新往後推，重置 pd_upper，讓 pd_upper 與 pd_lower 之間重新出現一大塊連續空間。

Record indirection

外部索引（Index）或指針不直接指向 Record 的物理地址，而是指向 (Page ID, Slot Number)。Slot Number 就像一個房間號碼，而 Record 是裡面的住客。

Slot Indirection：穩定的 Record 地址

這層 slot array 的存在不只是為了「找到 record 在哪」，更重要的是提供一層 indirection。

外部要引用某筆 record 的時候，用的是 (page ID, slot number) 這個組合。PostgreSQL 把它叫做 CTID（Current Tuple ID），格式是 (blockNumber, itemIndex)。這個 identifier 是穩定的：只要 record 還在同一個 page 裡，不管它在 page 內部被搬到哪個位置，slot number 都不會變，只是 slot 裡面記錄的 offset 會更新。

這很重要喔！因為 B+Tree 的 leaf node 裡存的就是這種 (page ID, slot number) 的 pointer。如果沒有 slot indirection，page 內部做任何 record 搬移（例如 compaction），都要回去更新所有指向這些 record 的 index entry，成本極高。有了 indirection，page 內部搬移 record 只需要更新自己的 slot array，外部的 pointer 完全不受影響。

  • CTID (PostgreSQL 術語): 格式為 (blockNumber, itemIndex)。
  • 穩定性： 即使 Record 在 Page 內部因為空間清理而搬移了位置（Offset 改變），它的 Slot Number 依然保持不變。
  • 解耦（Decoupling）： 這是數據庫物理獨立性的關鍵。如果沒有這層 Indirection，每次 Page 內部整理碎片，所有的 B+Tree 索引都要跟著更新地址，這會導致系統崩潰（Write Amplification）。

Pitfall:

Slot 重用危機： 在 Postgres 中，一旦 Slot 被分配，除非執行 VACUUM FULL，否則該 Slot Number 不會被回收給全新的 Record 使用，以避免 Dangling Pointer（懸空指針） 指向錯誤的資料。

variable-length record

define

超適合 Variable-Length Record

如果所有 record 長度都一樣（fixed-length），其實不需要 slotted page 這麼複雜的設計。你只要把 page 切成等大的 slot，用 slot number 乘以固定大小就能直接算出 offset，連 slot array 都省了。

但真實世界的資料幾乎都是 variable-length 的：VARCHAR 欄位、TEXT 欄位、nullable column（null 不佔空間 vs. 佔空間的差異）、甚至一張 table 經過 ALTER TABLE ADD COLUMN 之後新舊 row 的長度都不同。

Slotted page 不預設 record 有固定大小。代價是每筆 record 需要額外 4 bytes 的 slot 空間，而且存取 record 要先查 slot array 才能拿到實際位置（多一次 memory access）。對於 fixed-length record 的 workload，這個 overhead 是浪費，但對於 variable-length 的一般場景，這個設計的彈性遠超過 overhead 的代價。

PostgreSQL 的 heap record 本身就是 variable-length 的：每筆 record 有 23 bytes 的 header，接著是 null bitmap（每個 column 1 bit），最後才是實際的 user data。不同 record 的 column 數量和 null pattern 都可能不同，長度自然也不同。

Page compaction

當 Page 內部「洞」太多導致空間不連續時，重新排列 Heap Area 的過程。

Compaction：釋放洞洞

經過多次 delete 和 update 之後，heap area 裡面會出現很多 hole。總剩餘空間可能還很多，但沒有一段連續的空間夠大到塞得下新 record。這時候就需要 compaction（有些系統叫 defragmentation）：把 heap area 裡所有存活的 record 重新排列壓緊，把洞洞填滿、整併成一整塊連續的 free space。

Compaction 的好處在於：record 被搬移了，但 slot number 不變。Compaction 只需要更新每個 slot 裡面的 offset 值。所有外部用 (page ID, slot number) 引用這些 record 的 pointer 完全不受影響。這就是 slot indirection 設計最大的好處。

PostgreSQL 在什麼時候做 compaction 呢？當一個 page 的 free space 不夠放新的 record，但 page 裡有已經沒人需要的舊 record 時，PostgreSQL 會順手做一次 page pruning：把這些廢棄 record 清掉並壓縮 heap area，騰出空間給新 record。這個動作是在 INSERT 或 UPDATE 的時候順便觸發的，不用額外等背景清理。

  • 運作流程： 將所有存活的 Record 重新推向頁尾排整齊，合併所有碎片空間，並更新 Slot Array 中對應的 Offset。
  • 觸發時機： 通常在 Insert 空間不足，但計算發現「總剩餘空間（含洞）」足夠時，自動觸發 In-place Compaction。
  • Compaction vs. Vacuum:
    • Compaction: 頁內整理，不改變 Slot Number。
    • Vacuum: 掃描全表，標記哪些 Slot 真的沒人用了，回收空間給 OS 或後續使用。

Pitfall:

性能損耗： 頻繁的 Compaction 會消耗 CPU 並鎖定 Page。如果資料頻繁變動且長度落差大，容易造成 IO 瓶頸。

Insert 消耗中間的 Free Space；

Delete 只標記 Slot 無效並留下資料空洞 (Hole)；

Detail

為了效能，Delete 不會立刻挪動其他資料來填補空隙（因為搬移資料的 I/O 與 CPU 成本極高），這會導致 Heap Area 中出現無法立即使用的「碎片/空洞」。當 Page 剩餘的連續 Free Space 不足以容納新的 Insert，但「空洞總和」其實足夠時，系統就會觸發 Compaction，將所有存活的紀錄重新往底部壓緊，合併出連續的 Free Space 供新資料使用。

說明這個 page layout 為什麼天然適合 variable-length record，以及它與 fixed-length record 的 page layout 相比，在空間利用與存取效率上有什麼取捨

Answer

Slotted Page 能精確儲存變長資料不留白，但有 Slot 開銷；

Fixed-length 存取極快無碎片，但處理變長資料會嚴重浪費空間。

Key Concept

Variable-length Record, Fixed-length Record, Internal Fragmentation, Overhead vs. Speed。

Detail

空間利用：如果資料包含 VARCHAR，Slotted Page 依實際長度儲存，完美契合；Fixed-length 則必須以最大可能長度預留空間，產生嚴重的「內部碎片」。

存取效率：Fixed-length 像陣列一樣，位址可透過公式 $Base + (i \times RecordSize)$ 在 $O(1)$ 時間內直接算出；Slotted Page 則必須先讀取 Header，再讀取 Slot 取得 Offset，多了一層記憶體跳轉開銷（Overhead）。

Answer

PostgreSQL 完全採用此設計，其 Header 為 PageHeaderData，Slot 稱為 ItemId，中段的可用空間由 pd_lower 和 pd_upper 界定。

Key Concept

PageHeaderData, ItemIdData, pd_lower / pd_upper.

Detail

在 Postgres 原始碼中，pd_lower 指針標記了 Slot Array 的尾端（往下長），pd_upper 標記了 Heap Tuple 的頂端（往上長）。兩者之間的空間就是未分配的 Free Space。這個經典架構是支撐 Postgres 實作 MVCC（多版本並行控制）與變長欄位（TOAST）的重要基石。

為什麼 slotted page 要讓 slot array 和 heap area 從 page 的兩端相向成長，而不是把 slot array 和 record 資料放在一起、依序往同一個方向成長？

Answer

同向成長會導致新增資料時，必須挪動後方所有資料才能擴充 Slot 陣列，缺乏動態彈性。

Key Concept

Dynamic Memory Allocation, Array Resizing Penalty。

Detail

假設 Slot Array 和 Record 連續存放在一起並同向生長（如：Slot1, Slot2, Data1, Data2）。當你要插入 Data3 時，為了在陣列區新增 Slot3，你必須把 Data1 和 Data2 的實體位置全部往後推移。這種設計的搬移成本是災難性的。相向成長讓陣列與資料各安其位，互不干擾，完美解決了這個問題。

假設一個 PostgreSQL 8 KB heap page，page header 佔 24 bytes，每個 slot 佔 4 bytes，平均 record 大小（含 record header）是 200 bytes。這個 page 最多能放幾筆 record？
如果其中 20% 的 record 被 delete 但還沒被背景清理程序回收，實際可用的 free space 剩多少？

Answer

此 Page 最多能放 39 筆。若 20% 被刪除但未回收，可用的「連續 Free Space」約為 8 bytes，刪除產生的空間暫時無法供新紀錄分配。

Key Concept

8192 Bytes Alignment, Tuple Overhead, Usable Free Space vs. Dead Space。

Detail

  • 總容量：8 KB = 8192 bytes。扣除 Header (24 bytes) = 8168 bytes 可用。
  • 單筆開銷：200 (Record) + 4 (Slot) = 204 bytes。
  • 最多筆數：8168 / 204 = 40.03。考量到記憶體對齊，實務上最多容納 39 或 40 筆（以 40 筆計，佔用 8160 bytes，剩 8 bytes 真正連續的 Free Space）。
  • 刪除 20%：刪除 8 筆紀錄。這會在 Heap Area 產生 1600 bytes 的「空洞 (Dead Space)」。但在背景程序（VACUUM）或 Compaction 介入前，這些空間是不連續且未被標記為可重用的。因此系統眼中的「可立即分配的連續 Free Space」依舊只有那 8 bytes。

一個 B+Tree leaf node 裡存了指向 heap page 的 CTID (42, 7)。如果 page 42 做了 compaction，把所有 record 重新排列壓緊，這個 CTID 還能正確找到目標 record 嗎？為什麼？

Answer

能正確找到。因為 Compaction 只改變資料的實體位置，不會改變 Slot 的序號。

Key Concept

Stable Reference, Indirection Layer。

Detail

CTID (42, 7) 代表第 42 頁的第 7 個 Slot。Compaction 的運作邏輯是把 Heap 裡的資料重新排緊，然後把新的位址（Offset）更新回第 7 個 Slot 裡面。從外部透過 CTID (42, 7) 存取時，依然會先讀取第 7 個 Slot，進而拿到最新的正確實體位址。這正是 Slot Indirection 設計的精髓。

PostgreSQL 在 UPDATE 時不會立刻刪掉舊版本 record（因為可能有其他人還在讀）。從 slotted page 的角度，這對 page 內部的空間利用有什麼影響？為什麼需要一個背景清理程序來回收這些空間？

Answer

會導致 Page 快速累積無效的舊資料（Bloat/膨脹），因此需要 VACUUM 掃描並回收這些空間。

Key Concept

MVCC (Multi-Version Concurrency Control), Page Bloat, VACUUM, Dead Tuple。

Detail

Postgres 的 UPDATE 實質上是「標記舊版本失效，並 INSERT 新版本」。如果某筆資料被頻繁更新，同一個 Page 內就會堆滿這筆資料的歷史版本（Dead Tuples）。這會嚴重浪費空間，並拖慢循序掃描的效能（Page Bloat）。因此必須依賴 VACUUM 背景程序，定期識別出已經沒有活躍 Transaction 會看見的舊版本，並將其 Slot 標記為可用，讓新資料能夠覆蓋上去。

在什麼樣的 workload 下，fixed-length record 的簡單 page layout 會比 slotted page 更有優勢？請從空間利用率和存取效率兩個角度分析。

Answer

資料長度完全固定，且需要極高吞吐量的循序/隨機讀寫場景下更有優勢（例如感測器時序數據、金融 Log）。

Key Concept

Predictable Offset, O(1) Direct Access, Zero Indirection Overhead。

Detail

  • 空間利用率：如果所有紀錄都是固定的 64 bytes，那就不需要 Slot Array 來記錄動態 Offset。每筆紀錄省下 4 bytes 的 Slot 空間，在海量資料下能省下極大儲存成本。
  • 存取效率：CPU 可以透過簡單的指標運算直接跳轉到目標紀錄，避開了讀取 Slot 陣列所帶來的記憶體存取延遲（Cache Miss 風險）。這在需要極限效能且結構單純的系統中（如部分 In-Memory DB 或特定時序資料庫）是非常大的優勢。

Quiz Pool
  1. 某個資料庫系統使用 8 KB slotted page 來存放 heap records。page header 為 24 bytes， 每個 slot 為 4 bytes。某個 page 已經插入多筆 variable-length records。之後發生以下事件：
    1. slot 3 與 slot 6 的 record 被 DELETE，但尚未被 VACUUM 或 page pruning 回收
    1. slot 5 的 record 被 UPDATE，新的版本因為變大，無法原地覆寫，所以新版本被搬到 page 內另一個位置， 而 slot 5 改為指向新位置
    1. 接著系統想插入一筆新的 300-byte record，卻發現雖然 page 裡有不少刪除後留下的洞洞，仍然可能插不進去

    問：下列哪一個敘述最正確？

    1. Slotted page 的主要目的只是讓 variable-length record 比 fixed-length record 更省空間，與 pointer 穩定性無關。
    1. DELETE 掉 slot 3 和 slot 6 後，這兩個 slot 會立刻消失，因此 slot array 變短，free space 直接增加。
    1. 即使 page 內總空間看起來夠大，只要 free space 被切成不連續的碎片，新 record 仍可能插入失敗；這正是 compaction 或 pruning 要處理的問題。
    1. UPDATE slot 5 後，因為 record 搬家了，所以所有指向該 record 的 CTID 都必須更新，否則 index 會失效。
    Answer

    即使 page 內總空間看起來夠大，只要 free space 被切成不連續的碎片，新 record 仍可能插入失敗；這正是 compaction 或 pruning 要處理的問題。

    解析:

    對。這題考的是 fragmented free space 和 contiguous free space 的差別。 洞洞很多，不代表有一塊夠大的連續空間可放新 record。

    (1) 錯。Slotted page 的核心價值之一就是 slot indirection，讓 page 內部搬動 record 時，外部的 (page id, slot number) 仍然穩定。

    (2) 錯。DELETE 通常只會把 slot 標成 unused 或 dead，slot 本身不會立刻移除， slot array 也不會直接縮短。

    (4) 錯。外部通常存的是 (page id, slot number)。只要 slot 5 還在， 更新 slot 裡的 offset 即可，不需要改所有外部引用。

  1. 在高效能資料庫引擎（如 PostgreSQL 或 MySQL InnoDB）中，關於 Slotted Page Layout 處理 Variable-length records 與頁面維護的細節，下列敘述何者正確？
    1. 在執行頁面重組（Page compaction）時，為了保證外部指標的有效性，Slot Array 的大小與其在 Page Header 中的索引位置必須保持不變，即便中間存在因刪除而產生的空槽（Empty slots）
    1. 當 Slot Array 空間不足以容納新的 Slot 指標時，系統會動態調整 Page Header 的起始位址或縮小 Header 固定欄位，以騰出空間給 Slot Array 使用。
    1. Free-space pointer 始終指向 Slot Array 結束位置與 Heap Area 開始位置之間的「絕對中點（Absolute Midpoint）」，以平衡兩端增長的壓力。
    1. 當頁面內的一條 record 被刪除後，為了防止 External Fragmentation，Free-space pointer 會立即更新並觸發該 record 後方所有數據的位移，以確保剩餘空間始終是物理連續的。
    Answer

    在執行頁面重組（Page compaction）時，為了保證外部指標的有效性，Slot Array 的大小與其在 Page Header 中的索引位置必須保持不變，即便中間存在因刪除而產生的空槽（Empty slots）

    解析:

    如果 Compaction 時移動了 Slot Array 的順序，所有外部索引都會失效。因此，Compaction 僅在 Heap Area 進行物理碎片的整理，並更新 Slot Array 中對應的 Offset 值。被刪除的 Slot 會被標記為「可重用」，但在該 Slot 被新紀錄覆蓋前，它的位置必須保留。

    (2) Page Header 的大小在分頁初始化時是固定的。 Slot Array 緊接在 Header 之後向後增長，而資料紀錄（Heap）從頁尾向前增長。當兩者相撞時，代表頁面已滿。Header 本身其位置與大小不可變動，否則硬體對齊與解析會出錯。

    (3) 這是一個錯誤的假設。Free-space pointer 通常指向 Heap Area 的頂端（最新寫入紀錄的邊界）。Slot Array 與 Heap Area 並非對稱增長：Slot Array 每次增加一個固定大小的指標，而 Heap Area 每次增加一塊變長的資料。指針的作用是標註「下一次寫入資料的起始點」，而非維持中點。

    (4) 即時重組（Immediate Compaction）會導致極高的 CPU 與 I/O 成本，因為每刪除一筆資料都要移動大量記憶體。實際操作中，系統僅將該 Slot 標記為空，並更新 Page Header 中的 Space Counting。

  1. 某個 workload 的特性如下：table 的每個欄位都是 CHAR 固定長度，所有 record 大小完全相同（128 bytes），且幾乎沒有 DELETE 或 UPDATE，以 sequential scan 為主。

    工程師 A 主張繼續用 slotted page，工程師 B 主張換成 fixed-length page（直接用 slot number * record size 計算 offset，不需要 slot array）。

    請分析：在此 workload 下，fixed-length page 相比 slotted page 的優勢為何？同時指出 fixed-length page 在哪種常見的 schema 變化下會立刻失去優勢。

    1. Fixed-length page 的優勢是省去省去每筆 record 4 bytes 的 slot entry（記錄 offset 與 length），以及存取時的間接定址成本；一旦加入 variable-length 欄位導致 row length 變動，fixed-length page 的機制就會失效。
    1. Fixed-length page 的優勢是省去 page header 的固定開銷；一旦有任何 DELETE 操作，因為 fixed-length page 無法標記洞洞，整個 page 需要立刻 compaction。
    1. Fixed-length page 的優勢是省去在 Page Header 維護 Slot Array 末端指標與 heap area 前端指標的運算開銷；一旦有 Record 被刪除，Fixed-length page 會因為沒有 Slot Array 記錄位移，導致該 Page 無法回收剩餘空間
    1. Fixed-length page 的優勢是 sequential scan 時可以平行讀多個 record；一旦 workload 出現任何 index 查詢，因為 fixed-length page 沒有 CTID，index 無法定址到 record。
    Answer

    Fixed-length page 的優勢是省去省去每筆 record 4 bytes 的 slot entry（記錄 offset 與 length），以及存取時的間接定址成本；一旦加入 variable-length 欄位導致 row length 變動，fixed-length page 的機制就會失效。

    解析:

    省去每筆 record 4 bytes slot entry，以及存取時不需要先查 slot array 再跳到實際位置的間接成本

    舊 row 在 heap 裡沒有新欄位的實際資料，新舊 row 長度不同，用 slot number * 128 計算 offset 會得到錯誤位置。

    (2) Page header 是 page 層級的固定開銷，slotted page 和 fixed-length page 都需要某種形式的 metadata，並不是換成 fixed-length page 就能省掉多餘開銷。失效情境的描述也有問題：fixed-length page 處理 DELETE 的方式是用一個 bitmap 標記哪些 slot 是空的，不需要立刻 compaction，這與 slotted page 的洞洞問題性質不同。

    (3) Fixed-length 的回收機制只要直接計算 offset 覆蓋即可。

    (4) Sequential scan 平行讀多個 record 的能力來自 page 是連續的磁碟區塊，這與 slotted page 或 fixed-length page 無關，兩種 layout 都可以做 sequential scan。CTID 是 slotted page 的定址方式，fixed-length page 有自己的定址機制（page ID + slot number * record size），index 一樣可以用 (page ID, slot number) 來定址，不存在沒有 CTID 就無法建 index 的問題。

  1. 某資料庫系統採用 slotted page 設計。外部模組使用 ( page_id, slot_id ) 作為 record 的唯一識別（ RID ）。目前 page 狀態如下：
    • slot array： slot 0～4 都已使用
    • page 內存在碎片（ fragmentation ）
    • 系統準備執行 compaction，將 records 重新排列以消除空洞
    • compaction 過程中， records 的實際位置（ offset ）會改變

    在 compaction 完成後，下列哪一個敘述 必然正確？

    1. 只要更新 slot array 中的 offset，外部 reference（RID）不需要改變，仍然能正確存取資料。
    1. 為了避免更新 slot array，系統應避免移動 records，而只在 free space 中重新分配空間。
    1. 所有指向該 page 的外部 reference （ RID ）都必須更新，因為 record 的 offset 改變了。
    1. compaction 之後，slot 的順序（ slot_id ）通常會重新排序，以對應新的 record 位置，提升存取效率。
    Answer

    只要更新 slot array 中的 offset，外部 reference（RID）不需要改變，仍然能正確存取資料。

    解析:

    這是 Slotted page 的標準行為。外部模組持有的 RID 是 (page_id, slot_id)。當 Page 進行 compaction 時，資料在頁內的實際位置（ offset ）會變動，但系統只需更新該 slot_id 在 Slot Array 中對應的指標。外部模組依然使用同一個 slot_id 進入，並透過更新後的指標找到資料。

    (2) Compaction 正是為了處理頁面內的 external fragmentation 而移動 Record 。如果不移動 Record，空間就無法連續化，這會導致即使總剩餘空間足夠，也無法插入較大的 Record 。

    (3) 外部 reference 不依賴 offset ，依賴的是 slot_id 。即使實體 offset 改變，只要 slot array 沒變，外部引用就不需更新。

    (4) 如果重新排序 Slot ID，就會破壞所有 RID ，導致所有外部索引（ Indexes ）都需要更新，代價極大。

  1. 某資料庫考慮把一個 table 的 page layout 從 slotted page 改成 fixed-length page。

    已知條件如下：

    page 大小為 8 KB ，page header 為 24 B。
    在 slotted page layout 下， 每筆 record 需要 4 bytes 的 slot。
    額外的 slot 讀取成本可視為 5 ns / record。
    而在 fixed-length page layout 下每筆 record 不需要額外的 slot。
    每讀一個 page 到 CPU 可見層級的成本，視為 800 ns / page。

    這個 table 的 schema 如下：

    固定部分為 48 B。
    另外有一個 comment 欄位，固定大小為 80 B。
    但是只有 5% 的 record 真的有 comment。
    其餘 95% 的 record，comment = NULL。

    現在有 1,000,000 筆 record，要做一次 sequential scan。
    請問改成 fixed-length page 之後，哪一個選項最正確地描述總讀取時間的變化與原因。

    1. 改成 fixed-length page 之後一定比較快，因為 NULL 欄位本來就不佔空間，所以 fixed-length page 不會真的浪費容量。
    1. 改成 fixed-length page 之後反而比較慢，因為雖然少了 slot 讀取，但每筆 record 都必須預留 80 B 的 comment 空間，導致每個 page 能放的 record 大幅減少；增加的 page 讀取成本超過省下的 slot 成本
    1. 兩者速度幾乎相同，因為只有 5% 的 record 有 comment，大多數 record 都不受 layout 影響。
    1. 改成 fixed-length page 之後一定比較快，因為每筆 record 都少讀一次 slot。
    Answer

    改成 fixed-length page 之後反而比較慢，因為雖然少了 slot 讀取，但每筆 record 都必須預留 80 B 的 comment 空間，導致每個 page 能放的 record 大幅減少；增加的 page 讀取成本超過省下的 slot 成本

    解析:

    這個選項正確指出 fixed-length 雖然少了 slot 讀取，但為稀疏的 variable-length 欄位預留固定空間，導致 page utilization 下降，最後整體更慢。
    詳細的計算如下: 在 slotted page 中，平均每筆 record 的資料大小為 48 + 0.05 × 80 = 52 B 再加上 slot 之後，每筆 record 平均佔用 52 + 4 = 56 B 每個 page 可用空間為 8192 - 24 = 8168 B，因此 slotted page 每頁可放 floor(8168 / 56) = 145 筆 需要的 page 數為 ceil(1,000,000 / 145) = 6897 頁。 總 page 讀取成本為 6897 × 800 ns = 5,517,600 ns 總 slot 讀取成本為 1,000,000 × 5 ns = 5,000,000 ns 總成本為 5,517,600 + 5,000,000 = 10,517,600 ns，約為 10.52 ms。 在 fixed-length page 中，每筆 record 的資料大小為 48 + 80 = 128 B 每個page的可用空間仍為 8168 B，因此每頁可放 floor(8168 / 128) = 63 筆 需要的 page 數為 ceil(1,000,000 / 63) = 15874 頁。 總 page 讀取成本為 15874 × 800 ns = 12,699,200 ns 不需要 slot 讀取成本，因此總成本為 12,699,200 ns，約為 12.70 ms。 如此可以得出 fixed-length page 的總成本比 slotted page 還高，改成 fixed-length page 反而比較慢。

  1. 某資料庫系統使用 slotted page 管理 heap records，並採用 ( page_id, slot_id ) 作為外部 record identifier（RID）。

    現在考慮以下操作序列：

    1. page 中已有多筆 variable-length records，slot array 持續增長
    1. 多次 INSERT 後，slot array 已經接近 heap area（pd_lower 接近 pd_upper）
    1. 此時執行多筆 DELETE，但系統僅將對應 slot 標記為 unused，未進行 compaction
    1. 接著嘗試 INSERT 一筆小型 record（例如 20 bytes）

    已知 heap area 中存在大量因 DELETE 留下的 holes，且這些 holes 的總大小遠大於 20 bytes

    在這種情況下，INSERT 仍然可能失敗。請問最合理的解釋是什麼？

    1. 因為 INSERT 需要同時在 heap area 放資料與在 slot array 新增 slot，如果 slot array 已經沒有連續空間，即使 heap area 有空間也無法插入。
    1. 因為 DELETE 之後 slot array 會自動縮小，導致 pd_lower 回退，覆蓋掉原本的 free space，使 INSERT 無法進行。
    1. 因為 slot_id 必須保持連續（0,1,2,...），當中間存在 unused slot 時，系統禁止插入新 record 以避免破壞 slot ordering。
    1. 因為 heap area 的 free space 是 fragmented（不連續），即使總空間足夠，也可能沒有一段連續空間同時滿足 record 存放需求，因此需要 compaction 才能成功 INSERT。
    Answer

    因為 heap area 的 free space 是 fragmented（不連續），即使總空間足夠，也可能沒有一段連續空間同時滿足 record 存放需求，因此需要 compaction 才能成功 INSERT。

    解析:

    slotted page 的新 record 是放在 pd_upper 的位置往前長的，所以 INSERT 能用的空間是 pd_lower 和 pd_upper 之間的連續間隙。 DELETE 留下的 holes 散落在 heap area 內部，並不在這個間隙中，所以即使 holes 的總量遠大於 20 bytes， pd_lower 和 pd_upper 之間的間隙太小就是放不下。 Compaction 把存活的 records 壓緊後，消除中間的 holes， pd_upper 才會往後退，騰出大塊連續空間。才能支援後續 INSERT。

    (1) slot Array 位於頁面頂端，透過 pd_lower 指標線性增長，本身不存在碎片化或不連續的問題。 此外，即使系統能重用 unused slot，INSERT 失敗的原因也不在 slot array，而在於 DELETE 留下的 holes 散落在 heap area 內部，但 INSERT 能用的空間是 pd_lower 和 pd_upper 之間的連續間隙。 所以即使 holes 的總量遠大於 20 bytes， pd_lower 和 pd_upper 之間的間隙太小就是放不下。

    (2) DELETE 並不會讓 slot array 自動縮小。slot 通常只是被標記為 unused， pd_lower 不會回退，因此不會發生覆蓋 free space 的情況。 這個選項混淆了 slot 管理與空間回收機制。

    (3) slot_id 不需要保持連續對應有效 record。 slotted page 允許中間存在 unused slots，甚至可以重用這些 slot。 slot ordering 並不是 INSERT 的限制條件，這個選項誤解了 slot array 的設計目的。

  1. 假設某資料庫設計將 slot 與 record 資料交錯存放，並往同一方向成長：

    [slot][record][slot][record][slot][record]

    相較於 slotted page layout，該設計在處理 variable-length record 時可能產生一些問題。 下列何者最不可能為此設計所造成的問題？

    1. compaction 時需要同時搬動 slot 與 record，增加實作複雜度
    1. 插入新 record 時可能需要搬移大量既有資料
    1. 會導致該 page 無法被 B+Tree 的 leaf node 正確引用
    1. page 內空間容易產生 fragmentation，且難以有效利用
    Answer

    會導致該 page 無法被 B+Tree 的 leaf node 正確引用

    解析:

    B+Tree leaf node 透過 (page_id, slot_number) 來引用 record，只要求 page 內能根據 slot number 找到對應資料。 這與 slot 與 record 的實際排列方式無關，即使採用交錯設計，仍可透過線性掃描找到 slot，因此不會影響外部索引結構的正確性。

    (1) 由於 slot 與 record 沒有分離，搬移 record 時通常也需要同步調整 slot，增加實作成本。

    (2) 由於 record 長度不固定且交錯排列，插入時可能需要將後方資料整體移動，造成 O(n) 的成本。

    (4) DELETE 或 UPDATE 後會留下零碎空間，且 slot 與 record 混在一起，使空間較難整理成連續區域。

  1. 在設計資料庫的 page layout 時，工程師需要根據資料特性選擇合適的儲存結構。Slotted Page 是一種常見的頁面內資料管理方式。請問在以下情境中，哪一種最適合使用 Slotted Page？
    1. 報表分析資料，不經常寫入，但需要高效的 sequential scan 存取，通常以連續儲存方式來提升讀取效能。
    1. 商品描述或使用者備註，通常是可變長文字欄位。
    1. 系統操作日誌，資料以 append-only 方式持續寫入，幾乎不會進行刪除或更新，例如使用者行為紀錄。
    1. 訂單編號或會員 ID，固定長度整數欄位。
    Answer

    商品描述或使用者備註，通常是可變長文字欄位。

    解析:

    Slotted Page 透過 slot table 管理每個記錄的起始位置與長度，非常適合這類變長欄位資料。它能有效利用頁面空間，避免 fixed-length layout 為每筆 record 預留最大空間造成的空間浪費，並方便在頁面內進行插入、刪除或更新操作。

    (1) 這類 workload 以大量連續讀取為主，重視 cache locality 與資料連續性。Slotted Page 的 indirection（slot → record）提供的彈性（如 variable-length 支援、record 搬移）在此場景下派不上用場，額外的 slot table 只增加空間開銷而沒有帶來好處。

    (3) 這類資料主要為連續新增，幾乎沒有刪除或更新操作。Slotted Page 提供的彈性（如 record relocation）無法發揮，反而增加 slot table 與 indirection 的額外負擔， LSM-tree 更適合此種情境。

    (4) 這類固定長度欄位資料的每筆記錄大小相同，因此可以直接以連續陣列的方式儲存，透過 index 計算即可快速定位資料位置，不需要額外的 slot table 來記錄 offset。 Slotted Page 需要額外維護 slot table，並在存取時多一層 indirection（slot → record），反而會增加空間開銷與存取成本。在沒有變長欄位或記錄搬移需求的情況下，這些機制無法帶來實質好處，因此使用 Slotted Page 的效益不大。

  1. 某個資料庫系統採用 slotted page，並以 (page_id, slot_id) 作為 record 的外部識別（RID）。 B+Tree index 的 leaf node 直接儲存這些 RID 作為指向 heap record 的 pointer。

    現在考慮以下操作序列：

    1. 某個 page 中已有 6 筆 records，分別對應 slot 0～5，且該 table 上有一個 B+Tree index。
    1. DELETE slot 2 的 record；系統將該 slot 標記為 unused，heap area 留下一個洞洞。
    1. 緊接著，INSERT 一筆新 record。

    工程師甲說：「slot 2 已經是 unused，直接把新 record 分配到 slot 2 就好，這樣不用讓 slot array 再往後長。」

    工程師乙說：「不行，即使 slot 2 是 unused，立刻重用這個 slot 仍然有問題。」

    工程師乙的說法正確嗎？原因最接近下列哪一個描述？

    1. 工程師甲正確。DELETE 已經把 slot 2 標記為 unused，代表任何人都無法再透過正常查詢存取它。此時重用 slot 2 完全安全，也能省下 slot array 不必要的增長。
    1. 工程師乙正確。因為 slot array 只能往後增長，slotted page 在結構上根本不允許重用中間的 unused slot，否則 pd_lower 指標的語義會被破壞。
    1. 工程師乙正確。因為 B+Tree index 的 leaf node 可能仍然持有指向 (page_id, 2) 的 pointer；若把新 record 放到 slot 2，這個 index entry 就會變成 dangling pointer，指向完全不同的 record。
    1. 工程師甲正確。Slot indirection 的設計目的就是讓 slot 可以自由重用，只要更新 slot array 裡的 (offset, length) 即可，外部 pointer 透過 slot array 查詢時自然會讀到新位置。
    Answer

    工程師乙正確。因為 B+Tree index 的 leaf node 可能仍然持有指向 (page_id, 2) 的 pointer；若把新 record 放到 slot 2，這個 index entry 就會變成 dangling pointer，指向完全不同的 record。

    解析:

    Slot indirection 保護的是「同一筆 record 在 page 內搬移」，前提是 slot 的身份不變。 重用 slot 給另一筆 record 會讓舊 index entry (page_id, 2) 成為 dangling pointer， 刪除 heap record 並不會自動清除 index entry，兩者生命週期獨立。

    (1) Unused 標記只代表對新查詢不可見，B+Tree index entry 不會因此自動消失。 外部仍可能持有指向 slot 2 的 pointer，重用會造成 dangling pointer。

    (2) 重用 unused slot 不需要動 pd_lower，pd_lower 只追蹤 slot array 的末端。 結構上完全允許，問題在於「安不安全」，而非「能不能」。

    (4) Indirection 保護的是「同一個 slot 的 offset 改變」，不是「slot 換了主人」。 外部 pointer 透過 slot_id 找到的永遠是同一個邏輯身份，重用後身份已被替換，indirection 無法修正這個問題。

  1. 一張 PostgreSQL 資料表有 800 筆 live rows，workload 是對每筆 row 反覆執行 UPDATE， 沒有任何 INSERT 或 DELETE。執行一段時間後，資料表佔用的磁碟空間遠超過 800 筆 row 實際所需，但 VACUUM 在這段期間完全沒有執行過。

    從 slotted page layout 的角度，直接原因是什麼？

    1. 每次 UPDATE 在 heap 寫入新版本 tuple，舊版本以 dead tuple 留在 heap 裡， 兩者共存直到 VACUUM 回收。反覆 UPDATE 累積大量 dead tuple，導致實體空間遠超邏輯資料量。
    1. UPDATE 只修改 slot entry 的 (offset, length) 指向新位置，每個 slot entry 只有 4 bytes，即使累積大量 UPDATE 也不太可能造成顯著的空間膨脹。
    1. UPDATE 直接在原位覆寫 record 資料，slot 的 (offset, length) 更新後即完成。 不會產生額外的空間消耗，空間膨脹應該是其他因素造成的。
    1. UPDATE 後舊 tuple 的空間會立刻歸還到 pd_lower 與 pd_upper 之間的 free space，因此 UPDATE 本身不太會造成空間膨脹，問題主要出在 slot array 的成長。
    Answer

    每次 UPDATE 在 heap 寫入新版本 tuple，舊版本以 dead tuple 留在 heap 裡， 兩者共存直到 VACUUM 回收。反覆 UPDATE 累積大量 dead tuple，導致實體空間遠超邏輯資料量。

    解析:

    PostgreSQL 把 UPDATE 實作為 delete + insert：舊 tuple 標記 dead，新版本寫入 heap 並分配新 slot。舊版本保留是因為其他 transaction 可能仍需讀取。 VACUUM 確認無人需要後才回收，反覆 UPDATE 因此累積 dead tuple 造成 table bloat。

    (2) UPDATE 不只是修改 slot entry，它會在 heap area 寫入一筆完整的新 tuple （含 23-byte header + null bitmap + 所有欄位資料）。舊 tuple 仍佔用 heap 空間， 主要的空間膨脹來自 heap 裡的 dead tuple 資料，而非 4-byte slot entry。

    (3) 對 variable-length record，UPDATE 後新 record 大小可能改變，原位放不下。 即使大小不變，PostgreSQL 也不會覆寫舊版本，而是寫入新 tuple 並保留舊版本，因為其他 transaction 可能仍需讀取舊版本。

    (4) DELETE 或 UPDATE 標記舊 tuple 為 dead 時，heap area 裡只會留下 hole， 該空間不會自動歸還到 pd_lower 與 pd_upper 之間的連續 free space。 需要 compaction 或 page pruning 才能整併這些 hole。
