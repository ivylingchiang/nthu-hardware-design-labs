Bloom Filter

Nini 經營一座大鳥園，裡面有 1000 個鳥籠。今天客人指名想看一種很稀有的鳥：「藍喙彩羽大鴅」。

最笨的方法，就是 Nini 一籠一籠跑去找。如果這隻鳥真的不在園裡，她還是得把整座鳥園幾乎翻完，才能回答：「沒有這隻鳥。」

所以 Nini 先做了一本很小的鳥類特徵索引簿，不記每隻鳥在哪一籠，只記一些快速判斷用的特徵。每當新鳥進園，Nini 就根據幾個特徵（鳥喙顏色、翅膀長度、尾羽形狀、叫聲頻率），在索引簿上做記號。客人問「藍喙彩羽大鴅」在不在時，Nini 不必先衝進鳥園，只要先翻這本小簿子：只要有任何一個特徵記號對不上，她就能立刻說「這隻鳥一定不在園裡」，完全不用跑去查鳥籠。如果所有特徵都對得上，她也只能說「有可能在」，這時才值得真的進鳥園找。

這就是 Bloom filter：它不能保證「一定存在」，但可以很快保證「一定不存在」，用很少的記憶體，省掉大量白跑的 disk I/O。

Key Word Definition/ Discussion
Bloom filter

Bloom Filter 是一種空間效率極高的機率型資料結構，由一個長度為 m 的 bit array 和 $k$ 個獨立的 hash functions 組成。它用於測試一個元素是否屬於一個集合，能給出「絕對不存在」或「可能存在」的答案。

Bloom filter 的組成

一個長度為m 的 bit array（所有 bit 初始為 0），加上k 個獨立的 hash function。

插入一個元素時，用k 個 hash function 分別算出k 個位置，把這k 個 bit 都設為 1。查詢一個元素時，同樣算出k 個位置，檢查這k 個 bit 是否全部為 1。如果全部是 1，回答「可能存在」；如果任何一個是 0，回答「絕對不存在」。

注意 bit array 裡面只有 0 和 1，沒有存任何原始資料。你沒辦法從 Bloom filter 裡面「取出」元素，也沒辦法列舉裡面有哪些元素。它只能回答一個問題：這個東西在不在？而且回答還不是百分之百準確。

False Positive 與 False Negative

Bloom filter 保證沒有 false negative。如果一個元素確實被插入過，查詢時它對應的 kk 個 bit 一定都是 1（因為插入時已經設為 1 了，而且 Bloom filter 不支援刪除，bit 一旦設為 1 就不會變回 0）。所以「存在的東西一定查得到」。

但 Bloom filter 允許 false positive。一個從未被插入的元素，查詢時對應的 k 個 bit 可能「恰好」都被其他元素設成了 1。這時 Bloom filter 會錯誤地回答「可能存在」。你把它當成「在裡面」，結果去 disk 上一查，發現根本沒有。

這是 Bloom filter 的根本性質：它說「不在」就真的不在，它說「在」則未必。在儲存系統的應用場景中，false positive 只是浪費一次 disk read，不會造成正確性問題。但 false negative 如果發生（告訴你不在但其實在），就等於資料不見了，這才是災難。Bloom filter 的設計正好符合這個需求。

false positive rate (FPR) 取決於三個參數：

bit array 大小 m、hash function 數量 k、已插入的元素數量 n。

一百萬個元素，只用 1.14 MB 就能達到 99% 的過濾準確率。相比之下，如果你用 hash set 存這些元素（假設每個 key 平均 20 bytes），至少需要 20 MB，Bloom filter 的空間效率是 hash set 的 17 倍以上。

怎麼選參數

你通常知道兩件事：預計要存多少元素（n），以及可以接受多少的 false positive rate（目標 FPR）。要算出需要多大的 bit array（m）和幾個 hash function（k）。

Bloom Filter 有 Diminishing Return ：

m/n 從 10 增加到 15（多 50% 的記憶體），FPR 從 0.82% 降到 0.03%，降了 27 倍。但繼續從 15 增加到 20（再多 33% 的記憶體），FPR 只從 0.03% 降到 0.001%，降幅變得很小。所以大部分系統選在 m/n=8∼12 之間就夠了。

為什麼不能刪除？

標準 Bloom filter 不支援刪除，因為多個元素的 hash 位置可能重疊。如果你把某個元素對應的 bit 設回 0，可能會把另一個元素的 bit 一起清掉，導致本來存在的元素被誤判為不存在，也就是產生 false negative。

如果需要刪除功能，可以使用 counting Bloom filter：把每個 bit 換成一個計數器（通常 4 bits），插入時計數器加 1，刪除時減 1。這樣就能安全地刪除而不影響其他元素。代價是空間從每位置 1 bit 變成 4 bits，記憶體用量是標準版的 4 倍。

在 LSM-Tree 中的應用

Bloom filter 最經典的應用場景之一就是 LSM-Tree。LSM-Tree 的 read path 需要逐層搜尋多個 SSTable 檔案，查一個不存在的 key 可能要白跑好幾層 disk I/O。如果在每個 SSTable 配上 Bloom filter，查詢前先問一句「這個 key 在不在這個檔案裡？」，回答「不在」就直接跳過，省掉大量無謂的 disk read。下次上課我們會深入講 LSM-Tree 的結構，到時候會更清楚 Bloom filter 在裡面扮演多重要的角色。

延伸：Cuckoo Filter

標準 Bloom filter 有兩個比較麻煩的限制：不能刪除，而且查詢效能會隨著 bit array 填滿而下降（越來越多 bit 是 1，false positive rate 上升）。2014 年 CMU 的研究者提出了 cuckoo filter，用不同的思路解決了這些問題。

Cuckoo filter 不用 bit array，而是把元素的 fingerprint（一小段 hash 值）存進一張類似 hash table 的結構，用 cuckoo hashing 的方式處理碰撞：一個元素有兩個候選位置，插入時如果兩個都滿了，就把其中一個「踢走」到它的另一個候選位置，像杜鵑鳥把別人的蛋踢出巢一樣。因為存的是 fingerprint 而不是單純的 bit，刪除時可以精確移除特定元素的 fingerprint，不會影響其他元素。

在相同的 FPR 下，cuckoo filter 的空間效率和 Bloom filter 差不多，但額外支援了刪除操作，而且每次查詢只需要檢查 2 個位置（對 cache 非常友善），比 Bloom filter 的 kk 次 random access 更快。不過 cuckoo filter 有容量上限，塞太滿的時候插入可能失敗，這點和 Bloom filter 的「永遠能插入」不同。

運作流程：

插入：將元素通過 k 個 hash functions 得到 k 個索引，並將位元陣列中對應的位置全部設為 1。

查詢：檢查該元素對應的 k 個位置。若有任何一個位元為 0，則該元素必定不在集合中；若全部為 1，則該元素可能在集合中。

關鍵屬性：

No False Negatives：如果東西在裡面，一定查得到。

不可取出性：陣列不儲存原始資料，因此無法列舉集合內容，也無法還原 Key。

靜態性：標準 Bloom Filter 一旦建立，大小 m 就固定了，且不支援刪除。

Pitfall:

過載崩潰：當插入元素數量 n 超出預期（n > m/k 太多時），bit array 會幾乎全變成 1，此時 False Positive Rate 會趨近 100%，失去過濾功能。

不支援刪除：隨意將位元由 1 變為 0 會破壞其他元素的完整性。如果強烈需要刪除，請考慮 Counting Bloom Filter。

雜湊選擇：如果 k 個 hash functions 相關性太高，會導致位元分布不均，誤判率會比理論值高出許多。

Hash function

在 Bloom Filter 中，雜湊函數負責將任意長度的輸入數據映射到 [0, m-1] 的範圍內，作為位元陣列的索引。

效能要求：

因為一次操作需要 k 次雜湊，通常使用 Non-cryptographic hash（如 MurmurHash3, CityHash, xxHash），運算速度極快且分布均勻。

優化技巧：

實務上不需要真的寫 k 個演算法，通常利用兩個雜湊值 h1(x) 與 h2(x) 透過公式 gi​(x)=h1(x)+i⋅h2(x) 來模擬出 k 個雜湊函數。

Pitfall:

運算開銷：k 值的設定是雙面刃。k 越大，FPR 越低，但 CPU 計算雜湊的次數就越多。

Bit array

一組連續的記憶體空間，最小單位是 1 bit。這是 Bloom Filter 節省空間的核心實體。

存取效率：由於是連續空間，對硬體緩存（Cache）友善；但當 m 非常大時，隨機存取 k 個不同位置可能會造成 Cache Miss。

Pitfall:

記憶體對齊：在程式實作時，通常是用 byte 或 long 陣列模擬，存取特定 bit 需要正確的位元運算（Bitwise offset）。

False positive

當查詢一個不存在的元素，但其對應的 k 個位置剛好都被其他元素標記為 1 時，導致過濾器錯誤回報「存在」。

數學期望：FPR≈(1−e−kn/m)k。

系統設計觀點：在資料庫場景中，False Positive 只是增加了一次不必要的 Disk I/O，這被視為「效能損失」而非「正確性錯誤」。

Pitfall:

累積風險：如果後端查詢（Disk Read）極其昂貴，必須將 FPR 設定得極低，這會導致記憶體需求 m 顯著增加

Probabilistic data structure

一類以「不保證 100% 精確」為代價，換取極高空間效率與查詢速度的演算法與資料結構。

成員：除了 Bloom Filter，還包括 HyperLogLog（算不重複數量）、Count-Min Sketch（算頻率）。

Pitfall:

場景誤用：不可用於對錯誤「零容忍」的場景（如：銀行帳戶餘額查詢）。

Reference:

Space efficiency

Bloom Filter 儲存單個元素所需的空間與元素本身的長度無關，僅與要求的誤判率有關。

優勢對比：在 FPR = 1% 時，每個元素僅需約 9.6 bits。相比之下，存儲原始字串可能需要數百 bits。

Pitfall:

Diminishing Returns (邊際遞減)：當你已經投入一定記憶體後，再增加記憶體所能降低的誤判率會越來越不明顯。通常設定在 m/n≈10 是最經濟的選擇。

Key Concepts
理解 Bloom filter 的結構：使用 k 個 hash function 將元素映射到一個 bit array，插入時設定對應位元為 1，查詢時檢查所有對應位元

Answer

Bloom filter 由一個長度為 m 的 Bit Array（初始全為 0）和 k 個不同的 Hash Function 組成。不存資料本身，只存資料 hash 後的「特徵點」。

Key Concept

Bit Array, Multiple Hash Functions, Space Efficiency。

Detail

它不像是 Hash Map 會把原始資料字串存下來。當插入元素時，資料會分別經過 k 個 hash function，得出 k 個介於 0 到 m-1 的數字（索引位置），然後將陣列中這 k 個位置的 bit 設為 1。查詢時，做一樣的動作，檢查那 k 個位置：如果全部是 1，回答「可能存在」；如果有任何一個是 0，回答「絕對不存在」。

理解 Bloom filter 保證沒有 false negative（存在的元素一定會被判定為存在），但允許 false positive（不存在的元素可能被誤判為存在）

Answer

只要你存過，那幾個 bit 一定是 1，所以絕對查得到（無 FN）。但如果沒存過，那幾個 bit 有可能被「其他人」不小心設成 1 了，導致誤判（有 FP）。

Key Concept

False Positive (誤報), False Negative (漏報), Hash Collision (雜湊碰撞)。

Detail

這源於 bit 的狀態不可逆（只能 0 變 1）。曾經插入的元素，其對應的 k 個 bit 永遠保持 1，因此查詢該元素時永遠會過關，這是保證「No False Negative」的根本。相對地，由於不同資料可能算出一樣的 hash 位置（Collision），當陣列逐漸變擠，你查詢一個新資料時，它對應的 k 個位置可能「剛好」都被先前其他資料設為 1 了，系統無從分辨，只能給出 False Positive。

理解 false positive rate 與 bit array 大小 m、hash function 數量 k、以及已插入元素數量 n 之間的數學關係

Answer

陣列越長 (m)，FPR 越低；
存入的元素越多 (n)，FPR 越高；
Hash 函數數量 (k) 則有一個「黃金比例」能達到最佳的 FPR。

Key Concept

False Positive Rate (FPR), Bit/Element Ratio (m/n), Diminishing Returns (邊際效益遞減)。

Detail

FPR 的數學期望值大約是 (1−e−kn/m)k。

簡單來說，如果 Bit array 被填滿 1 的比例太高，FP 的機率就會飆升。
為了降低 FPR，我們需要提高每個元素能分配到的 bit 數量（也就是增加 m/n 的比值）。
然而增加 m 會遇到邊際效益遞減：

一開始增加記憶體可以讓 FPR 呈指數級下降，但降到極低時，再加倍記憶體也只會微幅改善。(大概比例是8 - 12是最好的)

知道如何根據預期的元素數量與可接受的 false positive rate 來選擇合適的 bit array 大小與 hash function 數量

Answer

工程師不需要瞎猜參數，可透過對數公式，由 n 與 FPR 嚴格推導出最佳的陣列大小 m，再推導出最佳的 Hash 次數 k。

Key Concept

Optimal Parameter Selection, Memory Allocation。

Detail

在系統設計時，我們會先評估「最大資料量 $n$」以及「業務能接受的誤判率 FPR」。接著帶入兩條黃金公式：

1. 最佳的 bit array 大小：m=−(ln2)2nln(FPR)​

2. 最佳的 hash 函數數量：k=nm​ln2

透過這兩條公式，我們可以精確地預估系統需要開出多少 MB 的記憶體。

為什麼 Bloom filter 保證沒有 false negative，但無法避免 false positive？請從 bit array 的操作機制解釋。

Answer

無 FN 是因為設為 1 的 bit 永遠不會變回 0；無法避免 FP 是因為不同資料產生的 Hash 位置會不可避免地產生重疊。

Key Concept

Irreversible State (不可逆狀態), Bit Overlap。

Detail

從 Bit 操作來看，Bloom Filter 不支援把 1 設回 0 的操作。這代表「凡走過必留下痕跡」，只要存進去，痕跡永遠在，所以絕不會漏報（FN）。但也因為空間 (m) 是有限的，隨著資料量 (n) 增加，越來越多位元變成 1。當系統去檢查一個從未輸入過的字串時，它 Hash 出來的 k 個位置，可能「碰巧」踩在別人留下的 1 上面。因為我們沒有儲存原始字串來做 100% 比對，所以無法避免 FP。

一個系統要追蹤 5,000,000 個 URL 是否出現在黑名單中，可接受的 false positive rate 為 0.1%。請計算需要多大的 bit array（多少 MB）以及最佳的 hash function 數量 k。

Answer

需要約 8.57 MB 的 Bit Array，且最佳的 Hash function 數量為 10 個。

Key Concept

Parameter Calculation, Storage Overhead。

Detail

計算 m：

公式 m=(ln2)2−nln(FPR)​

n = 5,000,000, FPR = 0.001

m=0.48045−5,000,000×(−6.9077)​≈71,887,938 bits

將 Bits 換算為 Megabytes：71,887,938÷8÷1024÷1024≈8.57 MB。

計算 k：

公式 k=nm​ln2

平均每個元素分配到的 bits (m/n) 約為 14.37

k=14.37×0.6931≈9.96

結論：只花不到 9MB 的 RAM 就能過濾 500 萬筆資料，這就是 Bloom filter 驚人的空間效率！

為什麼標準 Bloom filter 不支援刪除操作？如果硬把某個元素對應的 bit 設回 0，可能產生什麼後果？Counting Bloom filter 如何解決這個問題，代價是什麼？

Answer

因為 Bit 是共用的，硬設為 0 會波及其他元素，產生致命的 False Negative。Counting Bloom filter 將 bit 改為整數計數器，能支援刪除但代價是記憶體爆增。

Key Concept

Shared Bits, False Negative Hazard, Counting Bloom Filter

Detail

假設字串 A 和字串 B 的 Hash 位置剛好都包含index 5。如果你刪除字串 A，並把index 5設回 0，這時字串 B 的資料就「被破壞」了。下次你查詢 B 時，系統看到index 5是 0，就會斷言「B 絕對不存在」，產生系統無法容忍的 False Negative。

Counting Bloom filter的解法是將每個位置從1 bit變成例如4 bits的計數器（Counter）。插入時+1，刪除時-1，歸零才代表全空。代價非常直接：每單位空間消耗膨脹 4 倍，犧牲了原本極致的 Space Efficiency。

在什麼情境下 Bloom filter 的效益最大？在什麼情境下效益很小甚至不值得用？請從 workload 的 read/write 比例和 key 存在率的角度分析。

Answer

在「讀多寫少」且「大部分查詢的資料都不存在」時效益最大；若「寫入/更新極頻繁」或「絕大部分查詢都會命中」則不值得用。

Key Concept

I/O Filter (I/O 擋板), Read/Write Ratio, Hit/Miss Rate

Detail

  • 效益最大 (做為擋板)：

    例如惡意網址黑名單、防止快取穿透 (Cache Penetration)、LSM-Tree 的磁碟讀取優化。在這些情境下，超過 99% 的查詢都是「不在資料庫裡」的。Bloom filter 可以純靠記憶體瞬間給出「絕對不存在」的答案，幫資料庫擋下海量的無效 Disk I/O。

  • 效益極小 (甚至拖慢效能)：

    如果系統大部分時間都在 UPDATE 或 DELETE（Bloom filter 處理很差），或是系統的使用者查詢的通常是「一定存在於資料庫裡的熱門資料」。因為只要回答「可能存在」，你終究還是得去查 Disk 驗證。這時 Bloom Filter 不僅沒省到 I/O，反而白白浪費了 CPU (算 Hash) 與 RAM (存 Array)。

    Answer

    提議不可行。當 n 超出原始估計時，應重建更大的 Bloom filter，而不是只在查詢端單獨增加 hash 數量。

    解析:

    Bloom filter 的參數是整體設計的一部分：m、k、n 彼此耦合。 n 增加但 m 不變時，bit array 會更快飽和，FPR 上升是預期結果。 正確作法是重建更大 m，並用一致的 k 重新插入； 不能只改查詢邏輯，否則會引入 false negative。

    (1) 這個說法忽略了插入與查詢必須使用同一組 hash 定義。若插入時只設了 k 個位置， 查詢卻改成檢查 2k 個位置，對已存在元素也可能因新增檢查位元為 0 而被判定不存在， 會導致 false negative，破壞 Bloom filter 的核心保證。

    (2) 沒有 false negative 不代表 FPR 恆定。 在固定 m 下，n 增加會提高位元被設為 1 的機率，進而提升 false positive rate。

    (3) FPR 並非只由 k 決定，還受 m 與 n 影響，且在固定 m、n 下存在最佳 k。 k 過大反而會讓 bit array 更快趨近全 1，造成 FPR 惡化。
